一个 kernel PR 通常带着两样证据： 一个通过的单测， 一张加速比表格。 两样都是真的。 然后这个 kernel 进入模型， 接下来会发生三种情况之一： 模型开始输出乱码； 多卡运行挂住， 不报任何错； 或者一周都相安无事， 直到某个请求走进一条没人试过的路径。 维护 kernel 库的人会把它总结成一句话： *单测过了， 跑模型出问题。*

这不是某一个 bug， 而是测试覆盖范围上的缺口。 单测只在少数几个点上检查 kernel： 几个形状、 随机输入、 一张卡、 一个 stream、 一个新进程。 模型运行则是一个大得多的空间上的分布。 测试只能证明它检查过的点正确， 而模型几乎所有时间都在别处。

## 七个维度

先从任何 kernel 都成立的事实出发。 kernel 的输出不只取决于参数的值：

1. **形状**： 决定哪些代码路径和 tile 尾块会执行。
2. **数值**： 决定会碰到哪些数值区间。
3. **布局和 dtype**： 和输入的生产方之间的契约。
4. **执行环境**： graph 捕获、 stream、 缓存、 进程的生命周期。
5. **时序**： 哪个 wave 先到。
6. **规模**： 有几张 GPU 参与。
7. **软件和硬件**： 构建、 版本， 以及实际运行的那份副本。

单测之所以便宜， 是因为它把大多数维度固定在方便的值上： 小的、 按 tile 对齐的形状， `torch.randn` 生成的输入， 测试自己的辅助函数生成的布局， 默认 stream 上的 eager 模式， 调用一次， 一张卡， 仓库自己的构建。 对快速测试来说， 这是正确的取舍。 代价是每个被固定的值都藏起了一个 kernel 行为会改变的区间。

为什么不全部测一遍？ 因为这个空间是乘积： 10 种形状 × 5 种数值分布 × 3 种布局 × 4 种执行模式 × 3 种 GPU 数量， 已经是 1,800 种配置， 而时序根本不是一个能设置的参数。 目标不是穷举， 而是把测试点放在行为会改变的地方。

## 缺口 1： 形状与尺寸

kernel 是为常见情况写的， 其余情况靠补丁。 它高速处理完整的 tile， 用 mask 或 clamp 处理尾块。 它用 32 位算术计算地址， 因为 64 位地址运算在每次读取时都要多花寄存器和指令。 这两个选择在一个范围内都是对的， 超出范围就会悄无声息地出错。

32 位的选择有两道悬崖： 有符号 32 位索引在 2³¹ 处回绕， 相对 buffer 起点的 32 位字节偏移在 2³² 字节（4 GiB） 处回绕。 在 [FlyDSL #879](https://github.com/ROCm/FlyDSL/pull/879) 里， Kimi-K2.6 在 TP 1 时， MoE 第一阶段的权重张量是 385 × (2·2048) × 7168 × 0.5 字节， 约 5.3 GiB。 kernel 用一个带 32 位偏移的 buffer resource 访问它， 于是 4 GiB 之后的 expert 读到了别的 expert 的权重， 模型输出乱码。 在 TP 2 时， 张量被切成约 2.6 GiB， 落在悬崖之下， 这正是 bug 只在 TP 1 出现的原因。

安静的版本更糟。 在 [FlyDSL #1236](https://github.com/ROCm/FlyDSL/pull/1236) 里， 形状为 (4, 2²⁹) 的张量有 2³¹ 个元素； 用 int32 计算的总大小回绕成负数， 每个 lane 都写到了错误的位置， 而这些位置仍在范围之内， 所以没有任何报错。 [FlyDSL #1020](https://github.com/ROCm/FlyDSL/pull/1020) 在展平后的 FP8 attention 形状达到 2³¹ 个元素时报 `struct.error`， 在 head 维度 128、 64 个 head 时， 也就是任何 131,072 个 token 以上的序列。 [FlyDSL #1131](https://github.com/ROCm/FlyDSL/pull/1131) 的一次重构通过了针对性测试， 随后在完整 CI 里 M = 16 和 M = 33 的两个 FP16 tile 上失败， 第二天在 [#1189](https://github.com/ROCm/FlyDSL/pull/1189) 里被回滚。

每个带调优表的 kernel 库还有这个缺口的结构性版本： 调优表里没有的形状， 会退回默认配置或启发式配置。 测试通常跑调优过的形状， 所以回退配置往往是生产环境在跑的代码里测得最少的一段。

**能抓住它的测试：** 张量刚好低于和高于 2³¹ 个元素、 2³² 字节； 不切分时的最大部署， 而不是切分后的部署； 每一维的尾块； 以及一份明确列出 「没有调优表项的生产形状」 的清单。

## 缺口 2： 真实数据

真实的激活和权重不是随机的。 路由分数会扎堆， 经常几乎相等。 训练过的 attention 很尖锐。 预热流量可能全是相同的 token。 对随机输入精确无误的代码， 在这几种情况下都可能出错。

[FlyDSL #1213](https://github.com/ROCm/FlyDSL/pull/1213) 是最干净的例子。 [#1204](https://github.com/ROCm/FlyDSL/pull/1204) 的 MonoKernel 通过了自己的测试， 被合入； 一天之后， 在 ATOM 引擎里用真实的 GLM checkpoint 验证时发现： 把 expert ID 打包进路由分数， 在分数接近时会选错 expert。 一次抓取的 TP8 路由回放里， 正确的是 expert 226， kernel 选了 92。 随机分数几乎不会出现接近的情况。

[FlyDSL #1020](https://github.com/ROCm/FlyDSL/pull/1020) 展示了数值的一面。 一个 FP8 attention kernel 把 softmax 概率转成 e4m3， 而 e4m3 能表示的最小值是 2⁻⁹， 于是大部分概率下溢成 0， 归一化因子却仍然把它们算在内。 V 全为 1 时， 输出是 0.637， 而不是 1.0。 PR 写明只有尖锐的注意力会暴露这个问题， 随机初始化的模型不会。

**能抓住它的测试：** 回放从真实模型运行里抓取的激活、 路由分数和权重， 并刻意加入对抗性的值： 完全相等、 几乎相等、 one-hot 分布、 所有 token 落在同一个 expert。

## 缺口 3： 接口契约

kernel 相对一份契约正确： 布局、 dtype、 stride、 索引宽度、 跳过哪些行。 单测在结构上就把契约藏起来了， 因为输入由它自己的辅助函数写出， 参考实现也由它自己读取。 在模型里， 生产方是 checkpoint 加载器、 上一个 kernel， 或者别人写的框架。

还是 #1213： 真实 checkpoint 用了一种 kernel 不支持的权重 scale 布局； 参考实现跟随调用方的默认 dtype， 默认 dtype 一改成 BF16， 参考实现本身就变了； 很短的上下文会让融合的 indexer 选到超出实际上下文的位置。 在 [FlyDSL #1234](https://github.com/ROCm/FlyDSL/pull/1234) 里， 一次自动评审指出索引 buffer 按原始 int32 读取， 而 PyTorch 默认是 int64（这是评审发现， 不是实际观察到的故障）。

**能抓住它的测试：** 用每个 kernel 的真实生产方喂它， 并在 kernel 入口检查 dtype、 形状、 stride 和布局。

## 缺口 4： 执行环境

引擎会把 kernel 录进 CUDA 或 HIP graph， 使用旁路 stream， 并让一个进程活好几天。 在 [aiter #4494](https://github.com/ROCm/aiter/pull/4494) 里， 一个 split-K GEMM 的 semaphore 工作区在 graph 捕获下归属错误， 回放时一直空转： 「设备卡死， 不返回错误的数字， 也不会恢复」。 Kimi-K3 在 TP 8 下预热时挂住。 [FlyDSL #171](https://github.com/ROCm/FlyDSL/pull/171) 修复了一个只在 PyTorch 2.9 上出现、 在 2.8 上不出现的捕获段错误。 [FlyDSL issue #317](https://github.com/ROCm/FlyDSL/issues/317) 和 [aiter #6127](https://github.com/ROCm/aiter/pull/6127) 都发现了 JIT 缓存 key 的漏洞， 让一种配置复用了另一种配置的编译结果。

**能抓住它的测试：** 在测试里捕获并回放， 使用非默认 stream， 在同一个进程里先调用几种形状， 再检查最后一次的结果。

## 缺口 5： 偶发竞争

竞争取决于哪个 wave 先到， 所以测试只是在对一个概率抽样。 在 [aiter #4841](https://github.com/ROCm/aiter/pull/4841) 里， 一个跨 block barrier 竞争的候选修复， 仍然在 292,889,600 次行级调用里卡死了 7 次， 大约四千两百万次一次； PR 写明这个竞争可能卡死 GPU， 让整个 DP-attention 服务停住， 而健康检查接口还在正常应答。

算术是这样的： 单次调用出错的概率是 p， N 次调用至少出错一次的概率是 1 − (1 − p)ᴺ。 当 p ≈ 2.4 × 10⁻⁸ 时， 1,000 次调用的测试只有 0.002% 的机会抓到它。 一个假设每秒 10,000 次调用的服务， 大约半小时就超过 50%。 在 [aiter #6127](https://github.com/ROCm/aiter/pull/6127) 里， 相同的预热 token 让路由严重倾斜， 暴露了一个 LDS 槽位复用竞争， 几次调用之内就会出错； 随机路由会把它藏起来。 [FlyDSL #1235](https://github.com/ROCm/FlyDSL/pull/1235) 直接写明 「测试无法强制触发竞争所需的 wave 顺序」。

**能抓住它的测试：** 用同一个输入调用很多次， 要求输出逐位一致； 有 sanitizer 就跑一遍； 用倾斜的输入加压。

## 缺口 6： 多卡

多卡协议出错时表现为挂起， 而不是算错。 在 [aiter #6446](https://github.com/ROCm/aiter/pull/6446) 里， 一个 all-reduce 按消息大小计算槽位步长； 相邻调用的大小一变， 快的 rank 就覆盖了慢 rank 还没读的槽位， 慢 rank 于是永远轮询。 它在 vLLM 的 CI 里以 TP 2 下的 RCCL watchdog 超时出现。 仓库自己的多卡 CI 运行这个测试时没带大小参数， 从未走到 TP 2 和 TP 4 的用例。 连大小的先后顺序都有影响： TP 4 下， `[32768, 28800]` 循环从不重叠， `[32768, 32768, 28800]` 会重叠。 [FlyDSL #954](https://github.com/ROCm/FlyDSL/pull/954) 修复了在评审和 serving 测试中发现的多 rank dispatch 挂起。

**能抓住它的测试：** TP 2、 TP 4 和 EP， 让相邻调用的消息大小不断变化， 并套上看门狗。

## 缺口 7： 没测到的软件

生产环境通常运行的是锁定版本的下游副本。 [FlyDSL #1277](https://github.com/ROCm/FlyDSL/pull/1277) 说得很直接： 一个改动 「可能弄坏 vLLM 在生产环境运行的 kernel， 而这里的 CI 仍然全绿」， 例如删掉一个只有 vLLM kernel 还在用的旧分配器。 在 [aiter #3683](https://github.com/ROCm/aiter/pull/3683) 里， 不受支持的架构上一个导入阶段的 `KeyError` 让所有 flash-attention 导入失败。 [aiter #5133](https://github.com/ROCm/aiter/issues/5133) 发现有 141 个 pytest 函数从未执行， CI 却记为通过。

**能抓住它的测试：** 测引擎锁定版本的那份副本， 给下游导入的 API 加契约测试， 并让测试框架在一个用例都没收集到时直接失败。

## 为什么新架构更严重

每个缺口在成熟硬件上都存在。 到了新的 GPU 架构上， 它们会同时变大： 移植来的代码带着对 wave 大小、 越界检查和 barrier 的旧假设； 编译器还年轻； 调优表覆盖的形状少， 更多流量走进回退路径； CI 机器少； 更大的单卡显存让不切分的张量越过 32 位悬崖。 这不需要任何新类型的 bug， 只需要七个缺口里有更多个同时敞开。

## 验证阶梯

每一级都能抓到下一级抓不到的一类 bug， 成本也更高：

| 级别 | 关闭的缺口 | 要跑什么 |
|---|---|---|
| 1. 边界单测 | 形状 | 尾块、 2³¹ / 2³² 大小、 未调优的形状、 张量后的 guard page |
| 2. 回放真实输入 | 数据 | 抓取的激活和分数、 相等、 倾斜 |
| 3. 测接缝 | 契约 | 真实生产方 → 消费方、 kernel 入口检查 |
| 4. 生产执行模式 | 环境 | graph 捕获与回放、 旁路 stream、 同一进程的多种形状 |
| 5. 重复跑， 要求确定性 | 时序 | N 次调用逐位一致、 sanitizer、 倾斜负载 |
| 6. 多卡协议 | 规模 | TP 2 / TP 4 / EP、 变化的大小、 看门狗 |
| 7. 下游 | 软件 | 引擎用的副本和版本、 API 契约测试 |
| 8. 端到端模型 | 全部七个 | 固定随机种子的精度评测（例如 GSM8K）、 吞吐、 先单卡再多卡 |

顶端的模型同时覆盖全部七个维度， 所以它是最后一级， 而不是唯一的一级。 模型出错时， 本该抓住这个 bug 的那一级会告诉你该补哪个测试。

## 结语

「单测过了， 跑模型出问题」 听起来像运气不好， 其实不是。 单测是样本， 模型是总体。 上面每一个公开 bug， 都待在测试固定不动的某个维度里。 说出是哪个维度， 缺的那个测试通常就一目了然。
