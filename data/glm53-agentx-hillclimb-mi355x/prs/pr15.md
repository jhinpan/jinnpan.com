# #15 [Feat] [MI355X] glm53: Serve MTP verify steps on the monokernels
merged 2026-10-22T20:16:46Z 01852a313 +358/-64 files 7

## Motivation

**Summary.** This PR lets GLM-5.3 run MTP on the monokernels. MTP is EAGLE speculative decoding with the NextN draft layer of the model. The PR fixes three defects that stopped MTP. On 8x MI355X at TP8, the monokernels with MTP decode 68.8% faster than the normal path with MTP for one request. For two requests, they decode 33.2% faster. On 4x MI355X at TP4, the gain for one request is 29.9%. GSM8K accuracy does not change.

**Terms.**

- A **verify step** is a step of the target model that checks the draft tokens.
- A **verify row** is one token in a verify step. With 3 draft steps, each request has 4 verify rows.
- A **draft chain** is the set of verify rows of one request.

**Problem.**

- The InferenceX GLM recipes for MI355X all use MTP ([`glm5.2/sglang`](https://github.com/SemiAnalysisAI/InferenceX/tree/d892f56af2111329fd15ae0aa15b05274692799c/inferencex-e2e/benchmarks/single_node/srt-slurm-recipes/glm5.2/sglang)).
- `--monokernel-backend amd` refused to start GLM-5.3 when MTP was on.
- The monokernels without MTP were slower than the normal path with MTP. Thus the monokernels had no use in the production configuration.

| Workload, one request at a time | Normal path with MTP | Monokernels without MTP |
|---|---|---|
| InferenceX agentic coding, TP8, 8x MI355X, sgl-amd-mono `e952b22`, 1 run each | TPOT p50 5.66 ms | TPOT p50 10.32 ms |
| 4096-token prompts, TP4, 4x MI355X (the speed test of this PR) | 191.6 tok/s | 142.0 tok/s |

**Causes.** We found three defects. Defect 1 stopped the server, and it also hid defects 2 and 3.

| # | Defect | Effect |
|---|---|---|
| 1 | The spec did not list `Feature.SPECULATIVE_DECODING`. | SGLang refused to start: `speculative decoding is in use and the spec does not accept it`. |
| 2 | `_Built._step` read the key count of each row from `forward_batch.seq_lens`. In a verify step, `seq_lens` holds the prefix length of each request, not of each row. | Each verify row attended only the prefix of its request. The row did not attend its own token or the draft tokens before it. At TP8, a verify step of two requests stops with a tensor size error (8 rows, 2 prefix lengths). |
| 3 | The paged indexer read the earlier draft keys of a verify row from the index cache. The cache task writes these keys in the same launch with plain stores, and the scoring workgroups do not see these stores. | The indexer scored the old contents of these cache slots. The top-2048 selection can then drop correct keys or add wrong keys. |

The sparse MLA stage (`patch_new_kv`) and the unpaged indexer read all keys of the current launch from the mailboxes of their rows. The paged indexer read only the own key of each row from its mailbox.

## Modifications

**Base.** The branch merges `main` at `0bce188` ([#12](https://github.com/sgl-project/sgl-amd-mono/pull/12)). #12 moved the FlyDSL helpers of `glm53/gfx950/ops.py` to `common/ops.py`. The kernel change uses the same helpers as `patch_new_kv`.

- `glm53/spec.py`
  - The spec accepts `--speculative-algorithm EAGLE`. SGLang changes `NEXTN` to `EAGLE`.
  - The spec accepts one draft chain for each request: `--speculative-eagle-topk 1`, and draft tokens = draft steps + 1. It refuses other settings at startup and gives the reason.
  - `_Built._step` calculates the keys of each row from the position of the row. Row j of a request attends the prefix and j + 1 more keys. In a decode step, this value is equal to `seq_lens`.
  - A verify row after the context limit gets the last position of the context. The scheduler discards these rows. The rotary table and the score rows of the indexer end at the context limit.
- `glm53/gfx950/kernel.py`
  - The paged indexer scores each key that a row of the current launch writes from the `index_k_new` mailbox of that row. It finds these keys by slot, as `patch_new_kv` does.
  - In a decode step, the only such key is the own key of the row. This key came from the mailbox before this change too.
- `glm53/check.py`
  - `SGLANG_AMD_MONO_CHECK=1` also compares the top-k of each indexer layer with the top-k of SGLang.
  - The new bound `layer.topk_own.max_abs = 0` fails a check when the kernel drops a key of the draft chain that SGLang selects.
  - Before the launch of an indexer layer, the check keeps the index keys that SGLang wrote for the step in the cache, and sets their scales to -1e30. The kernel multiplies the score sum of a key by its scale. Thus a kernel that reads these keys from the cache drops each key with a positive score, and `layer.topk_own` fails. Before, the check put back the old cache contents, and these contents decided if a check failed (test 6).
- Tests
  - Unit tests: the keys of verify rows, the positions after the context limit, the refused draft settings, the `layer.topk_own` count, and the cache bytes that the check changes. The tests for the keys and the positions fail on the code before the fix.
  - E2E tests (TP8): GSM8K and the MTP accept length, and the layer check on verify steps with more than 2048 keys.
  - The fault test also accepts the message `on address (nil)`, as `test_minimax_m3_server.py` does. ROCm in the test image prints this message, so the old match failed at `e952b22` too.
- `README.md`: the coverage table and an MTP example.

**Coverage.** The monokernels run verify steps of up to 8 rows (4 rows at TP4). With 3 draft steps, this is 1 or 2 requests at TP8 and 1 request at TP4. Larger steps, the draft model, and prefill use the normal path.

**No change.** Decode steps, the DeepSeek-V4.1 and MiniMax-M3 specs, and GLM-5.3-Flash do not change. GLM-5.3-Flash has KDA layers, which need a recurrent state for each draft token. That is a different change.

## Accuracy Tests

**Setup.**

- Hardware: tests 1 to 4 and 6 used 4x MI355X (gfx950) at TP4. Tests 5 and 7 used 8x MI355X at TP8, and test 7 also ran at TP4.
- Commits: tests 1 to 5 and the speed tests used the serving code of `6b21141`, which did not change up to `a90b25e`. Tests 6 and 7 used `91f0cc7`, after the merge of `main`.
- Model: zai-org/GLM-5.3 @ `ba32f8c1` (FP8).
- Software: the image and the commits in "Speed Tests and Profiling".
- Server flags: the flags of `test/e2e/glm53_server.py`. Tests 1 to 4 used `--tp-size 4`.
- MTP: 3 draft steps, top-k 1, 4 draft tokens. This is the SGLang default for GLM-5.3.
- Each arm used a new server.

**Test 1: GSM8K.** We used `sglang.test.few_shot_gsm8k`: 5-shot, greedy, all 1319 questions. We compared the arms question by question with the McNemar test. With MTP, the client sent one question at a time, so all verify steps used the monokernels. Without MTP, the client sent 4 questions at a time, so all decode steps used the monokernels.

| Mode | Monokernels off | Monokernels on | Correct in one arm only (off / on) | McNemar p |
|---|---|---|---|---|
| MTP: accuracy | 0.9265 | 0.9234 | 32 / 28 | 0.70 |
| MTP: accept length | 3.253 | 3.288 | | |
| Decode: accuracy | 0.9272 | 0.9280 | 33 / 34 | 1.00 |

The differences are not significant. For comparison, the normal path with MTP and the normal path without MTP also differ on 53 questions (27 / 26).

**Test 2: layer check on a truncated model.** We used `SGLANG_AMD_MONO_CHECK=1` (eager). The model has the first 10 layers of GLM-5.3 with the real weights, and the real MTP layer. Layer 6 runs the indexer. Layers 3 to 5 and 7 to 9 use the top-k of the layer before them. The prompts had 600 and 6000 tokens. We applied the fix in steps, to show the effect of each part:

| Code | Verify rows with fewer than 2048 keys | Verify rows with 2048 keys or more | Violations |
|---|---|---|---|
| Defect 1 fixed | Stream cosine 0.816 (bound 0.95). In the worst row, the indexer dropped 42% of the keys that SGLang selected. One row dropped 3 keys of its draft chain. | Stream cosine 0.996 | 19 |
| Defects 1 and 2 fixed | Stream cosine 0.998. The top-k is the same as in SGLang. | Stream cosine 0.998 | 0 |
| This PR (defects 1, 2 and 3 fixed) | Stream cosine 0.999. The top-k is the same as in SGLang. | Stream cosine 0.999 | 0 |
| This PR, decode steps | Stream cosine 0.995. The top-k is the same as in SGLang. | Stream cosine 0.988 | 0 |

With 2048 keys or more, the top-k of the kernel and the top-k of SGLang differ by 2% to 4%. This also occurs in decode steps. The two use different kernels to score the keys, so keys near the threshold change places.

**Test 3: old cache contents (defect 3).** Before each launch, a patch for this test only set the cache slots of the current draft chains to zero. A kernel that reads these keys from the cache then calculates a score of 0.

- Before the kernel change, 276 of 276 earlier draft keys had a score of exactly 0.0.
- After the kernel change, 0 of 276 keys had a score of 0.0. For example, one key had a score of 1496.5 after the change and 0.0 before it.

**Test 4: layer check on the full model.** We used four 4096-token prompts and 32 new tokens for each prompt. The test made 972 checks of indexer layers with 2048 keys or more. This test did not set cache slots to zero.

- Before the kernel change, 4 checks dropped keys of the draft chain that SGLang selected (layers 26 and 62).
- After the kernel change, 0 checks dropped such keys, and there were no violations.

**Test 5: E2E tests at TP8.** We ran `test/e2e/test_glm53_server.py` as written, on 8x MI355X. All 6 tests passed:

- `TestMonokernelDecode`: the KL consistency test passed. GSM8K (sgl-eval, thinking on) was 0.99.
- `TestMonokernelMtp`: GSM8K was 0.995, and the accept length was 3.28.
- `TestMonokernelCheck`: 1425 checks of decode steps and 1425 checks of verify steps, with no violations. In the verify steps, the stream cosine was 0.996 or more.
- `TestMonokernelFault`: passed with the match change above. The first run failed on the message match only.

**Test 6: the layer check finds defect 3.** We removed only the kernel change, so the paged indexer read the earlier draft keys of a row from the cache again. Then we ran the layer check with the old cache setup and with the new one. The truncated model is the model of test 2. The E2E verify check is `test_each_covered_verify_layer_within_its_numerics` in a TP4 copy of `test/e2e/test_glm53_server.py` (`--tp-size 4`, verify steps of 4 rows).

| Kernel | Cache before each launch | Truncated model: checks with 2048 keys or more that fail | E2E verify check (TP4) |
|---|---|---|---|
| Without the kernel change | Old contents (`c1f3fa7`) | 0 of 46 | Passed (900 checks, 216 of them on indexer layers) |
| Without the kernel change | SGLang keys, scale -1e30 (`91f0cc7`) | 46 of 46, all on `layer.topk_own` | Failed: `layer.topk_own` on 16 of the 18 indexer layers |
| With the kernel change | SGLang keys, scale -1e30 (`91f0cc7`) | 0 of 46 | Passed (750 checks, 180 of them on indexer layers); the decode check also passed (1200 checks) |

Thus the E2E verify check now fails when the paged indexer reads the draft keys of the launch from the cache. Before this change, the same check passed.

In the dump of test 3, SGLang selected all 276 earlier draft keys, and 156 of them had a positive score. With fewer than 2048 keys, the indexer selects all keys, so the scale cannot drop a key there.

**Test 7: E2E tests after the merge.** We ran `test/e2e/test_glm53_server.py` at `91f0cc7`, as written, on 8x MI355X at TP8. All 6 tests passed:

- `TestMonokernelDecode`: the KL consistency test passed (average KL 0.013 to 0.036 for each batch, bound 0.06). GSM8K was 0.985.
- `TestMonokernelMtp`: GSM8K was 0.99, and the accept length was 3.36.
- `TestMonokernelCheck`: 1425 checks of decode steps and 1200 checks of verify steps, with no violations. In the verify steps, the stream cosine was 0.994 or more.
- `TestMonokernelFault`: passed.

This run also covers GLM-5.3 TP8 execution after [#12](https://github.com/sgl-project/sgl-amd-mono/pull/12), which #12 lists as not tested. A TP4 copy of the file (`--tp-size 4`, decode checks of 1 and 3 rows, verify checks of 4 rows) also passed all 6 tests: GSM8K 0.985 (decode) and 0.99 (MTP, accept length 3.16), 1200 checks of decode steps and 750 checks of verify steps.

## Speed Tests and Profiling

**Setup.**

- Hardware: one node with 8x MI355X (gfx950). TP4 used 4 of the GPUs, and TP8 used all 8.
- Image: `lmsysorg/sglang-rocm:v0.5.22-rocm720-mi35x-20261018` (`sha256:8f7d8034546b`).
- Software: SGLang `e9b22a0818`, AITER `2bb549102b`, FlyDSL 0.3.4.1, torch 2.9.1+rocm7.2.0.
- Model: zai-org/GLM-5.3 @ `ba32f8c1`.
- Server flags: the flags of `test/e2e/glm53_server.py`. TP4 used `--tp-size 4 --max-running-requests 2 --cuda-graph-max-bs-decode 2`. TP8 used `--tp-size 8 --max-running-requests 4 --cuda-graph-max-bs-decode 4`.
- Prompts: four 4096-token passages from novels. Greedy decoding, 1024 new tokens, `ignore_eos`. The client flushed the radix cache before each request.
- Metric: the decode rate of one request, from the first streamed chunk to the last chunk. This metric does not include prefill.
- Order: a new server for each arm, in the order B, A, A, B. The 95% confidence intervals come from a hierarchical bootstrap (servers, then requests).

**TP8.** Batches 1 and 2 have 4 and 8 verify rows, and use the monokernels. Batch 4 has 16 verify rows, and uses the normal path.

| Arm | Batch 1: decode tok/s | Batch 1: time for each verify step | Batch 2: decode tok/s | Batch 2: time for each verify step | Batch 4: decode tok/s |
|---|---|---|---|---|---|
| A: normal path, MTP | 198.1 | 13.56 ms | 156.6 | 16.26 ms | 136.7 |
| B: monokernels, MTP | 334.4 | 8.35 ms | 208.6 | 12.31 ms | 144.2 |
| B / A - 1 | +68.8% [+54.7, +83.9] | -38.5% [-38.7, -38.2] | +33.2% [+18.7, +49.9] | -24.3% [-26.9, -21.9] | +5.5% [-7.2, +20.3] |

The accept length at batch 1 was 2.69 (A) and 2.80 (B), a difference of +3.9% [-5.1, +13.3].

**TP4.** Batch 1 has 4 verify rows, and uses the monokernels. Batch 2 has 8 verify rows, which is more than the TP4 limit of 4 rows, so it uses the normal path.

| Arm | Batch 1: decode tok/s | Batch 1: time for each verify step | Batch 1: accept length | Batch 2: decode tok/s |
|---|---|---|---|---|

**After the merge of `main`.** We ran one server for each arm at `91f0cc7`, at TP4, with the same flags, prompts and client. At batch 1, the monokernels took 10.98 ms for each verify step (11.03 ms before the merge), and the normal path took 14.85 ms (14.86 ms before). The decode rates were 257.8 tok/s and 188.3 tok/s. Thus the merge of #12 does not make the verify steps slower. This check used one server for each arm, so it has no confidence interval across servers.

**Results.**

- At TP8, the monokernels with MTP decode 68.8% faster for one request and 33.2% faster for two requests.
- At TP4, the monokernels with MTP decode 29.9% faster for one request.
- Each verify step that uses the monokernels takes 24% to 38% less time. This value does not depend on the accept length.
- The accept length does not change significantly.
- Steps with more verify rows than the limit use the normal path. Their time for each verify step does not change. At TP8 batch 4, it is 18.60 ms (A) and 18.26 ms (B). At TP4 batch 2, it is 17.27 ms (A) and 17.23 ms (B).
- The two TP4 arms without MTP ran on one server each.
