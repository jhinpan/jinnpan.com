# #42 [Perf] [MI355X] glm53: Score the paged indexer keys per wave
merged 2026-10-25T04:08:03Z 9484c6016 +258/-74 files 2

## Motivation

**Summary.** After #24, the score stage of the GLM-5.3 indexer read the keys at about 0.7 TB/s, and at 5 to 8 rows past 128k keys it took about half of an indexer launch. This PR scores each group of 16 keys on one wave over all 32 heads, with the reads of the next groups in flight. The scores do not change: in one launch, they are bitwise equal to the scores of #24 on the same inputs. On 8x MI355X at TP8, in InferenceX agentic coding with MTP, interactivity p50 is 1.43x, 1.46x and 1.23x that of the normal path with MTP at concurrency 1, 2 and 4 (#24: 1.15x, 1.17x and 1.11x).

**On main after #24.** This PR is two commits on main (`240d587`, which has #24 and #56): `e405d6b` is `e0d7655` rebased with the same changed lines (and `e0d7655` is `9733ff4` rebased), and `3419a0e` is the fix from the review. The results below were measured at `9733ff4` unless marked.

**Cause.** In the paged score stage of #24:

- A CTA scored a tile of 64 keys with its 8 waves: 4 groups of 16 keys, each for the two halves of the 32 heads. The two waves of a group read the same keys, so each key was read two times.
- The two halves were added through LDS, with two block barriers a tile.
- The block-table read and the key reads of a tile started only after the tile before it ended. Thus each tile waited for two memory round trips: about 2.1 us a tile, 0.7 TB/s at 256k keys.
- Each key also compared its cache slot with the slots of all S rows of the launch (the new-key lookup of #15). This cost grows with the width (S = 2, 4 or 8).

## Modifications

- `glm53/gfx950/kernel.py`, paged score stage only:
  - A wave scores a group of 16 keys over all 32 heads: two MFMA chains on one read of the keys. The head sums stay in the lanes, so the stage has no LDS reduction and no barrier between groups.
  - A wave walks every 8th group of its CTA's tiles; the tiles of a CTA do not change. The key reads of the next 2 groups are in flight, and their block-table reads go one step further ahead. The first block-table reads of a row overlap the staging of its query.
  - The query fragments and the head weights of the row stay in registers. The values of a row (bound, request, counts) are wave-uniform.
  - The new-key lookup of #15 runs only for each wave's group that holds any of the last S keys of a row: a launch writes only those keys (a verify row's draft chain, a decode row's own key). A wave's groups are `SCORE_STRIDE` (32768) keys apart, so a wave has at most one such group; the walk asserts `S + 15 < SCORE_STRIDE` (review fix).
  - Each score is computed in the same order as before: the same MFMA chain, the same sums in the same order.
- `test/e2e/test_glm53_server.py` (review fix): the parallel check case of #24 passes 98304 keys (rows of about 108k keys at widths 2 and 4), where each wave's walk refills its buffers and looks blocks ahead. Before, the longest case (about 36k keys) gave each wave at most 2 groups, so the refills never ran.
- No new check. With a wrong refill offset (a deliberate error, not in this PR: a refilled buffer reads the keys 16 positions on), the parallel check case fails on the existing stream-cosine bound: 22 violations, lowest cosine 0.914 (bound 0.95). `layer.topk.rel` rises to 0.66 (0.052 without the error). So once a case reaches the walk's refills, the existing bounds catch an error there. The bitwise check needs a debug build (not in this PR).

## Accuracy Tests

**Setup.** 8x MI355X (gfx950) at TP8; zai-org/GLM-5.3 @ `ba32f8c1` (FP8); the image and the commits of #24; the server flags of `test/e2e/glm53_server.py`; a new server for each test.

**Test 1: bitwise scores in one launch.** A debug build (not in this PR) also runs the per-tile score code of #24 in the same launch, on the same inputs, and writes those scores to a second scratch buffer. A script compares the two buffers.

| Steps | Rows | Keys | Keys bitwise equal |
|---|---|---|---|
| Decode: 1 to 8 rows, 8k to 256k keys | 256 | 29,961,984 | 29,961,984 |
| MTP verify: 1 and 2 requests, 8k to 256k keys | 192 | 29,631,744 | 29,631,744 |

The exact top-k check of #24 also found 0 wrong rows in both runs.

We did not compare two servers: on this image, two prefills of the same prompt give different bits. After a prefill of 131072 tokens, the scores of the first decode step correlate at 0.9988 between two passes (one prefill, cached) and at 0.9457 between two prefills in the same server, with the same build. Between a server with #24 and a server with this PR, they correlate at 0.9460.

**Test 2: E2E tests at TP8 (review fix).** We ran `test/e2e/test_glm53_server.py` as written at `3419a0e` on main `240d587`. All 7 tests passed in one run (1214 s):

- `TestMonokernelDecode`: average KL 0.018 to 0.022 for each batch (bound 0.06); GSM8K (sgl-eval, thinking on) 0.99.
- `TestMonokernelMtp`: GSM8K 0.99, accept length 3.28.
- `TestMonokernelCheck`: no violations. `layer.topk_exact` (#24) and `layer.topk_own` are 0 in all 954 indexer checks.
  - Decode steps: 1425 checks, stream cosine 0.9942 or more, `layer.topk.rel` 0.014 or less.
  - Verify steps: 1350 checks, stream cosine 0.9976 or more, `layer.topk.rel` 0.017 or less.
  - Past the parallel top-k, with rows past 98304 keys: 1200 checks, stream cosine 0.9968 or more, `layer.topk.rel` 0.052 or less.
- `TestMonokernelFault`: passed. Since #55, the test sets `HSA_DISABLE_COREDUMP_ON_EXCEPTION=1` and turns off SGLang's crash dumps itself.

Two earlier runs also passed all 7 tests: at `9733ff4`, before the review fix, and at `9b48912`, the fix on #24's branch before #56 merged.
