# #60 [Feat] [MI355X] glm53: Read and write SGLang's E4M3 MLA cache
merged 2026-10-26T05:20:14Z 0a107f153 +68/-22 files 4

## Motivation

The glm53 monokernel accepted only a bf16 MLA cache (`--kv-cache-dtype auto` or `bfloat16`). That is what the SGLang cookbook's MI355X cells for GLM-5.3 run (they keep the default), but InferenceX's GLM recipes on MI355X run `--kv-cache-dtype fp8_e4m3` (for example its GLM-5.2 MI355X SGLang agentic recipe). With such a recipe, turning the monokernels on also moved SGLang's own prefill to a bf16 cache, and that prefill is slower: on one AgentX-like prefill (2048 new tokens on 100k cached tokens, TP8), TTFT is 220 ms on the fp8 cache and 269 ms on bf16. The extra 50 ms is one TileLang kernel of the DSA prefill backend (grid 2080), 644 us a layer on fp8 and 1276 us on bf16; every other kernel moves by less than 2 ms in total. In InferenceX agentic coding with MTP, that TTFT cost (+10% to +22%) cancelled the decode gain on P90 E2E-normalized interactivity.

On HIP, SGLang's DSA backends keep the fp8 MLA cache as raw rows: 576 E4M3 values (512 latent, then 64 rope), without block scales (`calculate_mla_kv_cache_dim`; the write is `set_mla_kv_buffer_triton_fp8_quant`, a bf16 to E4M3 store). The kernel's E4M3 path (`kv_cache_dtype="fp8"`) already reads and writes this row.

## Modifications

- `glm53/spec.py`: `kv_cache_dtype` accepts `fp8_e4m3`. The build reads SGLang's `kv_cache_dtype` (`get_model()`) and builds E4M3 launches for it. A layer binds its cache only if its dtype is the launch's and its rows hold 576 values, so the scaled E4M3 row (656 bytes) of the other DSA backends and a dtype mismatch are refused, not read as wrong keys.
- `glm53/gfx950/runner.py`: `Glm53Build.kv_fp8` selects `kv_cache_dtype="fp8"`; the runtime keeps the cache dtype, and each launch checks its cache against it.
- The kernel does not change. Its E4M3 path rounds each value to bf16 and then to E4M3, as SGLang's write does, stores four values a dword in element order, and widens them exactly when it reads them; the rows a launch writes are attended with the rounded values.
- Tests: `test/unit/test_glm53_spec.py` checks that an E4M3 launch binds only the raw E4M3 row; `test/e2e/test_glm53_server.py` adds the layer check in MTP verify steps on the E4M3 cache.

## Accuracy Tests

**Setup.** 8x MI355X (gfx950), TP8, zai-org/GLM-5.3 (FP8), image `lmsysorg/sglang-rocm:v0.5.22-rocm720-mi35x-20261024` (SGLang `fe1bd10837`, AITER `285579b6`) with this branch mounted, a new server for each test. The layer checks below ran at the final head `78f0265`. GSM8K, the speed tests and the profile ran at `4d98bda`; `78f0265` only keeps the cache dtype on the runtime instead of deriving it at each launch, and the layer checks gave the same verdicts at both heads.

- Layer check (`SGLANG_AMD_MONO_CHECK`) on the E4M3 cache:
  - the new test, verify steps of 4 and 8 rows past 2048 keys: 1200 checks, no violation; `layer.kv.cosine` 0.99926 or more, `layer.streams.cosine` 0.99140 or more; `layer.topk_exact` and `layer.topk_own` 0.
  - decode steps at widths 2, 4 and 8 (the decode case with `--kv-cache-dtype fp8_e4m3`, run locally): 1425 checks, no violation; `layer.kv.cosine` 0.99908 or more, `layer.streams.cosine` 0.98245 or more.
  - The cache rows are not bitwise SGLang's: `layer.kv.max_abs` is at most one E4M3 step, from bf16 values that differ in the last bit before the rounding (the kernel's RMSNorm runs in f32).
- The bf16 verify check still passes: 1350 checks, no violation.
- With the latent's E4M3 byte pairs swapped (a deliberate error, not in this PR), the new test fails: 1189 violations, `layer.kv.cosine` down to 0.095 over 1275 checks.
- GSM8K (InferenceX lm-eval, the first 500 questions, 5-shot, real MTP acceptance, concurrency 2), both on the fp8_e4m3 cache: monokernels off 0.986, on 0.988 (strict-match; flexible-extract 0.984 and 0.988), McNemar p 1.00 (0.62). MTP accept length (median of the server's decode logs) 3.39 off, 3.40 on.
