Experiment 008 · RFC

Kernel / Compiler

FlyDSL is a Python language for writing AMD GPU kernels. LLVM changes each kernel into machine instructions. This RFC proposes to keep LLVM, and to change the kernel code and the compiler together, so that a fixed compiler does not limit the final code. The evidence is 29 experiments on MI355X GPUs. This is a draft for comments.

FlyDSL 是一种用 Python 写 AMD GPU kernel 的语言。 LLVM 把每个 kernel 变成机器指令。 这份 RFC 提议保留 LLVM， 并让 kernel 代码和编译器一起改， 这样固定的编译器就不会限制最终代码。 证据是 MI355X GPU 上的 29 组实验。 这是一份征求意见的草稿。

02The loop: generate, change, teach循环： 生成、 修改、 教会编译器

In this RFC, the compiler is one method to generate code. It is not the limit of the code. The loop has three steps. It starts with the compiler at version n.

在这份 RFC 里， 编译器是生成代码的一种方法， 不是代码的上限。 循环有三步， 从第 n 版编译器开始。

  1. Generate. The compiler builds the kernel from its source. The result is the final code: code(n) = f(llvm(n)). Here f is the kernel source, and llvm(n) is the compiler at version n.
  2. Change the code. An agent or a person changes the final code directly, and then measures it: code(n+1) = agent(code(n)). The compiler does not limit this step.
  3. Teach the compiler. If the new code is correct and faster, make the compiler produce the same code from the kernel source: llvm(n+1) = f⁻¹(code(n+1)). Section 05 lists the places where this change can live.
  1. 生成。 编译器从 kernel 源码生成代码。 结果就是最终代码： code(n) = f(llvm(n))。 其中 f 是 kernel 源码， llvm(n) 是第 n 版编译器。
  2. 改代码。 agent 或人直接修改最终代码， 然后测量： code(n+1) = agent(code(n))。 这一步不受编译器限制。
  3. 教会编译器。 如果新代码正确而且更快， 就让编译器从 kernel 源码生成同样的代码： llvm(n+1) = f⁻¹(code(n+1))。 第 05 节列出这个改动可以放在哪里。

Then go back to step 1, with the next kernel or with the next change to the compiler.

然后回到第 1 步， 换下一个 kernel， 或者换下一个编译器改动。

04Evidence: a fixed compiler limits the final code today证据： 固定的编译器今天就在限制最终代码

The speed of an AMD GPU kernel depends on five kinds of decisions (Plate II). In FlyDSL, the author makes three of them in Python: the work split, the data movement and the instruction choice. The heuristics of LLVM make the other two: the register use and the instruction order.

AMD GPU kernel 的速度取决于五类决策（Plate II）。 在 FlyDSL 里， 作者在 Python 里做出其中三类： 工作划分、 数据搬运和指令选择。 另外两类由 LLVM 的启发式规则来做： 寄存器使用和指令顺序。

The red path is common. In the FlyDSL kernels at fe81c407, 34 of 180 kernel files use fences (257 times in total). 44 files place waits by hand (186 times). 13 files use inline assembly, and 12 files set the wave priority.

红色路径很常见。 在 fe81c407 的 FlyDSL kernel 里， 180 个 kernel 文件中有 34 个使用 fence（共 257 次）。 44 个文件手工放置 wait（共 186 次）。 13 个文件使用 inline 汇编， 12 个文件设置 wave 优先级。

The kernel comments give the reasons. One kernel uses inline assembly so that LLVM does not see a memory operation and does not add a wait (fp4_gemm_4wave.py). Another kernel adds a fence and gives this reason: "the scheduler may hoist them above s_barrier: a race" (mega_moe_tp/gemm.py). That is, LLVM can move the reads before the barrier, and the kernel then reads data that is not ready.

kernel 里的注释写明了原因。 一个 kernel 用 inline 汇编， 是为了让 LLVM 看不到一次访存， 从而不插入 wait（fp4_gemm_4wave.py）。 另一个 kernel 加了 fence， 注释写的是： "调度器可能把它们提到 s_barrier 之前： 这是竞争"（mega_moe_tp/gemm.py）。 意思是： LLVM 可能把读取移到 barrier 之前， kernel 就会读到还没准备好的数据。

The red path is steps 2 and 3 of the loop, done by hand. The author wants a specific final code, and forces the compiler to produce it.

红色路径就是手工完成的第 2 步和第 3 步。 作者想要某一份特定的最终代码， 就强制编译器生成它。

How much speed does this path give? We removed one decision of the author at a time, and let LLVM decide (appendix A). Six kernels became 5–16% slower. In two kernels, the results became wrong: the fences that we removed also kept the results correct.

这条路径值多少速度？ 我们每次去掉作者的一个决策， 让 LLVM 来决定（附录 A）。 6 个 kernel 慢了 5–16%。 有两个 kernel 的结果变错了： 被去掉的 fence 同时在保证结果正确。

Thus the default output of LLVM is not the final code that these kernels need. Today, each author closes this difference by hand, in one kernel at a time.

所以 LLVM 的默认输出不是这些 kernel 需要的最终代码。 今天， 每个作者手工去补这个差距， 一次只补一个 kernel。

05Open question: step 3 must not slow other kernels未解决的问题： 第 3 步不能让其他 kernel 变慢

A change in a kernel source affects one kernel. A change in LLVM affects each kernel that LLVM compiles. Thus step 3 has a risk that step 2 does not have. Three results show that this risk is real.

改一个 kernel 的源码， 只影响这一个 kernel。 改 LLVM， 会影响 LLVM 编译的每个 kernel。 所以第 3 步有第 2 步没有的风险。 三个结果说明这个风险是真实的。

  • One patch, two kernels. To keep one accumulator in AGPRs, FlyDSL patched the register allocator and the instruction selector of LLVM (#1368). Then the patch was reverted, because it caused spills in a kernel of another team (#1477).
  • One kernel, many shapes. Without the fences and interleave groups of its author, the preshuffle GEMM is 12% slower in total. But it is 3.4% faster at 16384³ and 2.1% faster at 8192³ (Plate IV).
  • Faster on average, slower on single shapes. With the schedulers of LLVM turned off, the same kernel ran at 1.025× in total. With max-ilp, it ran at 1.018×. But 3 and 5 shapes became slower by more than the noise level, to 0.92× and 0.93× in the worst case (appendix B).
  • 一个补丁， 两个 kernel。 为了把一个累加器固定在 AGPR 里， FlyDSL 修改了 LLVM 的寄存器分配和指令选择（#1368）。 后来这个补丁被回滚， 因为它让另一个团队的 kernel 出现了 spill（#1477）。
  • 一个 kernel， 很多 shape。 去掉作者的 fence 和交错组之后， preshuffle GEMM 整体慢了 12%。 但它在 16384³ 上快了 3.4%， 在 8192³ 上快了 2.1%（Plate IV）。
  • 平均更快， 单个 shape 更慢。 关掉 LLVM 的调度器后， 同一个 kernel 的整体速度比是 1.025×。 用 max-ilp 时是 1.018×。 但分别有 3 个和 5 个 shape 的变慢超出噪声下限， 最差到 0.92× 和 0.93×（附录 B）。

A change from step 3 can live in three places. The list goes from local to global:

第 3 步的改动可以放在三个地方。 下面从局部排到全局：

  1. In the kernel source, as an explicit decision: a fence, an interleave group, a pin. It affects one kernel. Authors use this place today (section 04).
  2. In a compiler option of one kernel. A FlyDSL kernel can set LLVM options for itself. For example, the dense flash attention turns off the post-RA scheduler (flash_attn_gfx950.py). It affects one kernel, and all kernels still use one LLVM.
  3. In LLVM itself: a heuristic, a pass or a patch. It affects all kernels.
  1. 放在 kernel 源码里， 作为一个显式决策： fence、 交错组或 pin。 它只影响一个 kernel。 作者今天用的就是这里（第 04 节）。
  2. 放在某个 kernel 的编译选项里。 FlyDSL kernel 可以给自己设置 LLVM 选项。 例如， dense flash attention 关掉了 post-RA 调度器（flash_attn_gfx950.py）。 它只影响一个 kernel， 所有 kernel 仍然共用一个 LLVM。
  3. 放在 LLVM 本身： 一条启发式规则、 一个 pass 或一个补丁。 它影响所有 kernel。

Places 1 and 2 are safe for other kernels. But the compiler learns nothing: the next kernel must find the same decision again. Place 3 helps each kernel, but it needs a gate.

放在 1 和 2， 对其他 kernel 是安全的。 但编译器什么都没学到： 下一个 kernel 还得重新找到同样的决策。 放在 3， 对每个 kernel 都有帮助， 但需要一道关卡。

A candidate gate, not decided. Accept a change to LLVM only if all kernels and shapes pass the check that FlyBench already uses for a change to one kernel: each result is correct, and no shape is slower by more than its noise level. A change that does not pass stays in place 1 or 2.

一个候选的关卡， 还没有定。 只有当所有 kernel 和 shape 都通过 FlyBench 现在用于单个 kernel 改动的检查时， 才接受对 LLVM 的改动： 每个结果都正确， 没有 shape 的变慢超出它的噪声下限。 通不过的改动留在 1 或 2。

We have not measured how often a change passes this gate, or how many kernels and shapes the check needs. Section 07 lists this experiment.

我们还没有测过一个改动通过这道关卡的概率， 也没有测过这个检查需要多少 kernel 和 shape。 第 07 节列出了这个实验。

06What this RFC does not propose这份 RFC 不提议什么

  • To remove LLVM. Where no author decides the instruction order, the default of LLVM is good. On the normalization kernels and the MoE reduce kernel, no other scheduling strategy was faster by more than the noise level. Without the schedulers of LLVM, RMSNorm became 10% slower (appendix B). LLVM also fills the gaps that hardware hazards need, and FlyDSL follows upstream LLVM (#945).
  • To remove MLIR, or to build a new IR and backend. We did not build them, and we did not measure them. No result on this page needs them.
  • To move the layouts to Python. Some layouts mix parts that are known at compile time with parts that are known only at run time. This change can make these layouts harder to write. We did not test it.
  • To make the compile faster. The work before each launch costs time (appendix D). But the test harness can solve this problem, and it is not part of this RFC.
  • 去掉 LLVM。 在作者没有决定指令顺序的地方， LLVM 的默认值是好的。 在 normalization 和 MoE reduce kernel 上， 没有其他调度策略的提速超出噪声下限。 关掉 LLVM 的调度器后， RMSNorm 慢了 10%（附录 B）。 LLVM 还负责留出硬件 hazard 需要的间隔， 而且 FlyDSL 一直跟随上游 LLVM（#945）。
  • 去掉 MLIR， 或者实现新的 IR 和后端。 我们没有实现它们， 也没有测量它们。 本页没有哪个结果需要它们。
  • 把 layout 移到 Python 里。 有些 layout 混着编译期已知的部分和运行时才知道的部分。 这个改动可能让这类 layout 更难写。 我们没有测试过。
  • 让编译更快。 每次启动前的工作确实要花时间（附录 D）。 但这个问题可以在测试 harness 里解决， 不属于这份 RFC。

07Next steps下一步

  1. Run the toy example of section 03 on one MI355X: all three steps, with the measured speed of each step.
  2. Measure the gate of section 05. Take one change to LLVM that makes one kernel faster. Run all kernels and shapes with it, and count the ones that become wrong or slower. The patch of #1368 is a candidate.
  3. Build the harness. Agents write a batch of kernels in one clean test flow. Then we read the development logs to see what the compiler lacks.
  1. 跑第 03 节的小例子。 在一张 MI355X 上走完三步， 并测出每一步的速度。
  2. 测第 05 节的关卡。 选一个让某个 kernel 变快的 LLVM 改动。 带着它跑所有 kernel 和 shape， 数出结果变错或变慢的有多少。 #1368 的补丁是一个候选。
  3. 搭 harness。 agent 在一个干净的测试流程里写一批 kernel。 然后我们读开发日志， 看编译器还缺什么。

08What could prove this wrong什么会推翻它

  • Step 2 gives little. In earlier FlyBench runs, the accepted speedups of agents came from four kinds of change to the kernel source: wider memory access, a tile choice per shape, more work splits, and new algorithms (median 1.46×). Order settings and register settings appear in only 8% and 5% of the reviews (appendix C). If direct changes to the final code give less than the noise level, on the toy kernel and on a batch of kernels, the loop is not worth its cost.
  • Step 3 does not generalize. If most changes fail the gate, each change stays in one kernel. Then the compiler does not improve, and the loop is only hand tuning with more steps.
  • Step 2 breaks the results, and no test shows it. In two of five kernels, fences that look like speed hints keep the results correct (appendix A). One MoE GEMM returned a wrong output in some runs, without any change (appendix B). If the tests miss such errors in changed code, step 2 needs a stronger check than the evaluator of today.
  • 第 2 步的收益很小。 在之前的 FlyBench 运行里， agent 被认可的提速来自对 kernel 源码的四类改动： 更宽的访存、 按 shape 选择 tile、 更多的工作切分， 以及新算法（中位数 1.46×）。 顺序设置和寄存器设置分别只出现在 8% 和 5% 的 review 里（附录 C）。 如果直接修改最终代码的收益在小例子和一批 kernel 上都低于噪声下限， 这个循环就不值它的成本。
  • 第 3 步推广不开。 如果大多数改动过不了关卡， 每个改动就只能留在一个 kernel 里。 这样编译器没有进步， 循环只是步骤更多的手工调优。
  • 第 2 步把结果改错了， 而测试看不出来。 在五个 kernel 里， 有两个的 fence 看起来是速度提示， 实际在保证结果正确（附录 A）。 一个 MoE GEMM 在没有任何改动的情况下， 有几次运行返回了错误的输出（附录 B）。 如果测试漏掉改动后代码里的这类错误， 第 2 步就需要比现在的评测器更强的检查。

Result 1: the decisions of the author give 5–16%, and LLVM does not find this speed

结果 1： 作者的决策值 5–16%， LLVM 找不到这部分速度

Without the fences and interleave groups, the preshuffle GEMM became 12% slower (0.882×). The MX preshuffle GEMM became 5% slower, and the sliding-window attention became 16% slower. In the preshuffle GEMM, the interleave groups cause all of the loss. Without only the groups, the speed ratio is 0.883×, the same as without all hints.

去掉 fence 和交错组之后， preshuffle GEMM 慢了 12%（0.882×）。 MX preshuffle GEMM 慢了 5%， 滑窗 attention 慢了 16%。 在 preshuffle GEMM 里， 全部损失都来自交错组： 只去掉交错组时速度比是 0.883×， 和去掉全部提示一样。

Without s_setprio, the two 8-wave GEMMs became 14% and 10% slower. For the first one, the ISA shows more than a priority change: the kernel got VGPR spills, and it had no spills before.

去掉 s_setprio 之后， 两个 8-wave GEMM 分别慢了 14% 和 10%。 对第一个 kernel， ISA 显示的不只是优先级变化： 原来没有 spill， 现在出现了 VGPR spill。

This kernel, the FP8 8-wave GEMM, has four s_setprio instructions. Their documented job is only to set the wave priority. When we removed them, the register use changed, and the kernel got 6 spills. The cause is one line in LLVM: LLVM treats s_setprio as a hard limit for instruction order (SIInstrInfo.cpp). Thus one hint has two effects, and the kernel source does not show the second effect.

这个 kernel（FP8 8-wave GEMM）里有 4 条 s_setprio 指令。 按文档， 它们只负责设置 wave 优先级。 我们去掉它们之后， 寄存器使用发生了变化， kernel 多出 6 个 spill。 原因是 LLVM 里的一行代码： LLVM 把 s_setprio 当作指令顺序的硬边界（SIInstrInfo.cpp）。 所以一个提示有两种效果， 而 kernel 源码里看不到第二种。

In the FP8 4-wave GEMM, we let LLVM assign the registers of the accumulators, instead of the AGPR pins of the author. The kernel became 14% slower at 16384³ and 9% slower at 8192³. The spills went from 10 to 92, and the moves between AGPRs and VGPRs went from 796 to 6,437. The ISA also shows a fact that nobody had reported: even the pinned kernel has 10 spills at that size.

在 FP8 4-wave GEMM 里， 我们让 LLVM 来分配累加器的寄存器， 不再使用作者的 AGPR pin。 kernel 在 16384³ 上慢了 14%， 在 8192³ 上慢了 9%。 spill 从 10 个增加到 92 个， AGPR 和 VGPR 之间的搬运指令从 796 条增加到 6,437 条。 ISA 还显示了一个之前没人报告过的事实： 即使用了 pin， 这个尺寸上也有 10 个 spill。

Without the occupancy hints of the same kernel, nothing changed. The ISA was the same at both shapes, so the default of LLVM already matched the hints. A hint with no effect does no harm. But no tool tells the author or the agent that the hint has no effect.

去掉同一个 kernel 的 occupancy 提示后， 什么都没变。 两个 shape 上的 ISA 完全相同， 说明 LLVM 的默认值本来就和这些提示一致。 没有效果的提示不会造成损害， 但没有任何工具告诉作者或 agent 它没有效果。

Result 2: in two kernels, the "scheduling" fences kept the results correct

结果 2： 两个 kernel 的"调度" fence 在保证结果正确

Without the fences, the A16W16 GEMM failed 1 of 880 FlyDSL tests. The dense flash attention failed 28 of 1039 tests: some log-sum-exp values (a value for each row that attention saves for later steps) were off by up to 0.43, and some outputs were NaN (not a number).

去掉 fence 之后， A16W16 GEMM 在 FlyDSL 的 880 个测试里失败了 1 个。 dense flash attention 的 1039 个测试里失败了 28 个。 部分 log-sum-exp 值（attention 为后续步骤保存的每行数值）最多差 0.43， 部分输出是 NaN（无效数值）。

We repeated the A16W16 arm in a new job. The same test failed, but with different wrong elements: 182 and 31 of 163,840. A rounding error gives the same wrong elements in each run. A race gives different ones. With the added lines but nothing removed, the same kernel passed all of its tests (null control, 0.998×).

我们在新作业里重复了 A16W16 这个 arm。 失败的是同一个测试， 但错的元素不同： 163,840 个元素里分别错了 182 个和 31 个。 舍入误差每次错的是同样的元素， 竞争每次错的元素不同。 加了那几行代码、 但什么都不去掉时， 同一个 kernel 通过了全部测试（空白对照， 0.998×）。

A scheduling hint should change only the speed. Here it changed the results. We did not find which instruction moved.

But the kernels show the probable cause. They control the order of memory copies and shared-memory reuse with waits and barriers that the author placed by hand. LLVM does not connect these waits and barriers to the reads that they protect. A FlyDSL comment in another kernel describes this risk: "the scheduler may hoist them above s_barrier: a race" (mega_moe_tp/gemm.py).

调度提示本应只改变速度， 这里却改变了结果。 我们没有找出具体是哪条指令被移动了。

但 kernel 本身指出了可能的原因： 它们用作者手工放置的 wait 和 barrier 来控制内存拷贝和共享内存复用的顺序。 LLVM 不会把这些 wait 和 barrier 与它们保护的读取联系起来。 FlyDSL 另一个 kernel 的注释写的正是这种风险： "调度器可能把它们提到 s_barrier 之前： 这是竞争"（mega_moe_tp/gemm.py）。

In the flash attention, we also removed only the interleave groups and kept the fences. The kernel stayed correct, at 0.990× [0.989, 0.991]. Thus the fences, not the groups, keep the results correct.

在 flash attention 里， 我们还试了只去掉交错组、 保留 fence。 kernel 的结果仍然正确， 速度比是 0.990× [0.989, 0.991]。 所以保证结果正确的是 fence， 不是交错组。

This result is not about speed. Today, an autotuner or an agent cannot safely change a scheduling hint, because some of these hints are correctness rules that look like speed hints.

这个结果和速度无关。 今天， autotuner 或 agent 不能放心地修改调度提示， 因为其中一些提示看起来是为了速度， 实际上是保证正确性的规则。

Result 3: on single shapes, the free order of LLVM is sometimes better

结果 3： 在单个 shape 上， LLVM 的自由排序有时更好

The same preshuffle arm is 12% slower in total. But it is 3.4% faster at 16384³ and 2.1% faster at 8192³. Thus the interleave pattern of the author is a good fixed rule, but it is not the best rule for each shape. Plate IV (section 05) shows this for all public shapes.

同一个 preshuffle arm 整体慢了 12%， 但在 16384³ 上快了 3.4%， 在 8192³ 上快了 2.1%。 所以作者的交错模板是一个不错的固定规则， 但不是每个 shape 上最好的规则。 Plate IV（第 05 节）显示了所有公开 shape 的情况。

Result 4: two small effects on the flash attention

结果 4： flash attention 上的两个小效果

Without s_setprio, the flash attention ran at 0.998× [0.997, 0.999] in total. But it was up to 4.3% slower on single shapes, and 5 shapes were slower by more than their noise level.

去掉 s_setprio 后， flash attention 整体速度比是 0.998× [0.997, 0.999]。 但在单个 shape 上最多慢 4.3%， 有 5 个 shape 的变慢超出了噪声下限。

The author of this kernel turned off the post-RA scheduler of LLVM to protect the order that the author wrote (flash_attn_gfx950.py). The post-RA scheduler is a second LLVM step that changes the instruction order after register assignment. When we turned it on again, the kernel ran at 1.006× [1.004, 1.008]. No shape was slower by more than its noise level, and the best shape was 6.7% faster. The ISA has 22 fewer s_nop instructions (185 → 163). An s_nop is an empty instruction that fills a hazard gap.

这个 kernel 的作者关掉了 LLVM 的 post-RA 调度器， 用来保护作者写下的顺序（flash_attn_gfx950.py）。 post-RA 调度器是 LLVM 在分配寄存器之后再调整一次指令顺序的步骤。 我们重新打开它之后， kernel 的速度比是 1.006× [1.004, 1.008]。 没有 shape 的变慢超出噪声下限， 最好的 shape 快了 6.7%。 ISA 里少了 22 条 s_nop（185 → 163）。 s_nop 是填充 hazard 间隔的空指令。

This gain is about the size of the 0.5% noise level of this kernel. Thus FlyBench would not count it as an improvement. The author could not see if this setting helps. The notes of FlyDSL say that three related flash attention kernels use different values for this setting, with no comment (arch-gfx950.md).

这个收益和这个 kernel 0.5% 的噪声下限差不多大， 所以 FlyBench 不会把它算作提升。 作者看不到这个设置到底有没有帮助。 FlyDSL 自己的笔记写着： 三个相关的 flash attention kernel 在这个设置上取值不同。 这些 kernel 里也没有注释说明原因（arch-gfx950.md）。

What we saw.

看到了什么。

  1. For kernels without a hand-written order, the default of LLVM is good. No strategy was faster by more than the noise level on the normalization kernels and the MoE reduce kernel. Without the schedulers, RMSNorm became 10% slower.
  2. For the hand-ordered preshuffle GEMM, the result is different. Without the schedulers of LLVM, it ran at 1.025× [1.021, 1.029], faster than stock. With max-ilp, it ran at 1.018×. But neither result is a clean gain: 3 and 5 shapes became slower by more than the noise level (worst 0.92× and 0.93×). Thus FlyBench would reject both arms. Even with the hints of the author, the heuristic scheduler of LLVM costs this kernel time.
  3. The MoE GEMM sometimes returns wrong results, even without a change. With max-ilp, one timed call failed the correctness check (cosine similarity 0.989; the limit is 0.99). We repeated the arm.   1. 对没有手工排序的 kernel， LLVM 的默认值是好的。 在 normalization 和 MoE reduce kernel 上， 没有哪种策略的提速超出噪声下限。 关掉调度器后， RMSNorm 慢了 10%。

  3. MoE GEMM 即使不做任何改动， 有时也会返回错误结果。 用 max-ilp 时， 有一次计时调用没有通过正确性检查（余弦相似度 0.989， 门限是 0.99）。 我们重复了这个 arm。 在重复实验里， stock kernel 自己返回了错误的输出（余弦相似度 0.977）。 所以不能怪这个设置。 原因可能是竞争， 但我们没有找到。 这个例子说明了另一个问题： 评测器只能在部分运行里抓到这个 bug。

Appendix C附录 CExperiment C · what agents did in 671 attempts实验 C · agent 在 671 次尝试里做了什么

What we did. The overlay has already run FlyBench many times. In each run, an agent gets one FlyDSL kernel and a time limit. It must make the kernel faster and keep the same results.

We read all the records that still exist. These are 98 runs with 671 attempts, 676 evaluator receipts, 89 independent reviews of the best patches and 827 command logs with 285,091 commands. We publish only totals.

做了什么。 overlay 已经跑过很多次 FlyBench。 每次运行中， agent 拿到一个 FlyDSL kernel 和一个时间限制， 要在结果不变的前提下让 kernel 变快。

我们读了所有留存下来的记录。 其中有 98 次运行（共 671 次尝试）、 676 张评测回执、 89 份对最好补丁的独立 review， 以及 827 份命令记录（共 285,091 条命令）。 我们只公开汇总数据。

Where the speedups come from. The accepted speedups have a median of 1.46×, as reproduced by the reviewer. They come from four kinds of change: wider memory access, a tile choice per shape, more work splits, and new algorithms. These changes are work split, data movement and instruction choice, the decisions that the author already makes. Order settings and register settings appear in only 8% and 5% of the reviews.

提速来自哪里。 被认可的提速经 review 复现， 中位数是 1.46×。 它们来自四类改动： 更宽的访存、 按 shape 选择 tile、 更多的工作切分以填满 GPU， 以及新算法。 这些都属于工作划分、 数据搬运和指令选择， 也就是作者本来就在做的决策。 顺序设置和寄存器设置分别只出现在 8% 和 5% 的 review 里。

Where the effort goes. A median attempt used 53.5M prompt tokens, 318 turns and 1.3 hours. In 69% of the 827 command logs, the agent read the IR or the ISA at least once. In 65%, it cleared the FlyDSL compile cache at least once (9,531 times in total). Agents do this when they cannot tell if the code that ran is the code that they wrote.

The most common failure in the reviews was a slower result on shapes that the agent did not time (35 of 89 reviews). A few reviews found problems that a compiler can find before the run. Some were correctness bugs, for example a missing barrier and an out-of-bounds read. Others were spills, for example a spill setting that made one shape 0.44× as fast. Nine reviews say that agents added their own launch caches to avoid the trace at each call.

精力花在哪里。 按中位数计， 一次尝试用了 53.5M prompt token、 318 轮对话、 1.3 小时。 在 827 份命令记录里， 有 69% 显示 agent 至少读过一次 IR 或 ISA。 有 65% 显示 agent 至少清过一次 FlyDSL 编译缓存（总共 9,531 次）。 agent 在无法确认 "运行的代码是不是自己写的代码" 时， 就会这样做。

review 里最常见的失败， 是 agent 没有计时的 shape 变慢了（89 份里有 35 份）。 少数 review 发现了编译器在运行前就能发现的问题。 有些是正确性 bug， 例如漏掉的 barrier 和越界读取。 有些是 spill， 例如一个让某个 shape 只剩 0.44× 速度的 spill 设置。 有 9 份 review 提到， agent 为了避开每次调用的 trace， 自己加了启动缓存。

Appendix E附录 EHow we measured怎样测量

How we measured experiments A and B

实验 A 和 B 怎样测量

  • Each arm is one patch to FlyDSL cb770e9a, the version that FlyBench v1 uses.
  • Arms that remove hints add a few lines to kernels/__init__.py. These lines change one kind of hint into an operation that does nothing, or they change the LLVM options. The register and occupancy arms change one line of the kernel.
  • The FlyBench v1 evaluator scored each arm. It is the same program that scores agent submissions.
  • The evaluator runs the stock kernel and the arm in new processes, in the order stock, arm, arm, stock (ABBA). It does this six times. This order cancels slow changes in GPU speed.
  • Before each cold call, it reads 512 MB of other data. Thus the caches do not keep data from the previous call.
  • It uses the public test shapes and new random shapes in each run.
  • An arm must pass the tests of FlyDSL and a correctness check on the new shapes. If it fails, it gets no speed result.
  • Each arm ran as one job on one MI355X GPU through the overlay. The job did not call an AI model.
  • 每个 arm 是针对 FlyDSL cb770e9a 的一个补丁， 这是 FlyBench v1 使用的版本。
  • 去掉提示的 arm 在 kernels/__init__.py 里加几行代码。 这几行代码把某一类提示变成什么都不做的操作， 或者修改 LLVM 选项。 寄存器和 occupancy 两个 arm 修改 kernel 里的一行。
  • 每个 arm 都由 FlyBench v1 评测器打分， 也就是给 agent 提交打分的同一个程序。
  • 评测器在新进程里按 stock、 arm、 arm、 stock 的顺序（ABBA）运行， 一共重复 6 次。 这个顺序能抵消 GPU 速度的缓慢变化。
  • 每次冷调用前， 评测器先读 512 MB 其他数据， 这样缓存里不会留下上一次调用的数据。
  • 每次运行都使用公开的测试 shape 和新随机抽取的 shape。
  • arm 必须通过 FlyDSL 自己的测试和新 shape 上的正确性检查， 否则不给速度结果。
  • 每个 arm 作为一个作业， 通过 overlay 在一张 MI355X GPU 上运行。 作业不调用 AI 模型。

Controls

对照

Each job also compiled the stock kernel and the arm at two shapes, and compared the ISA. All arms changed the ISA except three. The first is the occupancy arm (appendix A). The other two are null controls: RMSNorm, which has no hints to remove, and the A16W16 GEMM with the added lines but nothing removed.

The null controls measured 1.004× and 0.998×. This is the noise of our setup. Thus we cannot see effects smaller than about 0.5%.

每个作业还在两个 shape 上分别编译 stock kernel 和 arm， 并比较 ISA。 除了三个 arm， 其他 arm 都改变了 ISA。 第一个是 occupancy arm（附录 A）。 另外两个是空白对照： 一个是没有提示可去的 RMSNorm， 另一个是加了那几行代码、 但什么都没去掉的 A16W16 GEMM。

两个空白对照测得 1.004× 和 0.998×。 这就是我们这套测量的噪声， 所以小于约 0.5% 的效果看不出来。

The register arm changes code only for 256×256 tiles. Only two of its 19 timed shapes use these tiles. Thus we report this arm at these two shapes.

寄存器 arm 只改变 256×256 tile 的代码。 它的 19 个计时 shape 里只有 2 个用这种 tile， 所以我们只在这两个 shape 上报告它。

Limit. The overlay puts single-GPU jobs next to other jobs on the same node, so we did not measure on idle GPUs. The ABBA order removes slow drift between stock and arm. It does not remove noise from other jobs. The intervals below include this noise. The agent data in experiment C comes from earlier FlyBench runs, not from new agent jobs.

局限。 overlay 会把单卡作业和其他作业放在同一个节点上， 所以我们不是在空闲的 GPU 上测量的。 ABBA 顺序能消除 stock 和 arm 之间的缓慢漂移， 但消除不了其他作业带来的噪声。 下面的区间已经包含这部分噪声。 实验 C 的 agent 数据来自之前的 FlyBench 运行， 不是新跑的 agent 作业。

barrier (s_barrier)barrier（s_barrier）An instruction that stops each wave of a workgroup until all of these waves arrive at it.一条指令： 让一个 workgroup 里的每个 wave 停下， 直到所有 wave 都执行到这里。
fence (sched_barrier)fence（sched_barrier）A marker for the compiler, not an instruction for the GPU. The compiler must not move instructions across it.给编译器的标记， 不是给 GPU 的指令。 编译器不能把指令移过它。
interleave group (sched_group_barrier)交错组（sched_group_barrier）A marker that gives the compiler an order pattern, for example "one matrix instruction, then one load".给编译器的顺序模板， 例如 "一条矩阵指令， 然后一条加载指令"。
wave priority (s_setprio)wave 优先级（s_setprio）An instruction that tells the GPU which waves to run first.一条指令： 告诉 GPU 先执行哪些 wave。
pinpinA hint that forces a value into one kind of register, for example into AGPRs.强制把某个值放进指定寄存器（例如 AGPR）的提示。
hazardhazardA pair of instructions that must have a gap between them. The compiler fills the gap with s_nop, an instruction that does nothing.两条之间必须留出间隔的指令。 编译器用 s_nop（什么都不做的指令）填这个间隔。
heuristic启发式规则A general rule that a compiler uses to make a choice automatically. It works well on average, but it does not know what the author wants.编译器自动做选择时用的通用规则。 平均效果不错， 但它不知道作者想要什么。
LLVMLLVMA large, general compiler project. FlyDSL uses its AMD GPU part to make the final machine instructions.一个大型通用编译器项目。 FlyDSL 用它的 AMD GPU 部分生成最终的机器指令。
MLIRMLIRA framework for building compiler steps. FlyDSL uses it between Python and LLVM.一个用来搭建编译步骤的框架。 FlyDSL 在 Python 和 LLVM 之间使用它。
ISAISAThe machine instructions that the GPU runs. We read the ISA to see what the compiler did.GPU 真正执行的机器指令。 我们读 ISA 来确认编译器做了什么。
tracetraceFlyDSL runs the Python code of a kernel once and records its operations. It does this before each launch.FlyDSL 先把 kernel 的 Python 代码执行一遍， 记录其中的操作。 每次启动 kernel 前都要做一次。
layoutlayoutA rule that says which thread holds which element of a data tile.一条规则： 说明数据 tile 的哪个元素由哪个线程持有。
race竞争A bug in which the result depends on which wave runs first. The wrong output can change from run to run.一种 bug： 结果取决于哪个 wave 先执行。 错误的输出每次运行都可能不同。
