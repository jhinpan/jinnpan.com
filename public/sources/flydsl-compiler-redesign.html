01The question问题

My mentor keeps asking me to think about the compiler chain. The last reading asked where the compiler could join the kernel-optimization loop. This one asks the more basic question: if we were free to drop MLIR, and even LLVM, what should a kernel DSL whose main users are agents keep, and what should it throw away? A design argument costs nothing to write, so this post also runs the experiments that could have shown it to be wrong, on the same overlay fleet and with the same evaluator that score the agents.

mentor 一直让我想清楚 compiler chain。 上一篇问的是编译器能从哪里进入 kernel 优化循环。 这一篇问一个更基础的问题： 如果可以扔掉 MLIR， 甚至扔掉 LLVM， 一个主要给 agent 用的 kernel DSL 应该留下什么、 扔掉什么？ 设计论证写起来不花成本， 所以这一篇同时做了有机会推翻它的实验： 用的是给 agent 打分的同一个 overlay 集群和同一个评测器。

Short answer. The largest redundancy in FlyDSL's compiler is not code size. It is that two parties decide the same things: the author decides tiles, data movement and instruction interleaving in Python, then LLVM's heuristics decide register placement and instruction order again, then the author takes them back with fences, inline asm and LLVM patches. On MI355X, removing one explicit decision and letting LLVM decide cost 5–16% speed on 6 kernels and about 1% or less on one more, and on two kernels it made the output wrong, because their "scheduling" fences were holding correctness. Agents, meanwhile, found their speedups almost entirely in decisions the author already owns, and 69% of their runs went digging in IR or ISA. So the redesign gives every decision exactly one owner, expresses synchronization as data dependencies so that every performance knob is safe to search, and makes the compiler report what it did. MLIR can go entirely; LLVM goes in two steps.

简短回答。 FlyDSL 编译器最大的冗余不在代码量， 而在于同一件事有两方在决定： 作者在 Python 里决定 tile、 数据搬运和指令交错， LLVM 的启发式再把寄存器放置和指令顺序决定一遍， 作者再用 fence、 inline asm 和 LLVM 补丁把它们抢回来。 在 MI355X 上， 拿走作者的一个显式决策、 交给 LLVM 去决定， 让 6 个 kernel 的速度下降了 5–16%， 另一个 kernel 下降约 1% 或更少， 还让两个 kernel 算错了结果， 因为它们的"调度" fence 其实在撑着正确性。 与此同时， agent 的提速几乎全部来自作者本来就掌握的决策， 而 69% 的 agent 运行都去翻过 IR 或 ISA。 所以重新设计要做三件事： 每个决策只有一个决策者； 把同步表达成数据依赖， 让每个性能旋钮都可以放心搜索； 让编译器报告它做了什么。 MLIR 可以完全去掉， LLVM 分两步去掉。

02Five decisions, two deciders五类决策， 两个决策者

Start from what is true of any AMD GPU kernel, whatever language wrote it. Its speed is set by five kinds of decisions. Three of them shape the work: how the problem is cut into a grid of tiles (D1), which lane moves which bytes through which memory (D2), and which matrix instruction does the arithmetic (D3). Two of them shape the instruction stream: which register file each value lives in, which caps how many waves fit (D4), and in what order instructions issue, where the waits go and which wave gets priority (D5).

先从任何 AMD GPU kernel 都成立的事实出发， 不管它是用什么语言写的。 它的速度由五类决策决定。 其中三类决定"工作怎么分"： 问题怎样切成 tile 组成的 grid（D1）、 哪个 lane 通过哪一级存储搬哪些字节（D2）、 用哪条矩阵指令做运算（D3）。 另外两类决定"指令流长什么样"： 每个值放在哪个寄存器堆， 这又决定能驻留几个 wave（D4）； 指令按什么顺序发射、 wait 插在哪里、 哪个 wave 优先（D5）。

The red channel is not rare. In the kernel corpus at fe81c407, 34 of 180 kernel files call sched_barrier (257 times), 44 place waits by hand (186), 13 use inline asm and 12 set wave priority. Kernel comments say why in plain words: inline asm "so LLVM sees no memory op" and inserts no wait (fp4_gemm_4wave.py), a fence because "the scheduler may hoist them above s_barrier: a race" (mega_moe_tp/gemm.py). Pinning one accumulator to AGPRs through LLVM took patches to its register allocator and instruction selector (#1368), and the patch was reverted because it made another team's kernel spill (#1477).

红色通道并不少见。 在 fe81c407 的 kernel 语料里， 180 个文件中有 34 个调用 sched_barrier（共 257 次）， 44 个手工放 wait（186 次）， 13 个用 inline asm， 12 个设置 wave 优先级。 kernel 注释把原因写得很直白： 用 inline asm 是为了"让 LLVM 看不到访存"从而不插 wait（fp4_gemm_4wave.py）； 加 fence 是因为"调度器可能把它们提到 s_barrier 之前： 这是竞争"（mega_moe_tp/gemm.py）。 想通过 LLVM 把一个累加器固定在 AGPR 上， 需要修改它的寄存器分配器和指令选择（#1368）， 而这个补丁又因为让另一个团队的 kernel 出现 spill 被回滚（#1477）。

Why this matters more for an agent than for a person: an agent improves a kernel by local edits and measurement, which only works if a local edit has a local effect. A heuristic that re-decides globally breaks that premise. One example from our runs: removing the four s_setprio calls from the FP8 8-wave GEMM, an instruction whose only documented job is wave priority, changed the register allocation and created 6 VGPR spills. The reason is one line in LLVM's AMDGPU backend: s_setprio is a hard scheduling boundary (SIInstrInfo.cpp). One knob, two meanings, and nothing in the source says so.

这件事对 agent 比对人更要紧。 agent 靠局部修改加测量来改进 kernel， 这只有在"局部修改只产生局部影响"时才成立。 一个会全局重新决定的启发式打破了这个前提。 我们实验里的一个例子： 从 FP8 8-wave GEMM 里去掉 4 处 s_setprio（文档上它只负责 wave 优先级）， 寄存器分配随之改变， 多出 6 个 VGPR spill。 原因是 LLVM AMDGPU 后端里的一行代码： s_setprio 是一个硬调度边界（SIInstrInfo.cpp）。 一个旋钮有两种含义， 而源码里看不出来。

03Where the current compiler repeats itself现在的编译器在哪里重复自己

With the decision table in hand, the rest of the compiler's redundancy is easier to see. Each item below is a place where the same information is represented, or the same decision is made, more than once.

有了这张决策表， 编译器其余的冗余就容易看清了。 下面每一项， 都是同一份信息被表示了不止一次， 或者同一个决定被做了不止一次。

Two languages, switched by an implicit rule

两种语言， 靠隐式规则切换

A FlyDSL kernel is Python that runs at trace time mixed with Python that becomes runtime control flow, and a 1,928-line AST rewriter decides which is which from the type of a value (ast_rewriter.py). The rule leaks: #1436 fixed a case where if flag: return a followed by return b returned b for every flag, without an error, and one production kernel had silently ignored an input since it was written. The repository's agent guide lists four restrictions that exist only because of this rewriting (CLAUDE.md).

一个 FlyDSL kernel 里混着两种 Python： 一种在 trace 时执行， 一种会变成运行时控制流。 由一个 1928 行的 AST 改写器根据值的类型来判断哪段是哪种（ast_rewriter.py）。 这个规则会漏： #1436 修了一个问题， if flag: return a 后面接 return b 时， 不管 flag 是什么都返回 b， 而且不报错； 一个生产 kernel 从写成那天起就悄悄忽略了一个输入。 仓库给 agent 的指南里列了四条限制， 它们只因为这种改写才存在（CLAUDE.md）。

Layout algebra, built as IR and then deleted

layout algebra： 先建成 IR， 再删掉

Most layouts are fully static, so their algebra is compile-time arithmetic on integer tuples. FlyDSL nevertheless emits every step as an MLIR op whose type carries the layout, then folds it away. For fp8_gemm_4wave the traced module holds 61,989 ops; after canonicalization and layout lowering 9,907 remain. Building and deleting the other 84% is most of the 0.80 s trace. The pure-Python reference implementation of the same algebra, pycute, is about 760 lines.

大多数 layout 完全是静态的， 所以它们的代数就是整数元组上的编译期算术。 但 FlyDSL 仍然把每一步都生成为一个 MLIR op， layout 记在 op 的类型里， 然后再折叠掉。 对 fp8_gemm_4wave， trace 出来的模块有 61,989 个 op， 经过 canonicalize 和 layout lowering 后只剩 9,907 个。 建出来又删掉的这 84% 占了 0.80 s trace 时间的大部分。 同一套代数的纯 Python 参考实现 pycute 大约 760 行。

Registers modeled as memory, then promoted back

寄存器先当内存建模， 再提升回来

Register fragments are created as memrefs in a register address space, and two passes (about 900 lines) turn them back into vector values before LLVM sees them (Passes.td). The round trip copies C++ CuTe's habit of declaring register arrays; a compiler can represent a register tile as a value from the start.

寄存器 fragment 一开始被建成寄存器地址空间里的 memref， 再由两个 pass（约 900 行）在交给 LLVM 之前变回 vector 值（Passes.td）。 这个往返照搬了 C++ CuTe 声明寄存器数组的习惯； 编译器完全可以一开始就把寄存器 tile 表示成一个值。

Every call re-traces; every process re-JITs the launcher

每次调用都重新 trace， 每个进程都重新 JIT launcher

A @flyc.jit call traces the whole launcher and kernel, prints the module and hashes the text before it can look up the cache (jit_function.py). That keeps the cache key honest, but a cache hit on fp8_gemm_4wave still costs 0.96 s. The host launcher itself is lowered through MLIR and JIT-compiled by an LLVM ExecutionEngine at O3 in every process, 22–33 ms per artifact, to do what a kernarg buffer and hipModuleLaunchKernel already do.

@flyc.jit 每次调用都要先 trace 整个 launcher 和 kernel、 打印模块、 对文本做哈希， 然后才能查缓存（jit_function.py）。 这样缓存 key 很可靠， 但 fp8_gemm_4wave 命中缓存的一次调用仍要 0.96 s。 host 端的 launcher 本身也要经过 MLIR 降级， 再由 LLVM ExecutionEngine 在每个进程里以 O3 JIT 一次， 每个 artifact 22–33 ms， 而它要做的事情， 一个 kernarg 缓冲区加 hipModuleLaunchKernel 就能做到。

Knobs that reach LLVM through four lanes, some of them dead

旋钮通过四条通道到达 LLVM， 有的通道是死的

The repository's own LLVM skill documents four lanes from Python to LLVM, one of which is silently discarded on AMD; a compile-hint dictionary that accepts misspelled keys and still changes the cache key; and an optimization-level variable that is validated and never read (llvm skill §3, §8). Our own experiment found another: in fp8_gemm_4wave the explicit occupancy hints produce byte-identical ISA to no hints at all.

仓库自己的 llvm skill 记录了从 Python 到 LLVM 的四条通道， 其中一条在 AMD 上会被悄悄丢弃； 一个接受拼错 key、 却仍会改变缓存 key 的 compile-hint 字典； 一个会被校验、 却从没被读取的优化级别变量（llvm skill §3、§8）。 我们自己的实验又发现一个： 在 fp8_gemm_4wave 里， 显式的 occupancy 提示和完全不写提示生成的 ISA 逐字节相同。

04One decider per decision一个决策， 一个决策者

The redesign follows from the table. For every decision, either the author makes it explicitly and the compiler honors and checks it, or the author delegates it and the compiler makes it deterministically and says what it chose. Never both. Five consequences:

重新设计直接从这张表推出来。 对每个决策， 要么作者显式做出、 编译器照做并检查， 要么作者把它交出去、 编译器确定性地做出并说明选了什么。 不允许两者同时存在。 由此有五个推论：

  1. Python becomes the meta-language only. Python control flow always runs at compile time; runtime loops and branches are explicit constructs (fx.loop, fx.cond), and using a runtime value in a Python if is an error. This is JAX's model, and it deletes the AST rewriter and its four rules.
  2. Python 只做元语言。 Python 控制流永远在编译期执行； 运行时的循环和分支用显式构造（fx.loop、fx.cond）， 在 Python if 里用运行时值就报错。 这就是 JAX 的模型， 它让 AST 改写器和那四条规则一起消失。
  3. Layout algebra is evaluated where it is static: in Python. Every intermediate layout is a value one can print and test; only dynamic leaves become IR.
  4. layout algebra 在它静态的地方求值： 在 Python 里。 每个中间 layout 都是可以打印、 可以测试的值； 只有动态的部分才生成 IR。
  5. A small hardware-explicit IR (call it KIR). Values are typed as uniform (SGPR) or per-lane (VGPR); register tiles carry their thread-value layout and register class; asynchronous copies return tokens, and a wait names the token it waits for. Synchronization becomes a data dependency the compiler can see, so reordering can never break it.
  6. 一个小而显式的硬件 IR（这里叫 KIR）。 值的类型区分 uniform（SGPR）和 per-lane（VGPR）； 寄存器 tile 带着它的 thread-value layout 和寄存器类； 异步拷贝返回 token， wait 写明它等的是哪个 token。 同步变成编译器看得见的数据依赖， 于是重排永远不会破坏它。
  7. A deterministic backend that reports. Instruction selection by table (generated from AMD's machine-readable ISA XML, which already covers CDNA3, CDNA4 and CDNA5); program order in explicit regions and a list scheduler with a published machine model in automatic ones; linear-scan allocation that honors pins; waits derived from tokens; hazards from tables. Each pass writes what it decided into a report the agent reads.
  8. 一个确定性的、 会报告的后端。 指令选择查表（由 AMD 的机器可读 ISA XML 生成， 它已经覆盖 CDNA3、 CDNA4 和 CDNA5）； 显式区域按程序顺序， 自动区域用带公开机器模型的列表调度； 线性扫描分配， 遵守 pin； 由 token 推出 wait； 由表插入 hazard。 每个 pass 都把它的决定写进 agent 读的报告。
  9. Only semantics-preserving knobs. Because correctness depends only on data flow and tokens, schedule, pins, stage count and unroll can only change speed. Agents and autotuners can search them without a correctness review per point.
  10. 只保留不改变语义的旋钮。 正确性只依赖数据流和 token， 所以调度、 pin、 stage 数和 unroll 只会改变速度。 agent 和 autotuner 可以放心搜索， 不需要每个点都做一次正确性审查。

What this means for the two big dependencies. MLIR can go entirely: its passes take only 11–12% of a large kernel's cold compile (section 09), and the costs it does carry are the op-by-op trace, the build-then-delete IR, and C++ rebuilds for every pass change. LLVM goes in two steps. First drop its heuristic code generation for explicit kernels and keep it only as an assembler, which is exactly how AMD's own hipBLASLt TensileLite builds its GEMMs: Python writes assembly and amdclang++ -x assembler encodes it (Toolchain/Component.py). Then, once the new backend has passed the kernel corpus, generate an encoder from the ISA XML and drop LLVM for those kernels.

对两个大依赖意味着什么。 MLIR 可以完全去掉： 它的 pass 只占大 kernel 冷编译的 11–12%（第 09 节）， 它真正带来的成本是逐个 op 的 trace、 先建后删的 IR， 以及每改一个 pass 都要重编 C++。 LLVM 分两步去掉。 第一步， 在显式 kernel 上不再用它的启发式代码生成， 只把它当汇编器用。 AMD 自己的 hipBLASLt TensileLite 正是这样做 GEMM 的： Python 写汇编， amdclang++ -x assembler 负责编码（Toolchain/Component.py）。 第二步， 等新后端通过 kernel 语料之后， 从 ISA XML 生成编码器， 在这些 kernel 上去掉 LLVM。

05How we tested it on the overlay怎样在 overlay 上检验

The new backend does not exist yet, so the experiments test the premises it rests on, each with an outcome that would have counted against it:

新后端还不存在， 所以实验检验的是它所依赖的前提。 每个前提都有一个会对它不利的可能结果：

  • A. The D4/D5 decisions authors make explicitly carry real speed, and LLVM's heuristics do not recover it when left alone. Against it: removing them changes nothing.
  • A. 作者显式做出的 D4 / D5 决策带着实打实的速度， LLVM 的启发式在没人管时拿不回来。 不利结果： 去掉它们什么都没变。
  • B. Where authors made no such decision, untuned but safe knobs leave headroom. Against it: no knob moves the time.
  • B. 作者没有做这类决策的地方， 那些没人调过、 但安全的旋钮还留有空间。 不利结果： 没有哪个旋钮能改变时间。
  • C. Agents' cost is dominated by what a compiler could show or check. Against it: agents rarely look at compiler output, and their wins come from compiler knobs.
  • C. agent 的成本主要花在编译器本可以展示或检查的事情上。 不利结果： agent 很少看编译器输出， 而且它们的提速来自编译器旋钮。
  • D. The front end's cost is paid on every iteration. Against it: a cache hit is free.
  • D. 前端的开销在每次迭代都要付。 不利结果： 命中缓存不花时间。

Protocol. Every arm in A and B is a patch to FlyDSL cb770e9a, scored by the FlyBench v1 evaluator, the same one that scores agent submissions: candidate against stock in fresh worker processes for each of six ABBA pairs, each cold call after a 512 MB cache-flushing read, plus warm blocks, over the public timed shapes and freshly drawn ones, with FlyDSL's own tests and a fresh-shape correctness oracle as a gate. A speed ratio below 1 means the arm is slower than the stock kernel. Hint arms install a few lines in kernels/__init__.py that turn one family of hints into no-ops or edit the LLVM options; the AGPR and occupancy arms edit one line of the kernel. Each arm ran as one model-free job on one MI355X through the overlay queue, exactly as FlyBench evaluators do.

协议。 A 和 B 的每个 arm 都是一个针对 FlyDSL cb770e9a 的补丁， 由 FlyBench v1 评测器打分， 也就是给 agent 提交打分的那一个： 候选和 stock 在新的 worker 进程里成对比较， 做 6 组 ABBA， 每次冷调用前先读一遍 512 MB 来清缓存， 另外还有热调用， 覆盖公开的计时 shape 和每次新抽取的 shape； FlyDSL 自己的测试和新 shape 上的正确性 oracle 是门禁。 速度比低于 1 表示这个 arm 比 stock 慢。 提示类 arm 在 kernels/__init__.py 里加几行代码， 把某一类提示变成空操作， 或者修改 LLVM 选项； AGPR 和 occupancy 两个 arm 改 kernel 里的一行。 每个 arm 作为一个不调用模型的作业， 通过 overlay 队列在一张 MI355X 上运行， 和 FlyBench 评测作业完全一样。

Controls. Each job also compiled the stock kernel and the arm at two shapes, the first timed shape and the largest, and compared the final ISA. Every arm changed the ISA except three: the occupancy arm (section 06) and two null controls, RMSNorm, which has no hints to remove, and the A16W16 GEMM with the shim installed and nothing removed. The null controls measured 1.004× and 0.998×; that is the noise of this setup, so effects under about half a percent are not resolved. The AGPR arm changes code only for the 256×256 tiles that two of its 19 timed shapes use, so we report it at those shapes.

对照。 每个作业还在两个 shape 上（第一个计时 shape 和最大的 shape）分别编译 stock kernel 和这个 arm， 并比较最终 ISA。 除了三个 arm， 其他 arm 都改变了 ISA。 这三个是 occupancy arm（见第 06 节）和两个空白对照： 一个是没有提示可去的 RMSNorm， 另一个是装了 shim、 什么都没去掉的 A16W16 GEMM。 两个空白对照测得 1.004× 和 0.998×， 这就是这套测量的噪声， 所以小于约 0.5% 的效果分辨不出来。 AGPR 这个 arm 只会改变 256×256 tile 的代码， 而 19 个计时 shape 里只有 2 个用这种 tile， 所以我们在这两个 shape 上报告它。

Caveat. The overlay places single-GPU jobs beside other jobs on the same node. Pairing inside one job on one GPU removes drift between the two sides, but not noise from neighbours; the intervals below include it. The agent corpus in C comes from earlier FlyBench runs on the same fleet, not from new agent jobs.

注意。 overlay 会把单卡作业和别的作业放在同一个节点上。 在同一个作业、 同一张卡上做配对， 能消除两侧之间的漂移， 但消除不了邻居带来的噪声； 下面的区间已经包含了它。 C 里的 agent 语料来自同一集群上之前的 FlyBench 运行， 不是新跑的 agent 作业。

The decisions are worth 5–16%, and LLVM does not find them

这些决策值 5–16%， 而 LLVM 找不到它们

Removing the schedule hints cost the preshuffle GEMM 12% of its speed (0.882×), the MX preshuffle GEMM 5% and the sliding-window attention 16%. For the preshuffle GEMM the interleave groups carry all of it: dropping only them gives 0.883×, the same as dropping everything. Removing s_setprio cost the two 8-wave GEMMs 14% and 10%; the ISA shows why the first one is more than a priority change, with VGPR spills appearing where there were none. Letting LLVM allocate the FP8 4-wave GEMM's accumulators instead of pinning them cost 14% at 16384³ and 9% at 8192³: spills went from 10 to 92 and accumulator moves from 796 to 6,437. Interesting in the other direction: even the pinned version spills 10 VGPRs at that size, which nobody had been told. Removing the same kernel's occupancy hints (waves_per_eu, flat_work_group_size) changed nothing: the ISA is byte-identical at both dumped shapes, so LLVM's default already matched them. A hint that does nothing does no harm, but no tool tells the author or the agent that it does nothing.

去掉调度提示后， preshuffle GEMM 的速度下降 12%（0.882×）， MX preshuffle GEMM 下降 5%， 滑窗 attention 下降 16%。 对 preshuffle GEMM， 全部收益都来自交错 group： 只去掉 group 得到 0.883×， 和全部去掉一样。 去掉 s_setprio 让两个 8-wave GEMM 分别下降 14% 和 10%； ISA 说明了为什么前者不只是优先级变化： 原来没有 spill 的地方出现了 VGPR spill。 让 LLVM 分配 FP8 4-wave GEMM 的累加器、 而不是固定它们， 在 16384³ 上慢了 14%， 在 8192³ 上慢了 9%： spill 从 10 个增加到 92 个， 累加器搬运从 796 条增加到 6,437 条。 反过来也值得一提： 即使是固定后的版本， 在这个尺寸上也有 10 个 VGPR spill， 之前没有人知道。 去掉同一个 kernel 的 occupancy 提示（waves_per_eu、flat_work_group_size）什么都没改变： 两个 dump 的 shape 上 ISA 逐字节相同， 说明 LLVM 的默认值本来就和它们一致。 不起作用的提示没有害处， 但没有任何工具告诉作者或 agent 它不起作用。

Two kernels' "scheduling" fences were holding correctness

两个 kernel 的"调度" fence 其实在撑着正确性

Removing the schedule fences made the A16W16 GEMM fail 1 of 880 of FlyDSL's tests (a mismatched result) and the dense flash attention fail 28 of 1039 (log-sum-exp off by up to 0.43, and NaN). A repeat of the A16W16 arm in a new job failed the same test with different wrong elements (182 and 31 of 163,840), the signature of a race rather than of rounding. With the hint shim installed and nothing removed, the same evaluator passed all of its tests (null control, 0.998×). A scheduling hint is supposed to change only speed. Here it changes the answer. We did not trace which instruction moved, but the kernels point to the cause: they order asynchronous copies and shared-memory reuse with hand-placed waits and barriers that LLVM does not tie to the loads they guard, and a FlyDSL comment elsewhere names exactly this hazard: "the scheduler may hoist them above s_barrier: a race" (mega_moe_tp/gemm.py). Keeping the full fences and dropping only the interleave groups ran at 0.990× [0.989, 0.991] and stayed correct, so it is the fences, not the groups, that hold the answer. This is the strongest result of the post, and it is not about speed: in today's stack an autotuner, or an agent, cannot safely toggle a scheduling knob, because some of them are correctness constraints in disguise.

去掉调度 fence 之后， A16W16 GEMM 在 FlyDSL 自己的 880 个测试里失败了 1 个（结果不一致）， dense flash attention 失败了 1039 个里的 28 个（log-sum-exp 最多差 0.43， 还有 NaN）。 在新的作业里重复 A16W16 这个 arm， 失败的是同一个测试， 但错的元素不一样（163,840 个里分别错了 182 个和 31 个）， 这是竞争的特征， 不是舍入误差。 装上提示 shim、 什么都不去掉时， 同一个评测器下它的测试全部通过（空白对照， 0.998×）。 调度提示本应只影响速度， 这里却改变了答案。 我们没有追查具体是哪条指令被移动了， 但 kernel 本身指向了原因： 它们用手工放置的 wait 和 barrier 来安排异步拷贝和共享内存复用的顺序， 而 LLVM 不会把这些 wait 和 barrier 与它们所保护的 load 联系起来。 FlyDSL 另一处注释写的正是这种风险： "调度器可能把它们提到 s_barrier 之前： 这是竞争"（mega_moe_tp/gemm.py）。 保留全部 fence、 只去掉交错 group 时， 速度是 stock 的 0.990× [0.989, 0.991]， 结果也正确。 所以撑住正确性的是 fence， 不是 group。 这是本文最强的结果， 而且它和速度无关： 在今天的工具链里， autotuner 或 agent 不能放心地切换调度旋钮， 因为其中一些其实是伪装起来的正确性约束。

LLVM's free schedule is sometimes better, shape by shape

按 shape 看， LLVM 的自由调度有时反而更好

The same preshuffle arm that is 12% slower overall is 3.4% faster at 16384³ and 2.1% faster at 8192³. The author's interleave template is a good fixed policy, not the best one for every shape. Plate V returns to this.

同一个 preshuffle arm， 整体慢了 12%， 在 16384³ 上却快了 3.4%， 在 8192³ 上快了 2.1%。 作者的交错模板是一个不错的固定策略， 但不是每个 shape 上最好的。 Plate V 会回到这一点。

The other two flash arms are small, and they point the same way. Removing its s_setprio gave 0.998× [0.997, 0.999] overall but cost up to 4.3% on single shapes (5 shapes beyond their noise floor). The kernel's author had switched LLVM's post-RA scheduler off to protect the hand-tuned order (flash_attn_gfx950.py); turning it back on gave 1.006× [1.004, 1.008], with no shape slower beyond noise and the best shape 6.7% faster; the ISA has 22 fewer s_nops (185 → 163). That gain is about the size of the kernel's 0.5% noise floor, so FlyBench would not count it as an improvement. The author could not see whether that flag helps, and FlyDSL's own notes record that three sibling FMHA kernels disagree on it, with no comment (arch-gfx950.md).

flash 的另外两个 arm 影响很小， 方向和上面一致。 去掉 s_setprio 后整体是 0.998× [0.997, 0.999]， 但在单个 shape 上最多慢 4.3%（5 个 shape 超出噪声范围）。 这个 kernel 的作者为了保护手工调好的顺序， 关掉了 LLVM 的 post-RA 调度器（flash_attn_gfx950.py）； 重新打开后得到 1.006× [1.004, 1.008]， 没有 shape 超出噪声地变慢， 最好的 shape 快了 6.7%； ISA 里少了 22 条 s_nop（185 → 163）。 这个收益和这个 kernel 0.5% 的噪声下限差不多大， 所以 FlyBench 不会把它算作提升。 作者看不到这个开关到底有没有用； FlyDSL 自己的笔记也写着， 三个同系列的 FMHA kernel 在这个开关上取值不一致， 而且没有注释（arch-gfx950.md）。

08Experiment C · what 671 agent runs actually did实验 C · 671 次 agent 运行到底做了什么

The overlay has already run FlyBench mode A many times: an agent gets one FlyDSL kernel and a time budget and tries to make it faster without changing its results. We read all of it that survives: 98 runs, 676 evaluator receipts, 89 independent reviews of the best patches, and 827 command traces (285,091 commands). Only aggregates are published.

overlay 已经跑过很多次 FlyBench mode A： agent 拿到一个 FlyDSL kernel 和一段时间预算， 在不改变结果的前提下设法让它变快。 我们读了所有留存下来的记录： 98 次 run、 676 张评测回执、 89 份对最好补丁的独立 review， 以及 827 份命令轨迹（共 285,091 条命令）。 这里只发布汇总数据。

Where the wins are. The legitimate speedups (median 1.46× reproduced by the reviewer) come from vectorizing the memory path, choosing tiles per shape, splitting work to fill an under-occupied grid, and rewriting the algorithm: D1–D3, the decisions the author already owns. Schedule and register knobs appear in 8% and 5% of them. So the redesign must keep, not take away, the expressiveness agents use: Python metaprogramming, layout algebra, atoms. Its promise to agents is not a new source of speedups.

提速在哪里。 合法的提速（review 复现的中位数是 1.46×）来自访存路径向量化、 按 shape 选 tile、 拆分工作以填满占用不足的 grid， 以及重写算法： 都是 D1–D3， 作者本来就掌握的决策。 调度和寄存器旋钮分别只出现在 8% 和 5% 的 review 里。 所以重新设计必须保留、 而不是拿走 agent 用到的表达能力： Python 元编程、 layout algebra、 atom。 它对 agent 的承诺不是一个新的提速来源。

Where the cost is. A median record took 53.5M prompt tokens, 318 turns and 1.3 h. 69% of runs went digging in IR or ISA at least once, and 65% cleared the FlyDSL compile cache at least once (9,531 cache clears in total), the habit of agents that cannot tell whether what ran is what they wrote. The reviews' most common failure was a per-shape regression on shapes the agent did not time (35 of 89); a few broke correctness in ways a compiler could catch statically: a missing barrier, an out-of-bounds read, a spill tier that cut one shape to 0.44×. Nine reviews mention host-side launcher caches that agents added to get around per-call tracing.

成本在哪里。 一个中位数 record 花了 53.5M prompt token、 318 轮、 1.3 小时。 69% 的运行至少翻过一次 IR 或 ISA， 65% 至少清过一次 FlyDSL 编译缓存（总共 9,531 次）， 这是 agent 无法确认"跑的是不是自己写的那份"时的习惯。 review 里最常见的失败是 agent 没测过的 shape 出现回退（89 份里 35 份）； 也有少数正确性问题是编译器可以静态发现的： 漏掉的 barrier、 越界读、 一个让某个 shape 掉到 0.44× 的 spill 档位。 有 9 份 review 提到 agent 为了绕开每次调用的 trace 而自己加了 host 端 launcher 缓存。

What the agents need from the compiler is mostly what the redesign's report and checks provide: resources, spills and occupancy per shape before a GPU run; the waits it inserted and why; a race and bounds check on shared memory; a cache that is keyed honestly and a launch path that does not re-trace. None of that needs MLIR or LLVM's heuristics; it needs a compiler that owns its decisions.

agent 需要编译器提供的， 大多正是重新设计里的报告和检查： 上 GPU 之前就知道每个 shape 的资源、 spill 和 occupancy； 插了哪些 wait、 为什么； 共享内存上的竞争和越界检查； 一个 key 可靠的缓存和一条不重新 trace 的 launch 路径。 这些都不需要 MLIR， 也不需要 LLVM 的启发式， 只需要一个对自己的决定负责的编译器。

10What the evidence adds up to证据加起来说明了什么

Premise A held, more strongly than expected: removing an explicit D4/D5 decision cost 5–16% in most of the arms that changed code, LLVM's heuristics did not recover it, and in two of the five kernels whose fences we removed, the "hints" were load-bearing for correctness. Premise B held in its split form: where nobody scheduled by hand, LLVM's default is hard to beat and needed; where an author did, the heuristic scheduler still costs time, and per-shape choice among correct schedules is worth 2.7–4.1% on the one kernel we measured it on. Premise C held with a correction: agents look hard at compiler output and distrust its cache, but their speedups come from the decisions they already own. Premise D held: the trace is paid on every iteration.

前提 A 成立， 而且比预想的更强： 在大多数改变了代码的 arm 里， 去掉一个显式 D4 / D5 决策要损失 5–16%， LLVM 的启发式拿不回来， 而且在我们去掉 fence 的五个 kernel 里， 有两个的"提示"在承担正确性。 前提 B 以分化的形式成立： 没有手工调度的地方， LLVM 的默认值很难超越， 也是必需的； 有作者调度的地方， 启发式调度器仍在浪费时间， 而在结果正确的调度之间按 shape 选择， 在我们测的这一个 kernel 上值 2.7–4.1%。 前提 C 成立但需要修正： agent 花大力气看编译器输出、 不信任它的缓存， 但它们的提速来自本来就掌握的决策。 前提 D 成立： trace 在每次迭代都要付。

So, can the redesign bring a large performance gain? Not uniformly, and the experiments say where. The large, measured stakes are in expert kernels whose authors already fight LLVM: there, a compiler that honors explicit order, pins and waits by construction protects the 5–16% those decisions are worth, and it makes a per-shape schedule search safe in kernels where today a fence may be carrying correctness. For simple kernels it is a wash on speed; LLVM's scheduler is worth keeping as the automatic mode until a replacement matches it. For agents, the larger gain is in iterations, not peak speed: fewer runs spent decoding ISA and fighting caches, and checks that turn silent wrong answers into compile errors.

那么， 重新设计能不能带来很大的性能提升？ 不会处处都有， 实验告诉了我们在哪里有。 实测到的大收益在专家 kernel 上， 它们的作者本来就在和 LLVM 对抗： 在那里， 一个从构造上就遵守显式顺序、 pin 和 wait 的编译器， 能保住这些决策值的 5–16%， 也让按 shape 的调度搜索变得安全， 即使在今天 fence 可能承担着正确性的 kernel 里。 对简单 kernel， 速度上不会有明显差别； 在找到能与之匹敌的替代品之前， LLVM 的调度器值得留作自动模式。 对 agent， 更大的收益在迭代次数， 而不在峰值速度： 更少的运行花在解读 ISA 和与缓存斗争上， 也有检查把悄悄算错变成编译错误。

11What would change our mind什么会推翻这个结论

  • A program-order backend that loses. Build KIR and the deterministic backend for one GEMM (the FP8 4-wave one, whose decisions are all explicit) and compare it with LLVM's output at identical source decisions. If program order plus honored pins is slower than LLVM, the case for dropping LLVM's scheduler in explicit mode fails.
  • 按程序顺序的后端输了。 为一个 GEMM（FP8 4-wave， 它的决策全是显式的）实现 KIR 和确定性后端， 在相同的源码决策下和 LLVM 的输出比较。 如果"程序顺序 + 遵守 pin"比 LLVM 慢， 在显式模式下去掉 LLVM 调度器的理由就不成立。
  • Agents that do not benefit from the report. On the overlay, run the same FlyBench records with two arms that differ only in a report command (resources, spills and occupancy per shape, waits, race and bounds checks). If fast-1.2 counts, regressions and tokens per record do not move, the agent half of the argument fails.
  • agent 没有从报告中获益。 在 overlay 上用同样的 FlyBench record 跑两个 arm， 唯一区别是有没有一个 report 命令（每个 shape 的资源、 spill 和 occupancy， wait， 竞争和越界检查）。 如果 fast-1.2 数、 回退和每个 record 的 token 都不变， 论证里关于 agent 的一半就不成立。
  • Correctness fences that are rare. We found them in two of the five kernels whose fences we removed. A corpus-wide scan that removes fences one by one under the evaluator would say how common they are; if they are rare, token-based synchronization matters less than this post claims.
  • 撑着正确性的 fence 其实很少。 在我们去掉 fence 的五个 kernel 里发现了两个。 在评测器下对整个语料逐个去掉 fence 扫一遍， 就能知道它们有多常见； 如果很少， 基于 token 的同步就没有本文说的那么重要。

13Epilogue结语

I started out expecting to argue that LLVM was the problem. The experiments say something narrower and more useful. LLVM's heuristics are good at the decisions nobody makes; the trouble starts when someone does make them and the compiler cannot tell a preference from a constraint. A compiler for agents should be built around that distinction: every decision has one owner, every constraint is visible as data, and everything the compiler chose is written down where the agent can read it.

一开始我以为要论证的是"LLVM 是问题所在"。 实验给出的结论更窄， 也更有用。 LLVM 的启发式很擅长做没人去做的决定； 麻烦出在有人做了这些决定， 而编译器分不清哪些是偏好、 哪些是约束。 给 agent 用的编译器应该围绕这个区别来建： 每个决定只有一个主人， 每个约束都以数据的形式可见， 编译器做出的每个选择都写在 agent 读得到的地方。
