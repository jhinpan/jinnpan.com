Experiment 003 · TokenSpeed vs SGLang · Kimi-K3 · 8× MI355X

Faster kernels, slower engine更快的核， 更慢的引擎

TokenSpeed's hand-written Gluon kernels beat SGLang's on every block of Kimi-K3 — MLA decode by 2.77x, MoE routing by 6.51x, total device compute by 1.21x — while issuing 30% fewer launches and exactly the same number of collectives. TokenSpeed 手写的 Gluon 核在 Kimi-K3 的每一块上都赢过 SGLang——MLA decode 快 2.77 倍、 MoE routing 快 6.51 倍、 device compute 总量少 1.21 倍—— 而且 launch 次数少 30%、 collective 次数完全相同。 然后引擎端到端还是更慢。 这篇讲那些毫秒到底去了哪里。

The result that did not fit对不上的那个结果

When an engine is slower, you profile the kernels, and the kernels are usually where the answer is. This time the trace said the opposite twice over, and it took a third measurement before I believed it.

当一个引擎更慢时， 你会去 profile 它的核函数， 而答案通常也确实在那里。 这次 trace 连着两次给出了相反的答案， 直到第三个测量出来我才相信。

TokenSpeed is LightSeek's inference engine, MIT-licensed and public since May 2026. It treats Kimi-K3 on AMD gfx950 as a first-class path: a Dockerfile.amd, native Gluon kernels for MoE and MLA decode, per-commit CI on an 8× MI35x runner. We already had a heavily instrumented SGLang deployment of the same checkpoint on the same node, so the two could be put side by side under one methodology, on one day, on one machine.

TokenSpeed 是 LightSeek 的推理引擎， MIT 协议， 2026 年 5 月开源。 它把 Kimi-K3 on AMD gfx950 当成一等公民： 有 Dockerfile.amd、 MoE 和 MLA decode 都有原生 Gluon 核、 还有跑在 8× MI35x runner 上的 per-commit CI。 我们手上正好有同一份 checkpoint、 同一台机器上已经 profile 得很透的 SGLang 部署， 所以两者可以在同一套方法学下、 同一天、 同一台机器上并排测。

The headline is a contradiction. Every kernel group that maps cleanly between the two stacks is faster on TokenSpeed. Its total device compute per decode step is lower. It issues fewer launches. And it loses.

结论本身是个矛盾。 凡是能在两套栈之间干净映射的核函数组， TokenSpeed 都更快。 它每个 decode step 的 device compute 总量更低。 它的 launch 次数更少。 然后它输了。

the three numbers

Device compute per decode step: TokenSpeed 17,108 µs against SGLang 20,769 µs. Kernel launches per step: 2,375 against 3,372. Collective dispatches per step: 187 against 187 — identical. End-to-end step: 22.19 ms against 19.39 ms. TokenSpeed does less work, in fewer launches, with the same communication, and takes 14% longer.

每 decode step 的 device compute： TokenSpeed 17,108 µs， SGLang 20,769 µs。 每 step 的 kernel launch 数： 2,375 对 3,372。 每 step 的 collective dispatch 数： 187 对 187， 完全相同。 端到端 step： 22.19 ms 对 19.39 ms。 TokenSpeed 干的活更少、 launch 更少、 通信一样多， 然后多花 14% 的时间。

Both of the cheap explanations are ruled out by measurement, not by argument. It is not launch overhead — it issues 30% fewer launches. It is not collective count — both issue exactly one all-reduce per layer block, 187 per step. Whatever costs TokenSpeed those milliseconds happens between the kernels, not inside them, which turns the AMD story from a kernel problem into a runtime problem.

两个最省事的解释都是被测量排除的， 不是被论证排除的。 不是 launch overhead—— 它的 launch 少 30%。 不是 collective 数量—— 两边都是每个 layer block 一次 all-reduce， 每 step 187 次。 那些毫秒是花在核函数*之间*的， 不是核函数内部。 这把 AMD 上的故事从一个核函数问题变成了一个 runtime 问题。

the flag that would have silently ruined it

Both benchmark harnesses descend from vLLM's benchmark_serving.py and print identically-named metrics, so it is easy to assume the flags mean the same thing. --random-range-ratio does not. SGLang's 1 means exact lengths. TokenSpeed validates the argument into [0, 1) and 0 means exact lengths. Passing 1 to both compares exact lengths against an argument error. Every number here uses exact lengths on both sides.

两边的 benchmark harness 都源自 vLLM 的 benchmark_serving.py， 打印的指标名字一模一样， 所以很容易默认 flag 的含义也一样。 --random-range-ratio 不是。 SGLang 的 1 表示精确长度； TokenSpeed 把参数校验在 [0, 1) 区间内， 0 才表示精确长度。 两边都传 1， 比的就是「精确长度」对「参数报错」。 本文所有数字两边都用精确长度。

02

Four pitfalls to a running server到跑起来之间的四个坑

None of these are exotic, all four are load-bearing, and the documented recipe walks into three of them. They are worth recording because each one is the kind of failure that costs an afternoon and leaves no trace in a benchmark table.

没有一个是稀奇古怪的问题， 四个都绕不过去， 而官方文档的 recipe 会踩中其中三个。 值得记下来， 是因为每一个都是那种「浪费一个下午、 却在 benchmark 表格里不留痕迹」的失败。

2.1 · A pinned dependency that was never published2.1 · 一个从未发布过的依赖被硬钉住

python/pyproject.toml on main pins tokenspeed-mooncake>=0.3.12.post20260725. That package has no PyPI release at all, so the runtime install dies with from versions: none. Mooncake is the KV transfer engine for prefill/decode disaggregation; its imports are lazy, inside runtime/pd/ and runtime/cache/storage/mooncake_store/, and an aggregated single-node server started with --disable-kvstore never reaches them. Install the runtime with that one entry removed. The general lesson: repo main can be ahead of what its own package index can satisfy.

main 上的 python/pyproject.toml 把 tokenspeed-mooncake 钉在 >=0.3.12.post20260725。 这个包在 PyPI 上一个 release 都没有， 所以运行时安装直接死在 from versions: none。 Mooncake 是 prefill / decode 分离用的 KV 传输引擎； 它的 import 都是惰性的， 藏在 runtime/pd/ 和 runtime/cache/storage/mooncake_store/ 里， 而用 --disable-kvstore 起的单机聚合式服务永远走不到。 把这一条摘掉再装即可。 一般性的教训是： 仓库 main 可以跑在它自己的包索引能满足的范围之前。

2.2 · xgrammar silently replaces the ROCm Triton2.2 · xgrammar 悄悄换掉了 ROCm 版 Triton

This is the subtle one, and it fails silently. torch 2.11.0+rocm7.2 requires triton-rocm==3.6.0. xgrammar declares a bare triton dependency. Both distributions install into the same triton/ directory, so pip installs stock triton 3.7.1 from PyPI on top of the ROCm build and whichever landed last wins:

这个坑很隐蔽， 而且是静默失败。 torch 2.11.0+rocm7.2 要求 triton-rocm==3.6.0， 而 xgrammar 声明了一个裸的 triton 依赖。 两个发行包装进的是*同一个* triton/ 目录， 于是 pip 把 PyPI 的 triton 3.7.1 装到 ROCm 版之上， 谁后落地谁赢：

$ python -c "import triton; print(triton.__version__)"
3.7.1          # stock PyPI build — not the ROCm one torch asked for

Nothing errors. You simply run a Triton that was not built for your platform. The fix is to uninstall triton and reinstall triton-rocm==3.6.0 after everything else settles. The Gluon gfx950 kernels turn out to be immune, and the reason is a design decision worth stealing: tokenspeed-kernel-amd routes every Triton symbol through one indirection module.

全程不报错。 你只是在跑一个并非为你的平台构建的 Triton。 解法是等其它都装完后卸掉 triton 再重装 triton-rocm==3.6.0。 而 Gluon gfx950 那批核函数对此免疫， 原因是一个值得偷师的设计： tokenspeed-kernel-amd 把所有 Triton 符号都收敛到一个间接层。

# tokenspeed_kernel_amd/_triton.py
import tokenspeed_triton as triton
import tokenspeed_triton.experimental.gluon.language as gl
from tokenspeed_triton.experimental.gluon.language.amd.cdna4 import (
    async_copy as cdna4_async_copy,
)

Because tokenspeed_triton is a distinct top-level module name (version 3.8.10), it can never collide with whatever occupies triton/. Vendoring a compiler under its own namespace costs one file and buys immunity from every dependency resolver that will ever run against this environment.

因为 tokenspeed_triton 是一个独立的顶层模块名（版本 3.8.10）， 它永远不会跟占据 triton/ 的东西撞车。 把一个编译器 vendor 到自己的命名空间下， 代价是一个文件， 换来的是对将来任何一次依赖求解的免疫。

2.3 · The documented AMD recipe OOMs on boot2.3 · 文档里的 AMD recipe 一启动就 OOM

Following docs/recipes/models.md exactly, the server loads all 96 shards, captures decode graphs, and dies at 751 seconds. Prefill graph capture is what kills it, and the log lets you watch the memory drain bucket by bucket:

严格按 docs/recipes/models.md 来， 服务会加载完全部 96 个 shard、 捕获完 decode graph， 然后在第 751 秒死掉。 凶手是 prefill graph 捕获， 日志里能一个 bucket 一个 bucket 看着显存被抽干：

Capturing prefill buckets (bucket=2048 avail_mem=19.92 GB):   2%
Capturing prefill buckets (bucket=1024 avail_mem=14.64 GB):  22%
Capturing prefill buckets (bucket= 704 avail_mem= 4.65 GB):  35%
Capturing prefill buckets (bucket= 512 avail_mem= 0.03 GB):  42%
[FATAL ERROR]: HIP failure: 'out of memory'

After weights and the KV pool there are roughly 20 GB left per GPU, and capturing all 40 prefill buckets needs more. Add --disable-prefill-graph, which TokenSpeed's own MI35x CI perf config already passes — the docs recipe simply omits it.

权重和 KV pool 占完之后每张卡只剩约 20 GB， 而捕获全部 40 个 prefill bucket 需要的比这多。 加 --disable-prefill-graph 即可—— TokenSpeed 自己的 MI35x CI perf 配置本来就带这个 flag， 只是文档 recipe 漏了。

2.4 · It cannot share a Python environment with SGLang2.4 · 它没法跟 SGLang 共用一个 Python 环境

TokenSpeed hard-pins torch==2.11.0 and transformers==5.12.0; the container runs a custom torch 2.9.1+rocm7.2.0 that SGLang depends on. There is no reconciling those, so TokenSpeed goes in its own venv with its own 6.2 GB torch wheel. On a shared benchmarking box this is not a detail — it means the two engines can never be A/B'd inside one process image, and every comparison is across environments by construction.

TokenSpeed 硬钉 torch==2.11.0 和 transformers==5.12.0； 而容器里跑的是 SGLang 依赖的定制 torch 2.9.1+rocm7.2.0。 这两者没有调和余地， 所以 TokenSpeed 只能进自己的 venv， 带自己那个 6.2 GB 的 torch wheel。 在一台共享的 benchmark 机器上这不是细节—— 它意味着两个引擎永远无法在同一个进程镜像里做 A/B， 所有对比在构造上就是跨环境的。

With those handled the server boots in about 11 minutes, almost all of it reading 1.5 TB of weights, and reports max_total_num_tokens=4466304.

这些处理掉之后， 服务大约 11 分钟启动完成， 时间几乎全花在读 1.5 TB 权重上， 并报告 max_total_num_tokens=4466304。

The wedge at 8K × 1288K × 128 上的卡死

This is the workload SGLang was tuned around on this box: 890 tok/s output, 8,012 tok/s total, at concurrency 128 with 8 K prompts. TokenSpeed completed 1 of 128 requests in an hour. The distinction that matters is that it did not degrade — it wedged.

这正是 SGLang 在这台机器上重点调优的负载： 并发 128、 8 K 提示词下输出 890 tok/s、 总吞吐 8,012 tok/s。 TokenSpeed 一小时内只完成了 128 个请求中的 1 个。 关键区别在于它不是变慢， 而是卡死。

Plate II · FlatKV page pool under 128 × 9,216-token requests 图版 II · 128 个 9,216-token 请求下的 FlatKV 页池 live

The scheduler advertises one capacity and enforces another. The engine reports max_total_num_tokens=3556992; the scheduler's own config says 3,298 device pages at block size 128, shared across four cache groups because 69 of 93 layers are KDA and each needs its own paged recurrent state.

调度器对外宣称的容量和它实际执行的容量不是一个。 引擎报告 max_total_num_tokens=3556992； 而调度器自己的配置写的是 3,298 个 device page、 block size 128， 并且要被四个 cache group 共享—— 因为 93 层里有 69 层是 KDA， 每层都要自己的 paged recurrent state。

Overcommitting a pool is normal; every engine does it and resolves it by queueing. What makes this a wedge rather than a queue is that the retraction path is itself blocked — the scheduler frees a request to make room, admits one, and immediately needs to free again, so it converges to admitting a single request at a time while decode falls to 0.02 tok/s. A queue degrades linearly with load. This degrades to a standstill, which is a different failure and needs a different fix: admission control that refuses work it cannot hold, rather than eviction that fights itself.

超订一个池子是正常的， 每个引擎都会， 然后靠排队化解。 让这件事从「排队」变成「卡死」的， 是回收路径本身也被堵住了—— 调度器释放一个请求腾出空间、 放进来一个、 然后立刻又需要释放， 于是收敛到一次只接纳一个请求， 解码掉到 0.02 tok/s。 排队是随负载线性劣化， 而这是劣化到停滞， 属于另一类失败， 需要另一类修法： 用「拒绝装不下的请求」的准入控制， 而不是自己跟自己打架的驱逐。

One thing that is not a limit: the --max-model-len 8192 in the documented AMD recipe. Raising it to 16384 boots cleanly and reports max_req_input_len=16383, so the 8 K-in / 1 K-out shape itself fits. The wedge is about concurrency, not context.

有一点不是限制： 文档 AMD recipe 里的 --max-model-len 8192。 改成 16384 能正常启动并报告 max_req_input_len=16383， 所以 8 K 进 / 1 K 出这个形状本身装得下。 卡死是并发问题， 不是上下文问题。

05

How the traces were takentrace 是怎么抓的

A kernel comparison is only worth as much as its methodology, so here is the whole of it. Both sides: batch 1, ISL 4096, TP8, no speculative decoding, graph off, device-kernel duration summed per decode step, collectives excluded.

一个核函数对比的价值完全取决于它的方法学， 所以这里把方法学全部摊开。 两边都是： batch 1、 ISL 4096、 TP8、 无投机解码、 关 graph、 按 decode step 求和 device kernel 时长、 排除 collective。

Why graph off. Inside a replayed HIP graph the individual kernels are not separately attributable — you get one opaque replay. The SGLang baseline was captured graph-off for the same reason, so the two remain comparable. The cost is that eager wall-clock time is meaningless here; only the summed device time is.

为什么关 graph。 在一次被 replay 的 HIP graph 内部， 单个核函数无法单独归因—— 你只会得到一次不透明的 replay。 SGLang 那份 baseline 也正是出于同样原因用 graph-off 抓的， 所以两者保持可比。 代价是 eager 的墙钟时间在这里没有意义， 只有 device 时间的加总有意义。

Why collectives are excluded. In eager decode the all-reduce payload is a few kilobytes and the kernel busy-waits for its peers, so its recorded duration measures rank skew, not work. Leaving it in would have put 67.6 ms/step of pure waiting into a 17 ms compute budget. The SGLang baseline excluded it for the same reason. The dispatch count is still meaningful and is compared directly in §08.

为什么排除 collective。 在 eager 解码下 all-reduce 的 payload 只有几 KB， 核函数是在忙等其它 rank， 所以它记录的时长量的是 rank 之间的偏斜而不是工作量。 留着它会把 67.6 ms/step 的纯等待塞进一个 17 ms 的计算预算里。 SGLang 的 baseline 出于同样原因排除了它。 dispatch *次数*仍然有意义， 在 §08 里直接对比。

Proton does not attach on ROCm

TokenSpeed ships Proton, its semantic kernel profiler, and the guide recommends it. On ROCm it calls rocprofiler_force_configure, which must run before HIP initialises, so attaching it to a live server fails with error 16 on every rank. The torch/roctracer profiler attaches fine at runtime — and conveniently produces the same chrome-trace artifact the SGLang baseline used, which makes the two directly comparable rather than merely similar.

TokenSpeed 自带语义级核函数 profiler Proton， 官方指南也推荐用它。 但在 ROCm 上它会调 rocprofiler_force_configure， 而这个调用必须发生在 HIP 初始化之前， 所以挂到运行中的服务上会在每个 rank 上以 error 16 失败。 torch / roctracer 那条路可以正常运行时挂载—— 而且顺带的好处是， 它产出的 chrome trace 跟 SGLang baseline 是同一种产物， 于是两者是直接可比而不只是相似。

How kernels were attributed. By the source module that launches them, not by name matching. Name matching is actively wrong here: iris_stage_one_shot_allreduce_two_gluon_kernel contains "gluon" but is a collective, and _stage1_a16w4_situ_warp_gemv contains "stage1" but is MoE, not attention. Every kernel was traced to its defining file.

核函数是怎么归因的。 按发起它的源码模块归因， 不按名字匹配。 名字匹配在这里是实打实错的： iris_stage_one_shot_allreduce_two_gluon_kernel 名字里有 "gluon" 但它是个 collective； _stage1_a16w4_situ_warp_gemv 名字里有 "stage1" 但它属于 MoE 而不是 attention。 每个核函数都追到了定义它的文件。

One kernel genuinely spans blocks. _kimi3_projection_gemv_kernel backs four call sites in every MoE layer — the two latent H↔L projections, the shared-expert down projection and the router — plus kimi3_qkvfab_projection inside KimiLinearKDA. That predicts 4 × 92 + 69 = 437 dispatches per step, and the trace measured exactly 437. Getting the predicted dispatch count to match the measured one to the unit is the check that the attribution is right; its time is then split by dispatch share. The 93-dispatch vendor GEMM is the attention output projection, issued once per layer, split 69/24 between the two attention types — the same structure SGLang's own study found, where exactly one compute kernel is shared between KDA and MLA.

确实有一个核函数跨 block。 _kimi3_projection_gemv_kernel 支撑每个 MoE 层里的四个调用点—— 两个 latent H↔L projection、 shared expert 的 down projection、 以及 router—— 外加 KimiLinearKDA 里的 kimi3_qkvfab_projection。 这预测出每 step 有 4 × 92 + 69 = 437 次 dispatch， 而 trace 实测正好 437。 预测的 dispatch 数与实测数精确到个位对上， 就是归因正确的校验； 它的时间随后按 dispatch 占比拆分。 那个 93 次 dispatch 的 vendor GEMM 是每层一次的 attention 输出投影， 按 69 / 24 拆给两种注意力—— 这跟 SGLang 自己的研究发现的结构一致： 恰好有一个计算核函数被 KDA 和 MLA 共享。

7.1 · Gluon MLA decode — 2.77x, and the cleanest win7.1 · Gluon MLA decode—— 2.77 倍， 最干净的一场胜利

SGLang runs MLA decode as a two-stage split-KV Triton attention: _fwd_grouped_kernel_stage1 scans the KV cache in splits, _fwd_kernel_stage2 reduces them. That costs 50.5 µs per layer. TokenSpeed's _mla_decode_gluon plus its softmax/reduce-V companion does the same work in 18.3 µs per layer.

SGLang 把 MLA decode 做成两阶段的 split-KV Triton attention： _fwd_grouped_kernel_stage1 分片扫 KV cache， _fwd_kernel_stage2 做归约。 每层 50.5 µs。 TokenSpeed 的 _mla_decode_gluon 加它的 softmax / reduce-V 伙伴， 同样的活每层 18.3 µs。

Why the gap is real and not a tuning artifact: at batch 1 with a 4 K context, decode attention has an arithmetic intensity near one — it is a pure streaming read of the KV cache, and the only thing that matters is how close to peak bandwidth the load instructions get. A split-K template must choose its split count without knowing the access pattern, materialise partial results, and reduce them in a second pass over memory. A kernel written against one architecture can size its tiles to the cache line and the LDS budget and skip the second pass. That is a structural advantage of hand-writing for a fixed target, and it is exactly the regime where it pays.

为什么这个差距是真实的而不是调参产物： 在 batch 1、 4 K 上下文下， decode attention 的算术强度接近 1—— 它就是对 KV cache 的一次纯流式读取， 唯一重要的是 load 指令能跑到峰值带宽的多少。 一个 split-K 模板必须在不知道访问模式的情况下选定分片数、 把部分结果物化出来、 再用第二趟遍历内存去归约。 而一个针对单一架构写的核函数可以把 tile 尺寸对齐到 cache line 和 LDS 预算， 并且省掉第二趟。 这是「为固定目标手写」的结构性优势， 而这里正是它最划算的场景。

7.2 · The router — 6.51x, and the largest prize on the board7.2 · Router—— 6.51 倍， 桌上最大的一笔

Selecting top-16 of 896 experts and ordering tokens for the grouped GEMM costs SGLang 2.96 ms per decode step, spread across a pipeline of AITER kernels: grouped_topk, opus_moe_sorting in several phases, fused_mx_quant_moe_sort, moe_reduction. TokenSpeed does it in one _kimi3_sigmoid_bias_topk_kernel for 0.45 ms.

从 896 个 expert 里选 top-16 并为 grouped GEMM 排好 token 顺序， SGLang 要花 2.96 ms/step， 摊在一串 AITER 核函数上： grouped_topk、 分多个 phase 的 opus_moe_sorting、 fused_mx_quant_moe_sort、 moe_reduction。 TokenSpeed 用一个 _kimi3_sigmoid_bias_topk_kernel 花 0.45 ms 做完。

Plate V · Routing 896 experts: pipeline vs one pass 图版 V · 给 896 个 expert 做路由： 流水线 vs 一趟 per layer × 92

With 896 experts the routing metadata is large enough that writing it out and reading it back between kernels costs more than computing it. Fusing sigmoid, bias and top-k into one pass deletes those round trips.

在 896 个 expert 的规模下， routing 元数据已经大到「在核函数之间写出去再读回来」比「把它算出来」更贵。 把 sigmoid、 bias 和 top-k 融进一趟就把这些往返删掉了。

That single kernel is worth 2.5 ms per decode step, which is more than the entire end-to-end deficit TokenSpeed carries. Nothing about it is AMD-specific or Gluon-specific: it is the observation that when intermediate state is proportional to a large constant — here 896 — the cost of materialising it dominates the cost of producing it, so the boundary between kernels should not fall there. Delete the proper nouns and the idea still stands.

单这一个核函数就值 2.5 ms/step， 比 TokenSpeed 背着的整个端到端赤字还大。 它跟 AMD 无关， 跟 Gluon 也无关： 它讲的是， 当中间状态正比于一个很大的常数时—— 这里是 896—— 把它物化出来的成本会压过产生它的成本， 所以核函数的边界不该切在那里。 把专有名词删掉， 这个道理照样成立。

7.3 · Where AITER wins, and why the row is confounded7.3 · AITER 赢在哪里， 以及这一行为什么被污染

SGLang's mfma_moe1/mfma_moe2 MXFP4 kernels run the routed experts in 1.44 ms against 2.39 ms for TokenSpeed's Gluon _stage1_a16w4_situ_warp_gemv and _stage2_a16w4_warp_gemv_combine. Two caveats make this the weakest row in the table, and both should be stated rather than buried:

SGLang 的 mfma_moe1 / mfma_moe2 MXFP4 核跑完 routed expert 用 1.44 ms， TokenSpeed 的 Gluon _stage1_a16w4_situ_warp_gemv 加 _stage2_a16w4_warp_gemv_combine 用 2.39 ms。 有两个前提让这成为表里最弱的一行， 都该讲清楚而不是藏起来：

  • Different parallelism, different shapes. TokenSpeed runs EP8, so each rank owns 112 whole experts and at batch 1 touches only the few its tokens route to. SGLang runs pure TP8, where every rank runs all 16 experts at one-eighth width. Those are not the same GEMM, so this compares two strategies as much as two kernels.
  • 并行方式不同， shape 就不同。 TokenSpeed 跑 EP8， 每个 rank 拥有 112 个完整 expert， batch 1 时只碰它的 token 路由到的那几个。 SGLang 跑纯 TP8， 每个 rank 都跑全部 16 个 expert， 但只做 1/8 的宽度。 这不是同一个 GEMM， 所以这既是在比两个核函数， 也是在比两种策略。
  • Different activation precision. AITER's path is a8w4 — 8-bit activations — against Gluon's a16w4. AITER is moving half the activation bytes, which at batch 1 is most of what the kernel does.
  • 激活精度不同。 AITER 那条路是 a8w4—— 8-bit 激活—— 而 Gluon 是 a16w4。 AITER 搬的激活字节数只有一半， 而在 batch 1 下这几乎就是这个核函数做的全部事情。

The honest reading is not "AITER's GEMM is better" but "8-bit activations plus TP sharding beat 16-bit activations plus EP sharding at batch 1 on this shape". That is a useful finding, and it points at quantising the activations rather than rewriting the kernel.

诚实的读法不是「AITER 的 GEMM 更好」， 而是「在 batch 1、 这个 shape 下， 8-bit 激活加 TP 切分胜过 16-bit 激活加 EP 切分」。 这仍然是个有用的结论， 而且它指向的是去量化激活， 而不是重写核函数。

7.4 · KDA is a wash, and both are Triton7.4 · KDA 打平， 而且两边都是 Triton

Despite the "native AMD KDA implementation" framing in the docs, TokenSpeed's batch-1 decode recurrence lives in ops/attention/triton/kda.py — a Triton kernel, like SGLang's. They land within 14% of each other, which is what you expect when two implementations of the same recurrence hit the same wall. That wall is occupancy: 69 layers of a fixed-size recurrent state update at batch 1 fills 48 of 256 compute units. No kernel language moves a number that is set by how much parallelism the math exposes. Only batching does, and batching is precisely what this engine currently cannot do well.

尽管文档里写的是「原生 AMD KDA 实现」， TokenSpeed 在 batch 1 解码时的递推其实在 ops/attention/triton/kda.py 里—— 一个 Triton 核， 和 SGLang 一样。 两者落在彼此 14% 以内， 这正是「同一个递推的两个实现撞上同一堵墙」时该有的样子。 那堵墙是 occupancy： batch 1 下 69 层固定大小的 recurrent state 更新只填满了 256 个 CU 里的 48 个。 一个由「数学本身暴露出多少并行度」决定的数字， 换什么核函数语言都推不动。 只有加大 batch 能推动， 而加大 batch 恰恰是这个引擎目前做不好的事。

Where the milliseconds go毫秒去哪了

Plate VI · Four measurements that only reconcile one way 图版 VI · 只有一种自洽解释的四个测量 bs 1 · ISL 4096

Two cheap hypotheses eliminated by measurement rather than argument. What remains is the host path: the scheduler, the Python execution plane, and however much collective latency is exposed rather than overlapped.

两个省事的假设是被测量而不是被论证排除的。 剩下的是主机侧路径： 调度器、 Python 执行平面， 以及有多少 collective 延迟是暴露出来而没被 overlap 掉的。

A per-step cost that does not amortise as the batch grows is the shape that fits all the evidence. At concurrency 1 it costs 14%. At concurrency 8 the same class of overhead costs 3.7x — because the GPU work per step grows with batch while a fixed host-side cost per step does not, so its share should shrink; when the measured gap widens instead, the host path is not keeping up with the step rate rather than paying a constant tax.

一个不随 batch 增大而摊薄的 per-step 成本， 是唯一能同时解释所有证据的形状。 并发 1 时它值 14%； 并发 8 时同一类开销值 3.7 倍—— 因为每 step 的 GPU 工作量会随 batch 增长， 而固定的主机侧每 step 成本不会， 所以它的占比本应缩小； 当实测差距反而扩大时， 说明主机侧路径是跟不上 step 速率， 而不是在交一笔固定的税。

This is also why the fix is not in the kernel directory. The kernels are, measurably, the better half of this engine on this hardware. What needs profiling is the gap between them — and that requires a host-side trace, which is the natural next experiment.

这也是为什么修复不在核函数目录里。 在这块硬件上， 这些核函数可测量地是这个引擎更强的那一半。 需要 profile 的是它们之间的空隙—— 而那需要一份主机侧的 trace， 这也是自然的下一个实验。
