The Decision Frame先定决策框架

The scarce resource is not a kernel idea. It is a problem whose first bad stage is known, whose owner is clear, and whose model-level metric can move.

真正稀缺的不是一个 kernel 想法， 而是这样的问题： 首个出错或变慢的 stage 已经明确， ownership 清楚， 而且 model-level 指标确实能被它推动。

Why not rank by theoretical speedup? Because serving is a chain. A faster GEMM changes nothing when prefix caching misses, decode is starved by prefill, or the framework never dispatches the new kernel. The radar therefore scores evidence and integration path, not marketing headroom.

为什么不按理论 speedup 排名？ 因为 serving 是一条链。 当 prefix cache 没命中、decode 被 prefill 饿死、或者 framework 根本没有 dispatch 新 kernel 时， 更快的 GEMM 不会改变任何东西。 因此这份雷达优先看证据和集成路径， 而不是宣传口径里的 headroom。

Cross-repo Routes跨仓库落地路径

A good issue has a route to production. These three routes cover most of the selected work.

一个好 issue 必须有通向 production 的路径。 下面三条路径覆盖了大多数候选。

MLA / Attention

  1. Capture the production geometry and first bad stage in AITER.
  2. Implement and resource-gate the kernel in FlyDSL / ASM / Gluon.
  3. Wire actual dispatch in SGLang or vLLM.
  4. Close on TPOT, TTFT, long-context accuracy, and graph replay.
  1. 先在 AITER 固定 production geometry 和首个坏 stage。
  2. 用 FlyDSL / ASM / Gluon 实现， 并检查资源预算。
  3. 在 SGLang 或 vLLM 接入真实 dispatch。
  4. 最后用 TPOT、TTFT、长上下文准确率和 graph replay 收口。

MoE / GEMM

  1. Weight shapes by the model's real token and expert histogram.
  2. Gate small-M latency and large-M MFU separately.
  3. Preserve weight layout, config key, and graph-safe semantics through AITER.
  4. Verify throughput across concurrency, not one operator cell.
  1. 按模型真实 token 和 expert histogram 给 shape 加权。
  2. 分别检查小 M latency 与大 M MFU。
  3. 通过 AITER 保持 weight layout、config key 和 graph-safe 语义。
  4. 在多并发下验证 throughput， 而不是只看一个 operator cell。

Serving / Cache

  1. Separate scheduling, cache hit rate, communication, and kernels.
  2. Do not optimize a kernel while decode is starved or prefixes miss.
  3. Use fixed traffic and counter-ordered A/B.
  4. Report P50 and tail latency together with correctness.
  1. 把 scheduling、cache hit、communication 和 kernel 分开。
  2. 当 decode 被饿死或 prefix miss 时， 不要先优化 kernel。
  3. 使用固定流量和 counter-ordered A/B。
  4. 同时报告 P50、tail latency 和正确性。

Method and Limits方法与边界

Scope

Open issues mentioning the target models, ROCm / AMD, kernel families, or measurable inference performance. Parser-only and generic support requests were excluded.

筛选目标模型、ROCm / AMD、kernel family 或可测量 inference performance 相关的 open issue。 纯 parser 和泛化 support request 不进入主表。

Priority

P0 is a correctness or production blocker. P1 is an attributable performance opportunity. P2 is enabling infrastructure or evidence that should shape other work.

P0 是 correctness 或 production blocker； P1 是可归因的性能机会； P2 是基础设施或会改变其他工作的证据。

FlyDSL fit

Direct means the issue lives in FlyDSL. High means a FlyDSL kernel is a natural implementation. Medium means it is a useful alternative or cross-check. Low means the bottleneck is mainly framework-level.

Direct 表示问题就在 FlyDSL； High 表示 FlyDSL kernel 是自然实现； Medium 表示它适合作为替代或交叉验证； Low 表示主要瓶颈在 framework。
