GLM-5.3 on MI355X: the kernel was fast, the score was not

A decode monokernel cut GLM-5.3's inter-token latency by 28–30% on MI355X, and the InferenceX AgentX score did not move. The cost sat in prefill: the kernel accepted only a BF16 KV cache, and BF16 KV doubled the time of one DSA prefill kernel. Letting the kernel read the recipe's own FP8 cache, an integration change with no kernel code, turned the same kernel into +15–19% throughput and +10–15% interactivity at concurrency 1–4 over InferenceX's 3600-s window, with GSM8K unchanged.

一个 decode monokernel 让 GLM-5.3 在 MI355X 上的 inter-token latency 降了 28–30%， InferenceX AgentX 的分数却没有动。 代价在 prefill： kernel 当时只接受 BF16 KV cache， 而 BF16 KV 让 DSA prefill 里一个 kernel 的时间翻了一倍。 让 kernel 直接读写配方本来的 FP8 cache 之后（只改集成层， 不改 kernel 代码）， 同一个 kernel 在 InferenceX 的 3600 秒窗口下， c1–c4 吞吐提升 15–19%， 交互性提升 10–15%， GSM8K 不变。

02The route路线

Five camps, each with a decision rule written before the run. The first attempt was a no-go. A profile found why. One integration PR removed the cause. A 900-s rerun was too noisy to decide, and the 3600-s rerun decided it.

五个营地， 每一站的判定规则都在开跑之前写好。 第一次是 no-go；profile 找到了原因；一个集成层的 PR 去掉了原因；900 秒的重跑噪声太大， 判不了；3600 秒的重跑给出了结论。

03What the score measures分数在量什么

AgentX replays recorded multi-turn agent sessions: long prompts that grow every turn and reuse their own prefix. Concurrency counts live sessions, not requests. InferenceX reports three headline numbers per point: total tokens per second per GPU, the P90 of E2E-normalized interactivity (one over the 90th percentile of E2EL / OSL, in tokens per second per user), and the P90 end-to-end latency.

AgentX 回放录下来的多轮 agent 会话： prompt 很长， 每一轮都在变长， 并且复用自己的前缀。 并发数指的是同时在跑的会话， 不是请求。 InferenceX 每个点报告三个头条数字： 每张 GPU 每秒处理的总 token 数；E2E 归一化交互性的 P90， 也就是 1 除以 E2EL / OSL 的 90 分位， 单位是每用户每秒 token；以及端到端延迟的 P90。

The second number decides how a decode kernel scores. A request's latency is its prefill plus one ITL per extra output token. Divided by the output length, a long reply is mostly ITL, but a short reply is mostly TTFT. The 90th percentile of that ratio is set by the short replies, so a kernel that only speeds up decode barely moves it, and any TTFT cost moves it the wrong way.

决定 decode kernel 得分的是第二个数。 一个请求的延迟等于 prefill 时间， 加上每多一个输出 token 的一次 ITL。 除以输出长度之后， 长回复的时间主要是 ITL， 短回复的时间主要是 TTFT。 这个比值的 90 分位由短回复决定。 所以只加速 decode 的 kernel 几乎推不动它， 而 TTFT 的任何代价都会把它往坏的方向推。

Why not judge by the median? The dashboard publishes the P90. A change that helps the median can still lose the score, which is exactly what cohort 1 did.

为什么不看中位数？榜单发布的是 P90。 一个改动可以让中位数变好、却让分数变差， cohort 1 正是这样。

04First attempt: a fast kernel, a flat score第一次： kernel 快了， 分数没动

The glm53 monokernel in sgl-amd-mono#7 replaces GLM-5.3's whole verify-step forward when one or two requests are running. It accepted only a BF16 KV cache. That matched SGLang's cookbook cells for GLM-5.3 on MI355X, which run BF16 KV, and #7 listed FP8 KV under "Not in this PR". The InferenceX recipe runs fp8_e4m3 KV, so the only candidate we could run was the recipe switched to BF16 KV, plus the kernel.

sgl-amd-mono#7 里的 glm53 monokernel 在同时运行 1 到 2 个请求时， 替换 GLM-5.3 整个 verify 步的 forward。 它当时只接受 BF16 KV cache。 这和 SGLang cookbook 里 GLM-5.3 在 MI355X 上的配置一致， 那些配置用 BF16 KV；#7 也把 FP8 KV 列在 "Not in this PR" 里。 InferenceX 的配方用 fp8_e4m3 KV， 所以我们能跑的候选只有一个： 把配方改成 BF16 KV， 再加上 kernel。

Cohort 1 ran 900-s windows in two rounds of opposite order. On matched requests, ITL fell −28% … −30% and per-request E2EL −17% … −23%, but TTFT rose +10% … +22%. The slowest tenth per output token moved +0.4% … +12.2%, so P90 interactivity did not improve, and the rule written before the run called it a no-go.

cohort 1 跑 900 秒窗口， 两轮顺序相反。 同一批请求上， ITL 变化 −28% … −30%， 单请求 E2EL 变化 −17% … −23%， 但 TTFT 变化 +10% … +22%。 按每个输出 token 最慢的 10% 请求变化 +0.4% … +12.2%， 所以 P90 交互性没有提升， 事先写好的规则判为 no-go。

Two diagnostic arms split the cause. b0 changes only the KV dtype and shows the TTFT cost without any kernel. b1 runs the kernel version that the image bundles and shows almost no gain, because that pin predates the kernel's own fixes.

两个诊断臂把原因拆开。 b0 只改 KV dtype， 不开 kernel， TTFT 的代价照样出现。 b1 用镜像自带的 kernel 版本， 几乎没有收益， 因为那个 pin 早于 kernel 自己的几次修复。

The extra time is one kernel. Everything else moves by 0.6 ms. By its grid, the grid-2080 launch is the DSA sparse attention of prefill: each new token gathers its 2048 selected KV rows, and a row is 1152 bytes in BF16 against 576 in FP8. 多出来的时间来自一个 kernel， 其余 kernel 合计只变了 0.6 ms。 按 grid 判断， grid 2080 的那次 launch 是 prefill 的 DSA 稀疏 attention： 每个新 token 收集它选中的 2048 行 KV， 一行在 BF16 下是 1152 字节， 在 FP8 下是 576 字节。 我们没有对照 kernel 源码核实这个判断。 仅凭字节数， 一个受 gather 限制的 kernel 就应该慢一倍， trace 里是 ×1.98。

Why not keep BF16 KV and speed up that kernel? It belongs to SGLang's DSA backend, outside the monokernel. The recipe already runs FP8 KV, and FP8 halves the bytes of every DSA read, not only this one.

为什么不保留 BF16 KV、去优化那个 kernel？它属于 SGLang 的 DSA 后端， 不在 monokernel 里。 配方本来就用 FP8 KV， 而且 FP8 让每一次 DSA 读取的字节数都减半， 不只是这一个。

06The fix: read the recipe's FP8 cache修复： 直接读写配方的 FP8 cache

The kernel already had an FP8 path. glm53 was written against the ATOM layout, whose FP8 KV rows hold E4M3 values without block scales. SGLang's HIP DSA backend stores exactly that: raw 576-byte E4M3 rows of 512 latent and 64 rope values, kept as uint8 and viewed as float8_e4m3fn. Both sides write the BF16-rounded value in E4M3, so no conversion or rescaling sits between them.

kernel 本来就有 FP8 路径。 glm53 是按 ATOM 的布局写的， 它的 FP8 KV 行存的是没有分块 scale 的 E4M3 值。 SGLang 在 HIP 上的 DSA 后端存的正是这种格式： 每行 576 字节的原始 E4M3， 512 个 latent 值加 64 个 rope 值， 用 uint8 存储， 以 float8_e4m3fn 读取。 两边写入的都是先舍入到 BF16、再转成 E4M3 的值， 中间不需要任何转换或重新缩放。

So sgl-amd-mono#60 changed only the integration: the spec accepts fp8_e4m3, the build picks the FP8 kernel variant, and the runtime binds SGLang's rows after checking their dtype and 576-wide stride. It merged as 0a107f1 on 2026-10-26.

所以 sgl-amd-mono#60 只改了集成层： spec 接受 fp8_e4m3， 构建时选 FP8 版本的 kernel， runtime 检查 dtype 和 576 宽的行步长之后， 绑定 SGLang 的 KV 行。 它在 2026-10-26 以 0a107f1 合并。

The e2e checks run SGLang and the kernel on the same steps and compare every layer's KV and stream outputs by cosine. A negative control proves the check can fail: swapping the E4M3 byte pairs of the latent drops the KV cosine to 0.095 and trips 1189 violations.

e2e check 让 SGLang 和 kernel 跑同样的步， 逐层比较 KV 和 stream 输出的 cosine。 负对照证明这个检查确实会失败： 把 latent 的 E4M3 字节两两对调之后， KV cosine 降到 0.095， 触发 1189 次违例。

Why not quantize inside the kernel with block scales, as other FP8 caches do? The cache belongs to SGLang. The kernel must read and write the exact rows that SGLang's own prefill and decode use, or the two paths drift apart step by step.

为什么不像其他 FP8 cache 那样， 在 kernel 里用分块 scale 自己量化？因为 cache 属于 SGLang。 kernel 必须读写 SGLang 自己的 prefill 和 decode 用的那些行， 否则两条路径会一步一步地分开。

07The score at 3600 s3600 秒的分数

Cohort 2 repeated the 900-s ladder with the fix. On matched requests ITL fell −21% … −28%, E2EL −17% … −25%, and TTFT stayed at −0.2% … −2.0%; the slowest tenth per token now moved −4.2% … −7.6%. Yet the A/A noise of P90 interactivity in a 900-s window was 20% (27% in cohort 1), and the second round at concurrency 2 fell inside it. The rule still said no-go. The window, not the kernel, was the limit.

cohort 2 用修复后的 kernel 重跑 900 秒的梯子。 同一批请求上 ITL 变化 −21% … −28%， E2EL 变化 −17% … −25%， TTFT 保持在 −0.2% … −2.0%；每 token 最慢的 10% 现在变化 −4.2% … −7.6%。 可是 900 秒窗口里 P90 交互性的 A/A 噪声有 20%（cohort 1 是 27%）， c2 的第二轮落在噪声内， 规则仍然判 no-go。 限制在窗口， 不在 kernel。

Cohort 3 used InferenceX's own 3600-s window at concurrency 1, 2, 4, and 10, a fresh server per point, and an A/A pair at concurrency 2. The A/A noise of P90 interactivity fell to 1.3%. All nine runs were valid: each profiling phase ran the full window, failures and drain cancellations stayed far below 10%, the validator passed, and the realized accept length was 2.990 against InferenceX's golden 2.99.

cohort 3 用 InferenceX 自己的 3600 秒窗口， 并发 1、2、4、10， 每个点都新起服务器， 并在 c2 做一组 A/A。 P90 交互性的 A/A 噪声降到 1.3%。 九个 run 全部有效： 每个 profiling 阶段都跑满窗口， 失败和排空取消都远低于 10%， validator 通过， 实现的接受长度是 2.990， InferenceX 的 golden 值是 2.99。

InferenceX's Check 14 recommends at least five Pareto-frontier points per curve (throughput against P90 E2EL). This four-point ladder has 3 frontier points without the monokernel and 2 with it, because AgentX's P90 E2EL is not monotone in concurrency: concurrency 4 has a lower P90 E2EL than 1 and 2 and a higher throughput, so it dominates them.

InferenceX 的 Check 14 建议每条曲线至少有 5 个 Pareto 前沿点（吞吐对 P90 E2EL）。 这个 4 点的梯子里， 不开 monokernel 有 3 个前沿点， 开了有 2 个。 原因是 AgentX 的 P90 E2EL 不随并发单调： c4 的 P90 E2EL 比 c1、c2 低， 吞吐又更高， 所以 c1、c2 被它支配。

  • Kernel coverage in the GSM8K runs: 100% of decode-batch lines at concurrency 2, 25% and 22% at concurrency 10. InferenceX runs its own eval at the highest concurrency of a group, where the kernel serves a quarter of the steps, so the concurrency-2 pair is the evidence for the kernel path.
  • GSM8K run 里 kernel 的覆盖： c2 是 100% 的 decode 日志行， c10 是 25% 和 22%。 InferenceX 在一组的最高并发跑自己的 eval， 那里 kernel 只接四分之一的步， 所以 kernel 路径的质量证据是 c2 这一对。

12Method and limits方法与限制

  • Local node, not InferenceX's cluster. The kernel commit was installed over the published image, so these runs are not the confirmation run on a shipped image.
  • 本地节点， 不是 InferenceX 的集群。 kernel 的提交是装在已发布镜像之上的， 所以这些 run 不算在发布镜像上的确认 run。
  • One 3600-s run per point; the A/A pair is at concurrency 2 only, and the other points assume the same noise.
  • 每个点只跑一次 3600 秒；A/A 只在 c2， 其他点按同样的噪声水平假定。
  • AgentX runs use InferenceX's synthetic acceptance at the golden accept length 2.99 in both arms; GSM8K runs use real acceptance.
  • AgentX run 在两组都用 InferenceX 的模拟接受， 接受长度取 golden 值 2.99；GSM8K run 用真实接受。
  • Every run held all 8 GPUs under a lock after a 30-sample idle check, with amd-smi samples every 10 s and a foreign-process check; every point used a fresh server and sent no generation before the timed phase.
  • 每个 run 都先做 30 次采样的空闲检查， 再锁住全部 8 张卡；每 10 秒用 amd-smi 采样一次， 并检查外来进程；每个点都新起服务器， 计时阶段之前不发任何生成请求。
  • Each cohort's decision rule was written before its runs. One amendment replaced a span check that does not fit AgentX with the phase-based validity check, before any verdict.
  • 每个 cohort 的判定规则都在开跑之前写好。 唯一的一次修订， 是在出任何结论之前， 把不适合 AgentX 的跨度检查换成按阶段的有效性检查。
  • Published rows are context only: different hardware, precision, deployment shape, and output-length distribution.
  • 已发布的结果只作背景： 硬件、精度、部署方式和输出长度分布都不同。

14Epilogue结语

A kernel can win the step it was built for and still lose the score. When the headline number does not move, look at what the kernel's preconditions force onto the rest of the pipeline. Here a dtype precondition taxed prefill, and the tail metric weighs prefill most. The fix was not a faster kernel but a precondition the rest of the system already met.

一个 kernel 可以赢下它负责的那一步， 却输掉分数。 头条数字不动的时候， 要看 kernel 的前提条件给流水线的其他部分带来了什么。 这里， 一个 dtype 前提给 prefill 加了税， 而尾部指标最看重 prefill。 修复不是更快的 kernel， 而是换成系统其他部分本来就满足的前提。

The second lesson is about windows. A P90 over 900 s of agent sessions moved 20% between identical runs; over 3600 s it moved 1.3%. Measure at the window the score is published at before calling a tail result.

第二个教训关于窗口。 900 秒的 agent 会话上， 两次完全相同的 run 之间 P90 能差 20%；3600 秒时只差 1.3%。 在对尾部结果下结论之前， 先用分数发布时的那个窗口来测。
