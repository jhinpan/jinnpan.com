02What the monokernel doesmonokernel 做了什么

On the normal path, SGLang runs a GLM-5.3 decode step layer by layer. For one request at TP8, a step launches 1,821 GPU kernels and takes 11.70 ms of GPU time.

在 normal path 上， SGLang 逐层运行 GLM-5.3 的一个 decode 步。 TP8、单请求时， 一步要发起 1,821 个 GPU kernel， GPU 时间是 11.70 ms。

The monokernel replaces each of the 75 MoE decoder layers (layers 3 to 77) with one persistent launch. Then the same step has 212 kernels and takes 5.59 ms (sgl-amd-mono#7, no MTP).

monokernel 把 75 个 MoE decoder 层（第 3 到 77 层）各换成一次常驻 launch。 这样同一步只有 212 个 kernel， 用时 5.59 ms（sgl-amd-mono#7， 不开 MTP）。

  • Coverage: at TP8 the monokernel runs steps of 8 rows or fewer. A step with fewer rows runs at the next width (2, 4, or 8) with pad rows. Larger steps use the normal path.
  • 覆盖范围： TP8 时， monokernel 运行 8 行以内的步。 行数不够时， 按下一档宽度（2、4 或 8）运行， 多出的是填充行。 更大的步走 normal path。
  • With MTP (3 draft steps), each request has 4 verify rows. Thus the monokernel serves verify steps of one or two requests.
  • 开 MTP（3 个 draft 步）时， 每个请求有 4 个 verify 行。 所以 monokernel 负责 1 到 2 个请求的 verify 步。
  • GLM-5.3 uses DeepSeek Sparse Attention. On an indexer layer, each row scores all keys of its context and keeps the top 2048. The other layers reuse that selection.
  • GLM-5.3 使用 DeepSeek 稀疏注意力。 在 indexer 层， 每一行给上下文中的所有 key 打分， 保留前 2048 个。 其他层复用这个选择结果。
  • The indexer stage grows with the context. AgentX contexts are long: the median input of a request is 89k to 285k tokens.
  • indexer 阶段随上下文变长而变慢。 AgentX 的上下文很长： 请求输入的中位数是 89k 到 285k token。

03How InferenceX scores AgentXInferenceX 怎样给 AgentX 打分

AgentX replays recorded multi-turn agent sessions. Each turn adds text to the prompt and reuses the cached prefix. Concurrency is the number of live sessions.

AgentX 回放录制的多轮 agent 会话。 每一轮都在 prompt 后面追加内容， 并复用已缓存的前缀。 并发数是同时在跑的会话数。

  • Throughput: total tokens per second per GPU.
  • 吞吐： 每张 GPU 每秒处理的总 token 数。
  • Interactivity: 1 / P90 of (E2EL / OSL), in tokens per second per user. This page uses "interactivity" for this metric.
  • 交互性： 1 / (E2EL / OSL) 的 P90， 单位是每用户每秒 token。 本页用“交互性”指这个指标。
  • P90 E2EL: the 90th percentile of the end-to-end latency.
  • P90 E2EL： 端到端延迟的 90 分位。

Interactivity is sensitive to TTFT. E2EL = TTFT + (OSL − 1) × ITL. For a short reply, most of E2EL is TTFT, and the P90 of E2EL / OSL comes from the short replies. Thus a faster decode helps interactivity only a little, and a longer TTFT makes it worse.

交互性对 TTFT 很敏感。 E2EL = TTFT + (OSL − 1) × ITL。 短回复的 E2EL 主要是 TTFT， 而 E2EL / OSL 的 P90 由短回复决定。 所以 decode 变快， 交互性只改善一点；TTFT 变长， 交互性就变差。

05Why long contexts were slow长上下文为什么慢

The PRs measured each stage with a debug build. At 256k keys and one row, the exact top-2048 selection took 207 µs on one CTA. The other CTAs of the launch waited for it. A launch without the indexer took about 54 µs at all contexts.

这些 PR 用 debug 版本测量了每个阶段。 256k key、1 行时， 精确的 top-2048 选择在一个 CTA 上要 207 µs。 这次 launch 的其他 CTA 都在等它。 不带 indexer 的 launch 在任何上下文下都约 54 µs。

  • #24 splits the selection of a row longer than 32768 keys over up to 16 CTAs. Each CTA builds a histogram of its chunks. One CTA finds the threshold. Each CTA then gathers its candidates. The result is still the exact top-2048.
  • #24 把超过 32768 个 key 的行分给最多 16 个 CTA 来选。 每个 CTA 给自己的分块建直方图。 一个 CTA 找出阈值。 然后每个 CTA 收集自己的候选。 结果仍然是精确的 top-2048。
  • #42 changes the score stage. Before, two waves read each key and added their results through LDS with two barriers. Each tile also waited for two memory round trips. Now one wave scores a group of 16 keys over all 32 heads, and the reads of the next groups are in flight.
  • #42 改了打分阶段。 原来每个 key 被两个 wave 读取， 两者再经过 LDS 和两次 barrier 相加。 每个 tile 还要等两次内存往返。 现在一个 wave 为全部 32 个 head 给一组 16 个 key 打分， 后面几组的读取提前发出。

At 256k keys and one row, the estimated step falls from 8.84 ms (#15) to 6.20 ms (#24) and 5.73 ms (#42). At four rows, it falls from 13.45 ms to 10.37 ms and 8.33 ms.

256k key、1 行时， 预估单步时间从 8.84 ms（#15）降到 6.20 ms（#24）， 再降到 5.73 ms（#42）。 4 行时， 从 13.45 ms 降到 10.37 ms， 再降到 8.33 ms。

07The baseline gap and #60对照组的差距与 #60

The InferenceX recipe uses an FP8 E4M3 KV cache. The PR campaign compared against a BF16 baseline. Thus its gains did not show what the monokernel adds to the real recipe.

InferenceX 的配方使用 FP8 E4M3 KV cache。 PR 开发期间的对照组用的是 BF16。 所以那些收益不能说明 monokernel 给正式配方带来了多少。

Test 1 compared the monokernel with all PRs up to #42 (BF16 KV) against the recipe (FP8 KV), at 900 s. On the same requests, ITL changed by −28% to −30%, but TTFT changed by +10% to +22%. Interactivity did not improve. The decision rule gave no-go.

测试 1 用包含 #42 及以前所有 PR 的 monokernel（BF16 KV）， 和配方（FP8 KV）比较， 窗口 900 秒。 在同一批请求上， ITL 变化 −28% 到 −30%， 但 TTFT 变化 +10% 到 +22%。 交互性没有改善， 判定规则给出 no-go。

BF16 KV alone causes the TTFT cost. Without the monokernel, BF16 KV changed TTFT by +11.6% at concurrency 1 and by +23.0% at concurrency 2.

TTFT 的代价来自 BF16 KV 本身。 不开 monokernel 时， BF16 KV 让 c1 的 TTFT 变化 +11.6%， c2 变化 +23.0%。

A prefill profile found the cause. With BF16 KV, one TileLang kernel of the DSA prefill takes ×1.98 its FP8 time, and TTFT increases by 22%. By its grid, this kernel is the sparse attention, which reads 1152 bytes per KV row in BF16 and 576 in FP8. We did not confirm the kernel identity in the source.

一次 prefill profile 找到了原因。 使用 BF16 KV 时， DSA prefill 里的一个 TileLang kernel 耗时是 FP8 下的 ×1.98， TTFT 增加 22%。 按 grid 判断， 这个 kernel 是稀疏 attention： BF16 下每行 KV 读 1152 字节， FP8 下读 576 字节。 我们没有在源码中确认这个 kernel 的身份。

sgl-amd-mono#60 let the monokernel use the FP8 cache of the recipe. The monokernel already had an FP8 path in the same format as SGLang: 576-byte E4M3 rows without block scales. #60 changed only the integration: the spec, the build, and the binding of the KV rows.

sgl-amd-mono#60 让 monokernel 使用配方的 FP8 cache。 monokernel 本来就有 FP8 路径， 格式和 SGLang 相同： 每行 576 字节的 E4M3， 没有分块 scale。 #60 只改了集成部分： spec、构建， 以及 KV 行的绑定。

17Lessons经验

  • Test a kernel PR at the context lengths of the target workload. #15 made a verify step 38.5% faster with 4096-token prompts. On AgentX, it made requests above 192k tokens slower.
  • 要用目标负载的上下文长度测试 kernel PR。 #15 在 4096 token 的 prompt 上让 verify 步快了 38.5%。 在 AgentX 上， 它却让 192k token 以上的请求变慢。
  • Compare ablation results in the same context bin. In the same workload, a 900-s window and a 3600-s window had different shares of long requests.
  • 要在同一个上下文长度段内比较 ablation 结果。 同一个负载， 900 秒窗口和 3600 秒窗口里长请求的占比不同。
  • Find the stage that grows with the workload. At long contexts, the indexer selection and score stages set the step time. #24 and #42 gave most of the gain.
  • 找出随负载增长的那个阶段。 长上下文下， indexer 的选择和打分阶段决定了单步时间。 #24 和 #42 带来了大部分收益。
  • Compare against the published recipe. The BF16 baseline of the PR campaign hid the TTFT cost of BF16 KV. #60 removed that cost.
  • 要和已发布的配方比较。 PR 开发期间的 BF16 对照组掩盖了 BF16 KV 的 TTFT 代价。 #60 去掉了这个代价。
  • Use the window of the score for P90 decisions. In 900 s, two identical runs differed by 20%. In 3600 s, they differed by 1.3%.
  • 判定 P90 时， 要用分数所用的窗口。 900 秒时， 两次相同的运行相差 20%。 3600 秒时， 只相差 1.3%。
