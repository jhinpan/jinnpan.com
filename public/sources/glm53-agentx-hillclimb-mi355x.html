GLM-5.3 on MI355X: the decode monokernel needs an FP8 KV cache to raise the AgentX score

GLM-5.3 在 MI355X 上的 decode monokernel 要配合 FP8 KV cache 才能提高 AgentX 分数

  • The glm53 decode monokernel reduced inter-token latency (ITL) by 28–30% on MI355X. But the InferenceX AgentX score did not improve.
  • glm53 decode monokernel 让 MI355X 上的 inter-token latency（ITL）降低 28–30%。 但 InferenceX AgentX 的分数没有提高。
  • Cause: the monokernel accepted only a BF16 KV cache. With BF16 KV, one DSA prefill kernel took 2.0× longer, and TTFT increased by 22%.
  • 原因： monokernel 当时只接受 BF16 KV cache。 使用 BF16 KV 时， DSA prefill 里的一个 kernel 耗时变为 2.0 倍， TTFT 增加 22%。
  • Fix: sgl-amd-mono#60 lets the monokernel use the FP8 KV cache of the recipe. The kernel code did not change.
  • 修复： sgl-amd-mono#60 让 monokernel 直接使用配方的 FP8 KV cache。 kernel 代码没有改动。
  • Result at 3600 s: throughput +15–19% and interactivity +10–15% at concurrency 1–4. GSM8K accuracy did not change.
  • 3600 秒窗口的结果： c1–c4 的吞吐提高 15–19%， 交互性提高 10–15%。 GSM8K 精度没有变化。
  • Status: the InferenceX submission waits for an SGLang pin update, a new image, and the cookbook PR.
  • 状态： 提交 InferenceX 之前， 还要等 SGLang 更新 pin、发布新镜像， 并合并 cookbook PR。

02Test sequence测试过程

The work had five steps. We wrote the decision rule of each test before the test started.

整个工作分五步。 每次测试的判定规则都在测试开始前写好。

03How InferenceX scores AgentXInferenceX 怎样给 AgentX 打分

AgentX replays recorded multi-turn agent sessions. The prompts are long. Each turn adds text to the prompt and reuses the cached prefix. Concurrency is the number of live sessions.

AgentX 回放录制的多轮 agent 会话。 prompt 很长。 每一轮都在 prompt 后面追加内容， 并复用已缓存的前缀。 并发数是同时在跑的会话数。

InferenceX reports three headline metrics at each concurrency:

InferenceX 在每个并发点报告三个头条指标：

  • Throughput: total tokens per second per GPU.
  • 吞吐： 每张 GPU 每秒处理的总 token 数。
  • Interactivity: 1 / P90 of (E2EL / OSL), in tokens per second per user. This page uses "interactivity" for this metric.
  • 交互性： 1 / (E2EL / OSL) 的 P90， 单位是每用户每秒 token。 本页用“交互性”指这个指标。
  • P90 E2EL: the 90th percentile of the end-to-end latency.
  • P90 E2EL： 端到端延迟的 90 分位。

Interactivity is sensitive to TTFT, for these reasons:

交互性对 TTFT 很敏感， 原因如下：

  1. E2EL = TTFT + (OSL − 1) × ITL.
  2. E2EL = TTFT + (OSL − 1) × ITL。
  3. For a long reply, most of E2EL is ITL. For a short reply, most of E2EL is TTFT.
  4. 长回复的 E2EL 主要是 ITL。 短回复的 E2EL 主要是 TTFT。
  5. The P90 of E2EL / OSL comes from the short replies.
  6. E2EL / OSL 的 P90 由短回复决定。
  7. Thus a faster decode changes interactivity only a little. A longer TTFT makes interactivity worse.
  8. 所以 decode 变快， 交互性只改善一点。 TTFT 变长， 交互性就变差。

We judge by the P90 metric, not the median, because InferenceX publishes the P90. In Test 1 the median improved, but the P90 did not.

我们按 P90 指标判断， 不看中位数， 因为 InferenceX 发布的是 P90。 测试 1 中， 中位数变好了， 但 P90 没有。

04Test 1: BF16 KV cache测试 1： BF16 KV cache

sgl-amd-mono#7 added the glm53 monokernel. The monokernel runs the verify step of GLM-5.3 when one or two requests are running. In #7, the monokernel accepted only a BF16 KV cache. The SGLang cookbook cells for GLM-5.3 on MI355X also use BF16 KV. #7 listed FP8 KV as out of scope.

sgl-amd-mono#7 加入了 glm53 monokernel。 同时运行 1 到 2 个请求时， monokernel 负责 GLM-5.3 的 verify 步。 在 #7 中， monokernel 只接受 BF16 KV cache。 SGLang cookbook 里 GLM-5.3 在 MI355X 上的配置也用 BF16 KV。 #7 把 FP8 KV 列为不在范围内。

The InferenceX recipe uses an FP8 E4M3 KV cache. Thus Test 1 changed the recipe to BF16 KV and added the monokernel.

InferenceX 的配方使用 FP8 E4M3 KV cache。 所以测试 1 把配方改成 BF16 KV， 再开启 monokernel。

Test 1 used 900-s windows. On the same requests, the monokernel changed ITL by −28% to −30% and E2EL by −17% to −23%. But TTFT changed by +10% to +22%.

测试 1 使用 900 秒窗口。 在同一批请求上， monokernel 让 ITL 变化 −28% 到 −30%， E2EL 变化 −17% 到 −23%。 但 TTFT 变化了 +10% 到 +22%。

For the slowest 10% of requests, E2EL per output token changed by +0.4% to +12.2%. Interactivity did not improve. The decision rule gave no-go.

对最慢的 10% 请求， 每个输出 token 的 E2EL 变化 +0.4% 到 +12.2%。 交互性没有改善。 判定规则给出 no-go。

Two extra groups isolated the cause:

另外两组用来找出原因：

  • b0 uses BF16 KV without the monokernel. TTFT also increased. Thus BF16 KV causes the TTFT increase.
  • b0 使用 BF16 KV， 不开 monokernel。 TTFT 同样变长。 所以 TTFT 变长是 BF16 KV 造成的。
  • b1 uses BF16 KV with the monokernel version in the image (05e0bb02). The gain was small. That version does not include sgl-amd-mono#24 and sgl-amd-mono#42.
  • b1 使用 BF16 KV 和镜像自带的 monokernel 版本（05e0bb02）。 收益很小。 这个版本不包含 sgl-amd-mono#24 和 sgl-amd-mono#42。

05Root cause根因

We profiled one prefill that is similar to an AgentX request. It has about 100k cached tokens and 2048 new tokens. We used TP8 and the GPU trace of rank 0. The base group uses FP8 E4M3 KV. The b0 group uses BF16 KV. Neither group uses the monokernel.

我们 profile 了一次和 AgentX 请求相似的 prefill。 它有约 10 万个已缓存 token 和 2048 个新 token。 我们用 TP8， 取 rank 0 的 GPU trace。 base 组使用 FP8 E4M3 KV， b0 组使用 BF16 KV。 两组都不开 monokernel。

One kernel causes the increase. The other kernels change by 0.6 ms in total.

变慢来自一个 kernel。 其他 kernel 合计只变化 0.6 ms。

The grid of this kernel (2080) matches the DSA sparse attention of prefill. We did not confirm this in the source code. For each new token, this kernel reads 2048 selected KV rows. A KV row has 576 bytes in FP8 and 1152 bytes in BF16. If the reads limit the kernel, BF16 doubles its time. The trace shows ×1.98.

这个 kernel 的 grid（2080）和 prefill 的 DSA 稀疏 attention 相符。 我们没有在源码中确认这一点。 对每个新 token， 这个 kernel 读取 2048 行选中的 KV。 一行 KV 在 FP8 下是 576 字节， 在 BF16 下是 1152 字节。 如果读取是瓶颈， BF16 会让它的时间翻倍。 trace 显示的是 ×1.98。

We did not keep BF16 KV and optimize this kernel, for three reasons. The kernel is part of the SGLang DSA backend, not the monokernel. The recipe already uses FP8 KV. FP8 also halves the bytes of all other DSA reads.

我们没有保留 BF16 KV 去优化这个 kernel， 原因有三点。 这个 kernel 属于 SGLang 的 DSA 后端， 不属于 monokernel。 配方本来就使用 FP8 KV。 FP8 还让其他所有 DSA 读取的字节数减半。

06Fix: use the FP8 KV cache修复： 使用 FP8 KV cache

The monokernel already had an FP8 path. It uses the ATOM layout, which stores FP8 KV as E4M3 values without block scales. The SGLang DSA backend on HIP uses the same format.

monokernel 本来就有 FP8 路径。 它使用 ATOM 布局， 用不带分块 scale 的 E4M3 值存储 FP8 KV。 SGLang 在 HIP 上的 DSA 后端使用同样的格式。

Each row has 576 bytes: 512 latent values and 64 rope values. SGLang stores the rows as uint8 and reads them as float8_e4m3fn. Both SGLang and the monokernel round a value to BF16 first and then convert it to E4M3.

每行 576 字节： 512 个 latent 值和 64 个 rope 值。 SGLang 用 uint8 存储这些行， 用 float8_e4m3fn 读取。 SGLang 和 monokernel 都先把值舍入到 BF16， 再转成 E4M3。

Thus sgl-amd-mono#60 changed only the integration code:

所以 sgl-amd-mono#60 只改了集成代码：

  • The spec accepts fp8_e4m3.
  • spec 接受 fp8_e4m3。
  • The build selects the FP8 version of the monokernel.
  • 构建时选择 FP8 版本的 monokernel。
  • The runtime checks the dtype and the 576-byte row stride. Then it binds the SGLang KV rows.
  • runtime 检查 dtype 和 576 字节的行步长， 然后绑定 SGLang 的 KV 行。

#60 merged as 0a107f1 on 2026-10-26. The kernel code did not change.

#60 于 2026-10-26 合并， 提交是 0a107f1。 kernel 代码没有改动。

The e2e checks run SGLang and the monokernel on the same steps. They compare the KV output and the stream output of each layer by cosine similarity.

e2e check 让 SGLang 和 monokernel 跑同样的步。 它们逐层比较 KV 输出和 stream 输出的 cosine 相似度。

A negative control shows that the checks can fail. We swap the E4M3 byte pairs of the latent. Then the minimum KV cosine is 0.095, and the check reports 1189 violations.

负对照证明这些检查能够失败。 我们交换 latent 中两两相邻的 E4M3 字节。 这时 KV cosine 的最小值是 0.095， 检查报告 1189 次违例。

The monokernel does not quantize the cache with its own block scales. Reason: SGLang owns the cache. The monokernel must use the same rows as the SGLang prefill and decode. Otherwise the two paths give different results.

monokernel 不用自己的分块 scale 量化 cache。 原因： cache 归 SGLang 管理。 monokernel 必须和 SGLang 的 prefill、decode 使用同样的行。 否则两条路径的结果会不同。

07Tests 2 and 3: FP8 KV cache测试 2 和 3： FP8 KV cache

Test 2 repeated the 900-s tests with #60. On the same requests, ITL changed by −21% to −28% and E2EL by −17% to −25%. TTFT changed by −0.2% to −2.0%. For the slowest 10% of requests, E2EL per output token changed by −4.2% to −7.6%.

测试 2 用 #60 重做 900 秒测试。 在同一批请求上， ITL 变化 −21% 到 −28%， E2EL 变化 −17% 到 −25%。 TTFT 变化 −0.2% 到 −2.0%。 对最慢的 10% 请求， 每个输出 token 的 E2EL 变化 −4.2% 到 −7.6%。

But in a 900-s window, the A/A noise of interactivity was 20% (27% in Test 1). The second run at concurrency 2 was inside this noise. Thus the decision rule gave no-go again. The 900-s window was too short to measure a P90 reliably.

但在 900 秒窗口中， 交互性的 A/A 噪声是 20%（测试 1 中是 27%）。 c2 的第二次运行落在噪声内。 所以判定规则又给出 no-go。 900 秒窗口太短， 不能可靠地测量 P90。

Test 3 used the 3600-s window of InferenceX at concurrency 1, 2, 4, and 10. Each point used a new server. An A/A pair at concurrency 2 measured the noise: 1.3% for interactivity.

测试 3 使用 InferenceX 的 3600 秒窗口， 并发为 1、2、4、10。 每个点都用新的服务器。 c2 的一组 A/A 测量噪声： 交互性的噪声是 1.3%。

All nine runs were valid:

九次运行全部有效：

  • Each run completed the full 3600-s window.
  • 每次运行都跑满 3600 秒。
  • Failed and cancelled requests were far below 10%.
  • 失败和取消的请求远低于 10%。
  • The InferenceX validator passed.
  • InferenceX 的 validator 通过。
  • The measured accept length was 2.990. The InferenceX target is 2.99.
  • 实测的接受长度是 2.990。 InferenceX 的目标值是 2.99。

InferenceX Check 14 recommends at least five Pareto-frontier points for each curve (throughput against P90 E2EL). Our four points give 3 frontier points without the monokernel and 2 with it.

InferenceX 的 Check 14 建议每条曲线至少有 5 个 Pareto 前沿点（吞吐对 P90 E2EL）。 我们的 4 个点里， 不开 monokernel 有 3 个前沿点， 开了有 2 个。

The reason: AgentX P90 E2EL does not increase with concurrency. At concurrency 4, P90 E2EL is lower than at 1 and 2, and throughput is higher. Thus concurrency 4 dominates concurrency 1 and 2.

原因： AgentX 的 P90 E2EL 不随并发单调增加。 c4 的 P90 E2EL 比 c1、c2 低， 吞吐又更高。 所以 c4 支配 c1 和 c2。

11Steps to an InferenceX submission提交 InferenceX 还需要的步骤

The kernel work is complete. These steps remain, in this order:

  2. SGLang 更新 pin。 SGLang main 把 sgl-amd-mono pin 在 05e0bb02。 它的 glm53 spec 只接受 BF16 KV。 现有的 PR sglang#45045 pin 的是 e952b221， 也比 #60 早。

12Method and limits方法和限制

  • We used one local node, not the InferenceX cluster.
  • 我们用的是一台本地节点， 不是 InferenceX 的集群。
  • We installed the monokernel commit over the published image. Thus these runs do not replace the confirmation run on a published image.
  • 我们把 monokernel 的提交装在已发布的镜像上。 所以这些运行不能代替在已发布镜像上的确认运行。
  • We ran each point one time for 3600 s. We measured the A/A noise only at concurrency 2. We assume the same noise at the other points.
  • 每个点只跑一次 3600 秒。 A/A 噪声只在 c2 测量。 我们假设其他点的噪声相同。
  • The AgentX runs use the synthetic acceptance of InferenceX (accept length 2.99) in both groups. The GSM8K runs use real acceptance.
  • AgentX 运行在两组中都使用 InferenceX 的模拟接受（接受长度 2.99）。 GSM8K 运行使用真实接受。
  • Before each run, we checked that all 8 GPUs were idle (30 samples) and locked them. During each run, we sampled amd-smi every 10 s and checked for other processes.
  • 每次运行前， 我们检查 8 张 GPU 都空闲（采样 30 次）， 然后锁定它们。 运行时每 10 秒用 amd-smi 采样一次， 并检查有没有其他进程。
  • Each point used a new server. No request was sent before the measured phase.
  • 每个点都用新的服务器。 测量阶段之前不发送任何请求。
  • We wrote the decision rule of each test before the test. We changed one rule one time, before any result. We replaced a span check that does not apply to AgentX with a phase-based validity check.
  • 每次测试的判定规则都在测试前写好。 我们只改过一次规则， 而且是在出结果之前。 我们把不适用于 AgentX 的跨度检查， 换成了按阶段的有效性检查。
  • The published results are for context only. The hardware, precision, deployment, and output lengths are different.
  • 已发布的结果只作背景。 硬件、精度、部署方式和输出长度都不同。

14Lessons经验

  • A kernel can make its own step faster and still not improve the score. Then examine the conditions that the kernel requires. Here the BF16 KV condition made prefill slower, and the P90 metric depends mostly on TTFT.
  • kernel 可以让自己负责的那一步变快， 但分数仍然不提高。 这时要检查 kernel 要求的条件。 这里， BF16 KV 这个条件让 prefill 变慢， 而 P90 指标主要取决于 TTFT。
  • The fix did not change the kernel. It let the kernel use the KV format that the recipe already uses.
  • 修复没有改 kernel， 而是让 kernel 使用配方本来就用的 KV 格式。
  • Measure a P90 metric with the window that the score uses. In 900-s windows, two identical runs differed by 20%. In 3600-s windows, they differed by 1.3%.
  • 测量 P90 指标时， 要用分数所用的窗口。 900 秒窗口中， 两次相同的运行相差 20%。 3600 秒窗口中， 只相差 1.3%。
