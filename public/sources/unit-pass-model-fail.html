§ 00 · The phenomenonPrologue

§ 00 · 现象序言

A kernel pull request usually arrives with two pieces of evidence: a green unit test and a speedup table. Both are real. Then the kernel ships inside a model, and one of three things happens. The model starts to answer in garbage. A multi-GPU run hangs with no error. Or nothing happens for a week, until one request takes a path nobody tried. People who maintain kernel libraries learn to say it in one line: it passed the unit test and failed in the model.

一个 kernel PR 通常带着两样证据： 一个通过的单测， 一张加速比表格。 两样都是真的。 然后这个 kernel 进入模型， 接下来会发生三种情况之一： 模型开始输出乱码； 多卡运行挂住， 不报任何错； 或者一周都相安无事， 直到某个请求走进一条没人试过的路径。 维护 kernel 库的人会把它总结成一句话： 单测过了， 跑模型出问题。

This is not one bug. It is a gap in what the test covers. A unit test checks a kernel at a handful of points: a few shapes, random inputs, one GPU, one stream, a fresh process. A model run is a distribution over a much larger space. The test proves correctness only at the points it checks, and a model spends almost all of its time somewhere else.

这不是某一个 bug， 而是测试覆盖范围上的缺口。 单测只在少数几个点上检查 kernel： 几个形状、 随机输入、 一张卡、 一个 stream、 一个新进程。 模型运行则是一个大得多的空间上的分布。 测试只能证明它检查过的点正确， 而模型几乎所有时间都在别处。

This guide does three things. It names the seven dimensions along which a test and a model differ. For each one, it explains the mechanism from first principles and shows it with bugs from public kernel repositories. Then it turns the seven gaps into a validation ladder: what to test, in what order, and what each rung catches that the rung below cannot.

这篇 guide 做三件事。 第一， 列出测试和模型不同的七个维度。 第二， 对每个维度从第一性原理解释机制， 并用公开 kernel 仓库里的真实 bug 说明。 第三， 把七个缺口变成一套验证阶梯： 测什么、 按什么顺序测、 每一级能抓到下一级抓不到的哪类问题。

The one-line version 一句话版本

A unit test pins every dimension it does not vary. Every pinned dimension is a place where production can differ, and a place where a bug can hide in plain sight.

单测会固定所有它没有改变的维度。 每一个被固定的维度， 都是生产环境可能不同的地方， 也是 bug 可以明目张胆藏起来的地方。

§ 01 · A test is a point, a model is a distributionThe gap

§ 01 · 测试是点， 模型是分布缺口在哪里

Start from what must be true of any kernel. Its output depends on more than the values of its arguments. It depends on the shape, which decides the code paths and tile tails that run; on the values, which decide the numeric regimes it hits; on the layout and dtype the caller hands over; on the execution context, such as graph capture, streams and caches; on timing, meaning which wave arrives first; on how many GPUs take part; and on the software and hardware it is built and run with. These are the seven dimensions.

先从任何 kernel 都成立的事实出发。 kernel 的输出不只取决于参数的值， 还取决于： 形状， 它决定哪些代码路径和 tile 尾块会执行； 数值， 它决定会碰到哪些数值区间； 调用方传进来的布局和 dtype； 执行环境， 例如 graph 捕获、 stream 和缓存； 时序， 也就是哪个 wave 先到； 参与的 GPU 数量； 以及编译和运行它的软件与硬件。 这就是七个维度。

A unit test is cheap because it pins most of them to convenient values: small tile-aligned shapes, torch.randn inputs, layouts produced by its own helper, eager mode on the default stream, one call, one GPU, the repository's own build. For a fast test, that is the right trade-off. The cost is that each pinned value hides a regime where the kernel's behavior changes. Plate I puts the two sides next to each other.

单测之所以便宜， 是因为它把大多数维度固定在方便的值上： 小的、 按 tile 对齐的形状， torch.randn 生成的输入， 测试自己的辅助函数生成的布局， 默认 stream 上的 eager 模式， 调用一次， 一张卡， 仓库自己的构建。 对快速测试来说， 这是正确的取舍。 代价是： 每个被固定的值都藏起了一个 kernel 行为会改变的区间。 图 I 把两边并排放在一起。

Why not test everything? Because the space is a product. Ten shapes times five value distributions times three layouts times four execution modes times three GPU counts is already 1,800 configurations, before timing is even considered, and timing is not a parameter you can set. Exhaustive testing is not the goal. The goal is to place test points where behavior changes: at boundaries, at the extremes of the data, at the contracts between kernels, and in modes only production uses.

为什么不全部测一遍？ 因为这个空间是乘积。 10 种形状 × 5 种数值分布 × 3 种布局 × 4 种执行模式 × 3 种 GPU 数量， 已经是 1,800 种配置， 这还没算时序， 而时序根本不是一个能设置的参数。 目标不是穷举， 而是把测试点放在行为会改变的地方： 边界、 数据的极端、 kernel 之间的契约， 以及只有生产环境才用的模式。

§ 02 · Gap ① · boundaries the test never reachesShapes and sizes

§ 02 · 缺口 ① · 测试碰不到的边界形状与尺寸

Why do shapes matter at all? Because a kernel is written for the common case and patched for the rest. It computes full tiles fast and handles the last partial tile, the tail, with masks or clamps. It computes addresses in 32-bit arithmetic, because 64-bit address math costs registers and instructions on every load. Both choices are correct inside a range. Outside it, they fail without an error.

形状为什么重要？ 因为 kernel 是为常见情况写的， 其余情况靠补丁。 它高速处理完整的 tile， 最后那个不完整的 tile， 也就是尾块， 用 mask 或 clamp 处理。 它用 32 位算术计算地址， 因为 64 位地址运算在每次读取时都要多花寄存器和指令。 这两个选择在一个范围内都是对的。 超出范围， 它们会出错， 而且不报错。

The 32-bit choice has two cliffs. A signed 32-bit index wraps at 2³¹. A 32-bit byte offset from a buffer's base wraps at 2³² bytes, which is 4 GiB. A test at typical sizes never comes near either. A model can cross both, and how far it goes depends on the deployment. In FlyDSL #879, the MoE stage-1 weight tensor of Kimi-K2.6 at tensor-parallel degree 1 is 385 × (2·2048) × 7168 × 0.5 bytes, about 5.3 GiB. The kernel addresses it through one buffer resource with a 32-bit offset, so experts past the 4 GiB mark read another expert's weights, and the model prints garbage. At TP 2 the same tensor is split to about 2.6 GiB, below the cliff. That is exactly why the bug only appears at TP 1. Plate II draws the cliff.

32 位的选择有两道悬崖。 有符号 32 位索引在 2³¹ 处回绕。 相对 buffer 起点的 32 位字节偏移在 2³² 字节， 也就是 4 GiB 处回绕。 典型尺寸的测试离两道悬崖都很远。 模型可以越过两道， 越过多少取决于部署方式。 在 FlyDSL #879 里， Kimi-K2.6 在张量并行度为 1 时， MoE 第一阶段的权重张量是 385 × (2·2048) × 7168 × 0.5 字节， 约 5.3 GiB。 kernel 用一个带 32 位偏移的 buffer resource 访问它， 于是 4 GiB 之后的 expert 读到了别的 expert 的权重， 模型输出乱码。 在 TP 2 时， 同一个张量被切成约 2.6 GiB， 落在悬崖之下。 这正是这个 bug 只在 TP 1 出现的原因。 图 II 画出了这道悬崖。

The quiet version is worse. In FlyDSL #1236, a tensor of shape (4, 2²⁹) has 2³¹ elements. Each dimension fits in int32, but the total size, computed in int32, wraps to a negative number. The layout code divides by that size, so every lane writes to the wrong position. The wrong positions are still inside the buffer, so hardware bounds checking never fires and nothing reports an error. FlyDSL #1020 hit the same wall from the other side: an FP8 attention path packed its flattened shape as int32 and failed with struct.error once batch × sequence × heads × head-dim reached 2³¹. At head-dim 128 and 64 heads, that is any sequence of 131,072 tokens or more.

安静的版本更糟。 在 FlyDSL #1236 里， 形状为 (4, 2²⁹) 的张量有 2³¹ 个元素。 每一维都放得进 int32， 但用 int32 计算的总大小回绕成了负数。 布局代码要除以这个大小， 于是每个 lane 都写到了错误的位置。 这些错误位置仍在 buffer 之内， 所以硬件越界检查从不触发， 也没有任何报错。 FlyDSL #1020 从另一侧撞上了同一堵墙： 一条 FP8 attention 路径把展平后的形状按 int32 打包， 当 batch × 序列长度 × head 数 × head 维度达到 2³¹ 时， 直接报 struct.error。 在 head 维度 128、 64 个 head 时， 任何 131,072 个 token 以上的序列都会触发。

Tails fail the same way. A refactor in FlyDSL #1131 passed its targeted tests and was merged. The full CI then failed on two FP16 tile shapes at M = 16 and M = 33, and the change was reverted in #1189 the next day. The tested points were simply not the points that broke.

尾块也是这样出错的。 FlyDSL #1131 的一次重构通过了针对性测试， 被合入。 随后完整 CI 在 M = 16 和 M = 33 的两个 FP16 tile 形状上失败， 第二天这个改动就在 #1189 里被回滚。 测过的点恰好不是出错的点。

Every tuned kernel library has a structural version of this gap. The library picks a config from a table keyed by shape. A shape without an entry falls back to a default or a heuristic config. Tests usually run the tuned shapes, because those are the ones someone measured. So the fallback config is often the least-tested code that production runs, and production runs it exactly for the shapes nobody planned for.

每个带调优表的 kernel 库都有这个缺口的结构性版本。 库按形状从表里选配置。 表里没有的形状， 会退回默认配置或启发式配置。 测试通常跑的是调优过的形状， 因为那些是有人测过的。 所以回退配置往往是生产环境在跑的代码里测得最少的一段， 而生产环境恰恰在没人计划过的形状上运行它。

Why not 64-bit everywhere? 为什么不全用 64 位？

It is the safe default, but it costs registers and instructions on the hottest loops, so kernels keep 32-bit offsets where they can prove the range. The fix proposed in #879 keeps the fast path: it rebases the buffer per expert with a 64-bit base, so each 32-bit offset stays inside one expert. The rule is not "never use 32 bits". The rule is "prove the range for the largest deployment, not for the test".

它是安全的默认选择， 但会在最热的循环里多花寄存器和指令， 所以 kernel 在能证明范围的地方保留 32 位偏移。 #879 提出的修复保留了快速路径： 用 64 位基址给每个 expert 单独设置 buffer， 让每个 32 位偏移都落在一个 expert 之内。 规则不是 「永远别用 32 位」， 而是 「按最大的部署证明范围， 而不是按测试」。

Test that catches it: one test per cliff, with tensors just below and just above 2³¹ elements and 2³² bytes; the largest single-GPU deployment of each model, not the sharded one; tails in every dimension; and an explicit list of production shapes that have no tuning entry.

能抓住它的测试： 每道悬崖一个测试， 张量刚好低于和刚好高于 2³¹ 个元素、 2³² 字节； 每个模型在单卡上的最大部署， 而不是切分后的部署； 每一维的尾块； 以及一份明确列出 「没有调优表项的生产形状」 的清单。

§ 03 · Gap ② · real numbers are not randomReal data

§ 03 · 缺口 ② · 真实的数不是随机的真实数据

A unit test draws inputs from torch.randn. Real activations and weights are not random. Router scores cluster, so two experts often score almost the same. Trained attention is peaked, so a few keys take most of the weight and thousands take almost none. Warmup traffic can be identical tokens, so every token routes to the same expert. Code that is exact for random inputs can fail on each of these.

单测从 torch.randn 里取输入。 真实的激活和权重不是随机的。 路由分数会扎堆， 所以两个 expert 经常得分几乎一样。 训练过的 attention 很尖锐， 少数几个 key 拿走大部分权重， 成千上万个 key 几乎为零。 预热流量可能全是相同的 token， 于是所有 token 都路由到同一个 expert。 对随机输入精确无误的代码， 在这几种情况下都可能出错。

FlyDSL #1213 is the cleanest example. The GLM-5 MonoKernel from #1204 passed its own tests and was merged. One day later, validation with real GLM checkpoints in the ATOM engine found several correctness gaps. The first: the kernel packed expert IDs into the router scores. Packing an ID into a score costs the score some precision. With random scores, near-ties almost never happen, so the packing never changed a winner. With real scores, two experts can be close enough that it does, and a captured TP8 routing replay picked expert 92 where expert 226 was correct. The fix keeps full FP32 scores and uses the expert ID only to break exact ties.

FlyDSL #1213 是最干净的例子。 #1204 的 GLM-5 MonoKernel 通过了自己的测试， 被合入。 一天之后， 在 ATOM 引擎里用真实的 GLM checkpoint 验证时， 发现了几处正确性问题。 第一处： kernel 把 expert ID 打包进了路由分数。 把 ID 塞进分数， 会让分数损失一些精度。 随机分数几乎不会出现接近的情况， 所以打包从没改变过赢家。 真实分数里， 两个 expert 可能接近到足以改变结果： 一次抓取的 TP8 路由回放里， 正确的是 expert 226， kernel 选了 expert 92。 修复保留完整的 FP32 分数， 只在分数完全相等时才用 expert ID 决定先后。

FlyDSL #1020 shows the numeric side. An FP8 attention kernel cast the softmax probabilities to e4m3 before the PV product. e4m3 bottoms out at 2⁻⁹, so with thousands of keys most probabilities underflow to zero, while the normalizer had been summed before the cast and still counted them. With V set to all ones the output should be exactly 1.0. The kernel returned 0.637. The PR says it plainly: only peaked attention shows this, and a random-init model will not.

FlyDSL #1020 展示了数值的一面。 一个 FP8 attention kernel 在做 PV 乘法之前， 把 softmax 概率转成了 e4m3。 e4m3 能表示的最小值是 2⁻⁹， 所以 key 有几千个时， 大部分概率下溢成 0； 而归一化因子是在转换之前求和的， 仍然把它们算在内。 V 全为 1 时， 输出应该正好是 1.0， kernel 返回 0.637。 PR 原文说得很直白： 只有尖锐的注意力会暴露这个问题， 随机初始化的模型不会。

aiter #6127 adds a twist: the data distribution can expose a timing bug. Identical warmup tokens sent every token to the same expert. That skewed the schedule enough for a lagging wave to read its tile index from an LDS slot that the next stage had already reused. That is a race, covered in § 06. Random routing would have hidden it.

aiter #6127 多了一层转折： 数据分布可以暴露时序 bug。 相同的预热 token 把所有 token 都送到同一个 expert， 调度因此严重倾斜， 一个落后的 wave 从一个已被下一阶段复用的 LDS 槽位里读出了自己的 tile 编号。 这是一个竞争， 留到 § 06 讲。 随机路由会把它藏起来。

Test that catches it 能抓住它的测试

Test with captured inputs. Record real activations, router scores and weights from one model run, and replay them against the reference. Add adversarial values on purpose: exact ties, near-ties, one-hot distributions, all tokens on one expert, extreme magnitudes.

用抓取的输入做测试。 从一次模型运行里录下真实的激活、 路由分数和权重， 拿它们对照参考实现回放。 再刻意加入对抗性的值： 完全相等、 几乎相等、 one-hot 分布、 所有 token 落在同一个 expert、 极端的量级。

§ 04 · Gap ③ · correct relative to what?Contracts

§ 04 · 缺口 ③ · 相对什么才算正确？接口契约

A kernel is not correct in isolation. It is correct relative to a contract: this layout, this dtype, these strides, this index width, these rows to skip. A model is a chain of kernels plus a framework, and every link in the chain is a contract between a producer and a consumer.

kernel 不是孤立地正确的。 它相对一份契约正确： 这种布局、 这种 dtype、 这些 stride、 这种索引宽度、 跳过这些行。 模型是一串 kernel 加一个框架， 链条上的每一环都是生产方和消费方之间的契约。

A unit test hides contracts by construction. The test's helper produces the input in the layout the kernel expects, and the reference reads it the same way, so producer and consumer always agree. In the model, the producer is a checkpoint loader, a previous kernel, or a framework that someone else wrote. Plate III shows the two chains.

单测在结构上就把契约藏起来了。 测试的辅助函数按 kernel 期望的布局生成输入， 参考实现也按同样的方式读取， 所以生产方和消费方永远一致。 在模型里， 生产方是 checkpoint 加载器、 上一个 kernel， 或者别人写的框架。 图 III 对比了这两条链。

#1213 again shows three seams at once. Real GLM checkpoints used a UV weight-scale layout the kernel did not support; the fix supports both the 64-row and the 128-row layouts and derives which one from the tensor shapes. The reference implementation followed the caller's default dtype, so a BF16 default silently changed the reference itself; the fix keeps the reference in FP32. And short contexts, such as the first decode steps of a new request, let the fused indexer select beyond the available context and left output slots uninitialized.

#1213 又一次同时展示了三处接缝。 真实的 GLM checkpoint 用了一种 kernel 不支持的 UV 权重 scale 布局； 修复同时支持 64 行和 128 行两种布局， 并从张量形状推断用哪一种。 参考实现跟随调用方的默认 dtype， 于是默认 dtype 一改成 BF16， 参考实现本身就悄悄变了； 修复把参考实现固定在 FP32。 还有很短的上下文， 例如新请求刚开始的几步 decode， 会让融合的 indexer 选到超出实际上下文的位置， 并留下未初始化的输出槽位。

Index width is a contract too. In FlyDSL #1234, an automated review of a decode MonoKernel pointed out that the kernel read several index buffers as raw int32 while checking only their element counts. PyTorch's default integer dtype is int64, so passing a default tensor would reinterpret half-words as row numbers and read arbitrary cache addresses. This is a review finding, not an observed failure, but it is the same seam.

索引宽度也是契约。 在 FlyDSL #1234 里， 一次对 decode MonoKernel 的自动评审指出： kernel 把几个索引 buffer 当作原始 int32 读取， 却只检查了元素个数。 PyTorch 默认的整数 dtype 是 int64， 传入一个默认张量， 就会把半个字当作行号， 读到任意的 cache 地址。 这是评审发现， 不是实际观察到的故障， 但它是同一条接缝。

Test that catches it 能抓住它的测试

Test the seams. For every kernel boundary, feed the consumer with the real producer: the checkpoint loader, the previous kernel, the framework's own buffers. Validate dtype, shape, stride and layout at the kernel entry instead of trusting the caller.

测接缝。 对每一个 kernel 边界， 用真实的生产方喂给消费方： checkpoint 加载器、 上一个 kernel、 框架自己的 buffer。 在 kernel 入口检查 dtype、 形状、 stride 和布局， 不要信任调用方。

§ 05 · Gap ④ · production does not call kernels like a test doesExecution context

§ 05 · 缺口 ④ · 生产环境调用 kernel 的方式和测试不一样执行环境

Inference engines record kernels into CUDA or HIP graphs and replay them. They run kernels on side streams. They keep one process alive for days and call the same kernel with hundreds of shapes. Each of these changes what the kernel and its host code must get right.

推理引擎会把 kernel 录进 CUDA 或 HIP graph 再回放。 它们在旁路 stream 上运行 kernel。 它们让一个进程活好几天， 用上百种形状调用同一个 kernel。 每一点都会改变 kernel 和它的 host 代码必须做对的事情。

Graph capture freezes host decisions. aiter #4494 is a split-K GEMM that coordinates its partial sums through a semaphore workspace. Under graph capture, the ownership of that workspace was wrong, and on replay the kernel spun forever. In the PR's words, the device wedges; it does not return a wrong number and it does not recover. Kimi-K3 at TP 8 hung during warmup as soon as the draft model was graphed, so the server never became ready. No eager test can see this, because eager mode re-runs the host code on every call. The fix changes only how the semaphore is allocated under capture; no kernel code changed.

graph 捕获会把 host 端的决定冻结下来。 aiter #4494 里的 split-K GEMM 通过一块 semaphore 工作区协调各部分的累加。 在 graph 捕获下， 这块工作区的归属是错的， 回放时 kernel 会一直空转。 用 PR 原文的话说： 设备卡死， 不返回错误的数字， 也不会恢复。 Kimi-K3 在 TP 8 下， draft 模型一进 graph 就在预热时挂住， 服务器永远无法就绪。 eager 测试看不到这个问题， 因为 eager 模式每次调用都会重新执行 host 代码。 修复只改了捕获时 semaphore 的分配方式， 没有改 kernel 代码。

Capture also breaks host code that is correct in eager mode. FlyDSL #171 fixed a segfault inside hipStreamEndCapture on PyTorch 2.9, while the same tests passed on 2.8. One of its three causes: exporting a tensor through DLPack during capture recorded stream synchronization events on the capture stream and corrupted the capture.

捕获还会弄坏在 eager 模式下正确的 host 代码。 FlyDSL #171 修复了 PyTorch 2.9 上 hipStreamEndCapture 里的段错误， 而同样的测试在 2.8 上能通过。 三个原因之一是： 捕获期间通过 DLPack 导出张量， 会在捕获 stream 上记录 stream 同步事件， 从而破坏捕获。

Long-lived processes stress caches. A JIT compiler caches compiled kernels by a key. If the key misses anything that changes the generated code, one shape gets another shape's kernel. FlyDSL issue #317 reported exactly that: a cached kernel reused for a different shape produced wrong outputs, and turning the cache off fixed them. aiter #6127 found the same pattern in a launcher whose cache key ignored the spec object, so different stage configs could share one compiled kernel. A test that calls one shape per process cannot see a cache collision.

长时间运行的进程会考验缓存。 JIT 编译器按一个 key 缓存编译好的 kernel。 如果 key 漏掉了任何会改变生成代码的因素， 一个形状就会拿到另一个形状的 kernel。 FlyDSL issue #317 报告的正是这种情况： 缓存的 kernel 被用到另一个形状上， 输出错误， 关掉缓存就恢复正常。 aiter #6127 在一个 launcher 里发现了同样的模式： 它的缓存 key 忽略了配置对象， 于是不同阶段的配置可能共用同一个编译结果。 每个进程只调用一种形状的测试， 看不到缓存冲突。

Test that catches it 能抓住它的测试

Run tests the way production runs kernels: capture and replay inside the test, use a non-default stream, and call several shapes in one process before you check the last one.

按生产环境运行 kernel 的方式跑测试： 在测试里捕获并回放， 使用非默认 stream， 在同一个进程里先调用几种形状， 再检查最后一次的结果。

§ 06 · Gap ⑤ · a test samples a probabilityRare races

§ 06 · 缺口 ⑤ · 测试只是在对概率抽样偶发竞争

A data race on a GPU depends on which wave arrives first. Most of the time the arrival order is benign, and the kernel passes. A missing barrier or fence can be harmless thousands or millions of times in a row. A test that calls the kernel once, or a hundred times, is sampling a probability. It is not proving correctness.

GPU 上的数据竞争取决于哪个 wave 先到。 大多数时候到达顺序是无害的， kernel 也就通过了。 少一个 barrier 或 fence， 可能连续成千上万次、 甚至上百万次都没事。 调用一次或一百次的测试， 只是在对一个概率抽样， 而不是在证明正确性。

aiter #4841 puts a number on it. A multi-block radix top-k used a cross-block barrier in which thread 0 signalled arrival while other waves in its block still had atomic histogram updates in flight; a block barrier does not wait for those. One candidate fix still left the race open, and a detector caught it 7 times in 292,889,600 row-launches, about once in 42 million. That rate would never show up in a unit test. The PR states the stakes: the race can permanently wedge the GPU in the GLM-5.2 indexer path and stall the whole DP-attention service, while the health endpoint keeps answering. The final fix completed 311,936,000 row-launches with no stuck event.

aiter #4841 给出了具体的数字。 一个多 block 的 radix top-k 用了跨 block 的 barrier： 线程 0 宣布到达时， 同一个 block 里的其他 wave 还有原子的直方图更新没有完成， 而 block barrier 不会等这些更新。 有一个候选修复仍然留着这个竞争， 检测器在 292,889,600 次行级调用里抓到 7 次， 大约四千两百万次一次。 这个频率在单测里永远看不到。 PR 写明了后果： 这个竞争可能让 GLM-5.2 的 indexer 路径永久卡死 GPU， 让整个 DP-attention 服务停住， 而健康检查接口还在正常应答。 最终的修复跑完了 311,936,000 次行级调用， 没有一次卡死。

The arithmetic is simple. If one call fails with probability p, then N independent calls see at least one failure with probability 1 − (1 − p)^N. With p ≈ 2.4 × 10⁻⁸, a test of 1,000 calls catches the race with probability 0.002%. A service doing 10,000 row-launches a second crosses 50% in about half an hour and certainty within a day. The model is not unlucky. It simply runs the test billions of times.

算术很简单。 如果单次调用出错的概率是 p， 那么 N 次独立调用至少出错一次的概率是 1 − (1 − p)^N。 当 p ≈ 2.4 × 10⁻⁸ 时， 1,000 次调用的测试抓到这个竞争的概率是 0.002%。 一个每秒做 10,000 次行级调用的服务， 大约半小时就超过 50%， 一天之内几乎必然出现。 不是模型运气差， 而是它把这个测试跑了几十亿遍。

Other public races follow the same shape. In aiter #6127, three block-broadcast values lived in an LDS slot that the next stage reused. Under skewed routing a lagging wave read the next stage's bytes as its tile index and faulted. Before the fix it failed within a few calls under that routing; after it, 150 back-to-back calls at four sizes ran clean. In FlyDSL #1235, two block reductions shared one LDS slot without a barrier between them, and the PR notes that a test cannot force the wave order that triggers the race, so the evidence is the code itself. In FlyDSL #1107, an automated review flagged a workgroup barrier that only half the waves execute: a deadlock waiting for the right schedule.

其他公开的竞争也是同一个形态。 在 aiter #6127 里， 三个 block 广播值放在一个会被下一阶段复用的 LDS 槽位里。 路由倾斜时， 一个落后的 wave 把下一阶段的字节当成自己的 tile 编号读出来， 随即出错。 修复前， 这种路由下几次调用之内就会出错； 修复后， 四种大小各连续跑 150 次都没有问题。 在 FlyDSL #1235 里， 两次 block 归约共用一个 LDS 槽位， 中间没有 barrier； PR 写明测试无法强制触发竞争所需的 wave 顺序， 所以证据只能是代码本身。 在 FlyDSL #1107 里， 自动评审指出一个只有一半 wave 会执行的 workgroup barrier： 这是一个在等待合适调度的死锁。

Test that catches it 能抓住它的测试

Turn probability into evidence. Call the same input many times and require bit-identical output. Run a synchronization sanitizer where one exists. Stress the kernel under concurrency with skewed inputs, such as every token on one expert.

把概率变成证据。 用同一个输入调用很多次， 要求输出逐位一致。 有同步 sanitizer 的地方就跑一遍。 在并发负载下用倾斜的输入给 kernel 加压， 例如所有 token 都落在同一个 expert。

§ 07 · Gap ⑥ · hangs, not wrong numbersMulti-GPU

§ 07 · 缺口 ⑥ · 挂起， 而不是算错多卡

A multi-GPU kernel adds states that do not exist on one GPU: two ranks arriving in different orders, a fast rank lapping a slow one, slots reused across calls of different sizes. When such a protocol is wrong, the usual symptom is not a wrong number. It is a hang: every rank waits for a signal that will never come. Hangs are expensive to debug and easy to mistake for infrastructure trouble.

多卡 kernel 带来了单卡上不存在的状态： 两个 rank 以不同顺序到达、 快的 rank 套圈慢的 rank、 不同大小的调用复用同一批槽位。 这类协议出错时， 常见症状不是算错， 而是挂起： 每个 rank 都在等一个永远不会来的信号。 挂起很难调试， 也很容易被误认为是基础设施的问题。

aiter #6446 is a textbook case. An all-reduce derived its bank offset and per-rank slot stride from the current message size. Consecutive calls alternate banks, but the banks stay disjoint only when both calls have the same size. A rank that has all its peers' data for call k moves on to call k+1 while a slower peer is still reading call k. With a different size, the call-(k+1) stores can land on the peer's unread slots, and the peer polls forever for a flag that has been overwritten. It surfaced in vLLM's CI as an RCCL watchdog timeout while serving Kimi-K3 at TP 2. A reviewer explained why the repository's own CI never saw it: multi-GPU CI ran the test file without its size argument, so it never reached the TP 2 and TP 4 cases that hang. Plate V shows the overwrite.

aiter #6446 是一个教科书式的例子。 一个 all-reduce 按当前消息大小计算 bank 偏移和每个 rank 的槽位步长。 相邻两次调用交替使用两个 bank， 但只有两次调用大小相同时， 两个 bank 才不会重叠。 一个 rank 收齐了第 k 次的全部数据， 就进入第 k+1 次， 而较慢的 rank 还在读第 k 次。 大小一变， 第 k+1 次的写入就可能落在慢 rank 还没读的槽位上， 慢 rank 于是一直轮询一个已被覆盖的标志。 它在 vLLM 的 CI 里以 RCCL watchdog 超时的形式出现， 当时在用 TP 2 跑 Kimi-K3。 一位评审者解释了仓库自己的 CI 为什么从没看到它： 多卡 CI 运行这个测试文件时没带大小参数， 所以永远走不到会挂起的 TP 2 和 TP 4 用例。 图 V 画出了这次覆盖。

FlyDSL #954 fixed multi-rank dispatch synchronization and completion handling in a fused MoE that could hang; the PR says the problems were found during review and serving tests, not by unit tests. In the same repository, the default test script excludes every multi_gpu test, as a review of FlyDSL #1277 noted. That is a reasonable cost trade-off, but it means a single-GPU green check says nothing about the protocol.

FlyDSL #954 修复了一个融合 MoE 里会导致挂起的多 rank dispatch 同步和完成处理问题； PR 写明这些问题是在评审和 serving 测试中发现的， 不是靠单测。 在同一个仓库里， 默认的测试脚本排除了所有 multi_gpu 测试， 这一点在 FlyDSL #1277 的评审中被指出。 这是合理的成本取舍， 但也意味着单卡的绿色结果对协议本身什么也说明不了。

Test that catches it 能抓住它的测试

Test protocols, not just math. Run TP 2 and TP 4, and EP where it applies, with message sizes that change between consecutive calls. Wrap every multi-GPU test in a watchdog, so a hang fails the test instead of the CI runner.

测协议， 而不只是测数学。 跑 TP 2 和 TP 4， 适用时也跑 EP， 并让相邻调用的消息大小不断变化。 给每个多卡测试套上看门狗， 让挂起变成测试失败， 而不是把 CI 机器拖死。

§ 08 · Gap ⑦ · production runs a different copyThe software you didn't test

§ 08 · 缺口 ⑦ · 生产环境跑的是另一份副本没测到的软件

In production, the model rarely runs your repository's kernel. It runs a downstream library's copy, pinned to some version, reached through an API your tests may not cover. So a change can keep your CI green and still break production.

在生产环境里， 模型很少直接运行你仓库里的 kernel。 它运行的是某个下游库里的副本， 锁定在某个版本上， 通过你的测试未必覆盖的 API 调用。 所以一个改动可以让你的 CI 保持全绿， 同时弄坏生产环境。

FlyDSL #1277 states the problem directly: a change under the compiler or expression layers "could break a kernel vLLM runs in production while CI here stayed green". Its sharpest example was a legacy allocator that nothing in the repository used anymore, but three vLLM decode kernels did. Deleting it per the deprecation plan would have failed no test in the repository. The PR's answer is a contract test that freezes the API surface downstream code imports.

FlyDSL #1277 把问题说得很直接： 编译器层或表达式层的一个改动， 「可能弄坏 vLLM 在生产环境运行的 kernel， 而这里的 CI 仍然全绿」。 它最尖锐的例子是一个旧的分配器： 仓库里已经没有任何代码使用它， 但 vLLM 的三个 decode kernel 在用。 按弃用计划删掉它， 仓库里不会有任何测试失败。 这个 PR 的办法是加一个契约测试， 冻结下游代码导入的 API。

Import-time coupling fails even earlier. In aiter #3683, importing the FlyDSL ops on an architecture that FlyDSL ships no kernels for crashed with a KeyError while registering configs, and that took down every flash-attention import on that GPU. A model failed to start because of a kernel it never meant to call.

导入阶段的耦合出错得更早。 在 aiter #3683 里， 在一个 FlyDSL 根本不提供 kernel 的架构上导入 FlyDSL 算子， 注册配置时直接抛出 KeyError， 连带这张卡上所有 flash-attention 的导入都失败了。 一个模型因为一个它根本不打算调用的 kernel 而启动不了。

Tests can also report success without running. aiter #5133 found that op tests were run as scripts, so 141 pytest test functions never executed; the files exited 0 having executed no test, and CI recorded that as a pass. FlyDSL #1020 found the runtime version of the same problem: an FP8 kernel never read a tuning flag, so the flag did nothing and every test of it passed trivially.

测试也可能没跑就报告成功。 aiter #5133 发现算子测试是以脚本方式运行的， 所以有 141 个 pytest 测试函数从未执行； 这些文件一个测试都没跑就以 0 退出， CI 把它记为通过。 FlyDSL #1020 发现了同一问题的运行时版本： 一个 FP8 kernel 从来没有读取某个调优开关， 所以这个开关什么也没做， 针对它的每个测试都毫无意义地通过了。

Test that catches it 能抓住它的测试

Test the copy the engine runs, at the version it pins. Add contract tests for every API a downstream project imports. Make the test runner fail when it collects nothing, and check that a flag under test changes the generated code.

测引擎实际运行的那份副本， 用它锁定的版本。 给下游项目导入的每个 API 加契约测试。 让测试框架在一个用例都没收集到时直接失败， 并确认被测的开关真的改变了生成的代码。

§ 09 · every gap at onceWhy a new architecture makes it worse

§ 09 · 所有缺口同时变大为什么新架构更严重

Every gap above exists on mature hardware. On a new GPU architecture, each one widens at the same time. None of this requires a new kind of bug. It only requires more of the seven gaps to be open at once.

上面每一个缺口在成熟的硬件上都存在。 到了一个新的 GPU 架构上， 它们会同时变大。 这不需要任何新类型的 bug， 只需要七个缺口里有更多个同时敞开。

  • New memory and synchronization mechanisms. Code ported from the previous generation carries assumptions about wave size, bounds checking and barrier semantics. They hold for common shapes and break at the edges, where tests rarely go. (Gaps ①, ⑤)
  • Young compilers. Code generation changes from release to release, so a result on one toolchain version does not carry over to the next. (Gap ⑦)
  • Sparse tuning tables. Few shapes have measured configs, so more production shapes take the fallback path. (Gap ①)
  • Few CI machines. Without the new hardware in CI, correctness rests on the author's own runs, on the author's toolchain. (Gaps ④, ⑦)
  • Larger single-GPU memory. A model that used to be split across GPUs now fits on one, so per-GPU tensors grow and cross the 32-bit cliffs. (Gap ①)
  • 新的内存和同步机制。 从上一代移植过来的代码， 带着对 wave 大小、 越界检查和 barrier 语义的假设。 这些假设对常见形状成立， 在边界上失效， 而测试很少走到边界。 （缺口 ①、 ⑤）
  • 年轻的编译器。 代码生成随版本变化， 在一个工具链版本上得到的结论， 换个版本就不一定成立。 （缺口 ⑦）
  • 稀疏的调优表。 测过配置的形状很少， 于是更多的生产形状走进回退路径。 （缺口 ①）
  • 很少的 CI 机器。 CI 里没有新硬件， 正确性只能靠作者自己在自己的工具链上跑。 （缺口 ④、 ⑦）
  • 更大的单卡显存。 以前要切到多张卡上的模型， 现在一张卡就放得下， 单卡上的张量变大， 越过 32 位悬崖。 （缺口 ①）

§ 10 · from cheap to completeA validation ladder

§ 10 · 从便宜到完整验证阶梯

The gaps suggest an order. Each rung catches a class of bugs the rung below cannot, and costs more to run. Climb it in order, and the end-to-end run at the top rarely fails. When it does fail, the rung that should have caught the bug tells you which test to add.

这些缺口给出了一个顺序。 每一级都能抓到下一级抓不到的一类 bug， 运行成本也更高。 按顺序往上爬， 顶端的端到端运行就很少出错。 万一出错， 本该抓住这个 bug 的那一级会告诉你该补哪个测试。

  1. Boundary unit tests (①). Tails in every dimension, M = 1, sizes just below and above 2³¹ elements and 2³² bytes, the largest unsharded deployment, and every production shape with no tuning entry. Put a guard page after the tensor, so an out-of-bounds read faults instead of silently reading a neighbour.
  2. Replay real inputs (②). Captured activations, router scores and weights from one model run, plus adversarial ties, peaks and extremes.
  3. Test the seams (③). Real producers feeding real consumers. Validate dtype, shape, stride and layout at the kernel entry.
  4. Production execution modes (④). Graph capture and replay, side streams, several shapes in one process.
  5. Repeat for determinism (⑤). The same input many times with bit-identical output, a sanitizer where available, skewed inputs under load.
  6. Multi-GPU protocols (⑥). TP 2, TP 4 and EP with changing message sizes, under a watchdog.
  7. Downstream (⑦). The copy and version the engine runs, API contract tests, and a test runner that fails when it collects no tests.
  8. The model, end to end. An accuracy evaluation with a fixed seed, such as GSM8K, and a throughput run, first on one GPU and then on several.
  1. 边界单测（①）。 每一维的尾块、 M = 1、 刚好低于和高于 2³¹ 个元素与 2³² 字节的大小、 不切分时的最大部署， 以及每一个没有调优表项的生产形状。 在张量后面放一页 guard page， 让越界读直接报错， 而不是悄悄读到相邻的数据。
  2. 回放真实输入（②）。 从一次模型运行里抓取的激活、 路由分数和权重， 再加上刻意构造的相等、 尖峰和极端值。
  3. 测接缝（③）。 用真实的生产方喂真实的消费方。 在 kernel 入口检查 dtype、 形状、 stride 和布局。
  4. 生产执行模式（④）。 graph 捕获与回放、 旁路 stream、 同一进程里的多种形状。
  5. 重复跑， 要求确定性（⑤）。 同一个输入跑很多次， 输出逐位一致； 有 sanitizer 就用上； 在负载下使用倾斜的输入。
  6. 多卡协议（⑥）。 TP 2、 TP 4 和 EP， 消息大小不断变化， 并套上看门狗。
  7. 下游（⑦）。 引擎实际运行的副本和版本、 API 契约测试， 以及一个没收集到用例就会失败的测试框架。
  8. 端到端模型。 固定随机种子的精度评测， 例如 GSM8K， 再加一次吞吐测试， 先单卡， 再多卡。
How I use it 我怎么用它

Before I call a kernel change done, I write down which rungs it has climbed. A green unit test is rung one. A speedup table is not a rung at all. If the kernel is not on any engine's call path yet, I say so, because then even a perfect end-to-end run says nothing about it.

在说一个 kernel 改动完成之前， 我会写下它爬到了哪几级。 一个通过的单测是第一级。 一张加速比表格根本不算一级。 如果这个 kernel 还不在任何引擎的调用路径上， 我会明确写出来， 因为那样的话， 就算端到端运行完美， 也说明不了它的任何问题。

§ 12 · not bad luckEpilogue

§ 12 · 不是运气不好尾声

"It passed the unit test and failed in the model" sounds like bad luck. It is not. A unit test is a sample, and a model is the population. Every public bug in this guide lived in a dimension the test held still: a size past a 32-bit cliff, a near-tie between two router scores, a layout written by a different loader, a graph replay, one race in forty million calls, a second GPU, a downstream copy. Name the dimension, and the missing test is usually obvious.

「单测过了， 跑模型出问题」 听起来像运气不好， 其实不是。 单测是样本， 模型是总体。 本文里的每一个公开 bug， 都待在测试固定不动的某个维度里： 越过 32 位悬崖的大小、 两个几乎相等的路由分数、 由另一个加载器写出的布局、 一次 graph 回放、 四千万次调用里的一次竞争、 第二张卡、 一份下游副本。 说出是哪个维度， 缺的那个测试通常就一目了然。
